**หัวข้อ:** ระบบนับวัตถุจากวิดีโอแบบเรียลไทม์บน FPGA ด้วย YOLO
**อัปเดต:** 23 สิงหาคม 2026

> เอกสารนี้อธิบาย **คอนเซปต์และกลไกการทำงาน** ของโครงงาน

## 1. โครงงานนี้คืออะไร (อ่าน 30 วินาที)

งานตรวจจับและนับวัตถุจากวิดีโอด้วย AI ทุกวันนี้ทำได้ดีอยู่แล้ว — **แต่ทำบนคอมพิวเตอร์ที่กินไฟหลายสิบวัตต์**
ซึ่งเป็นปัญหาเมื่อต้องติดตั้งที่หน้างานจริง หลายจุด ตลอด 24 ชั่วโมง

โครงงานนี้จึงเสนอ **FPGA (บอร์ด AMD Kria KV260)** เป็นทางเลือกแทนระบบเดิม แล้ว**พิสูจน์ด้วยงานจริง**
คือระบบนับพัสดุบนสายพานจากกล้อง โดยวัดผลเทียบกับระบบเดิมใน 4 มิติ: ความแม่นยำ ความเร็ว พลังงาน และความถูกต้องของการนับ

```
ปัญหาพลังงานของระบบเดิม → เสนอ KV260 เป็นทางเลือก → พิสูจน์ด้วยงานนับพัสดุ → วัด 4 มิติเทียบระบบเดิม
```

**ประโยคหลักของโครงงาน:**
> ระบบเดิมทำเรียลไทม์ได้ **แต่ต้องแลกด้วยพลังงาน ขนาด และต้นทุนต่อจุดตรวจที่สเกลไม่ไหว**
> โครงงานนี้เสนอ KV260 เป็นทางเลือกที่ให้ **ความเร็วเพียงพอต่องาน** ในงบพลังงานที่ต่ำกว่ามาก

## 2. ปัญหา — ระบบเดิมติดตรงไหน

**"ระบบเดิม"** ในที่นี้หมายถึงการรัน object detection บน**คอมพิวเตอร์ทั่วไปแบบโลคอล 100%**
ซึ่งเป็นรูปแบบที่คนคุ้นเคยที่สุดและเข้าถึงง่ายที่สุด

ระบบเดิม **ทำงานได้จริงและเร็วพอ** — ปัญหาไม่ได้อยู่ที่ความสามารถ แต่อยู่ที่**ต้นทุนของการได้ความสามารถนั้นมา**:

| ประเด็น | ระบบเดิม | ผลที่หน้างานจริง |
|---|---|---|
| **กำลังไฟ** | ทั้งเครื่องกินหลายสิบวัตต์ แม้ตอนโหลดต่ำ | ค่าไฟสะสม + ต้องมีระบบระบายความร้อน |
| **ขนาด** | ต้องมีเครื่องคอมทั้งเครื่อง | ติดตั้งข้างสายพาน/เสากล้องลำบาก |
| **ต้นทุนต่อจุดตรวจ** | 1 เครื่องต่อ 1 จุด (หรือ 1 เครื่องแรง ๆ ต่อหลายจุด) | ขยายหลายกล้องแล้วไม่คุ้ม |
| **ความทนทาน** | ฮาร์ดแวร์สำหรับสำนักงาน | ฝุ่น ความร้อน การสั่นสะเทือน |

> ⚠️ **สิ่งที่โครงงานนี้จะไม่เคลม:** ไม่เคลมว่า FPGA "เร็วกว่า" ระบบเดิม เพราะโดยทั่วไปแล้ว
> GPU ให้ throughput ดิบสูงกว่า — สิ่งที่เราเสนอคือ **ความเร็วที่เพียงพอต่องาน ในงบพลังงานที่ต่ำกว่ามาก**

## 3. ข้อเสนอ — ทำไม FPGA และทำไมต้อง KV260

### 3.1 ทำไม FPGA

FPGA คือชิปที่ **ปรับวงจรภายในได้** จึงสร้างวงจรเฉพาะทางสำหรับงานหนึ่ง ๆ ได้
วงจรที่ออกแบบมาตรงงานย่อมใช้พลังงานต่อการคำนวณน้อยกว่าชิปอเนกประสงค์อย่าง CPU/GPU

**แต่ปกติ FPGA มีกำแพงสูงมาก** — ต้องเขียน RTL (Verilog/VHDL) ออกแบบวงจรเอง
การออกแบบวงจรเร่งความเร็วสำหรับ YOLO ทั้งตัวเป็นงานขนาดใหญ่เกินกรอบเวลาของโครงงานนี้

**และมีเหตุผลที่สำคัญกว่าเรื่องเวลา:** คำถามของโครงงานคือ **การเทียบแพลตฟอร์มในสภาพใช้งานจริง
ไม่ใช่การออกแบบ accelerator ขึ้นใหม่** — ถ้าใช้วงจรที่ออกแบบเอง ผลเทียบจะไม่สะท้อนสิ่งที่คนทั่วไป
จะได้รับเมื่อเอาแพลตฟอร์มนี้ไปใช้จริง การใช้ toolchain มาตรฐานของผู้ผลิตจึงให้ผลที่เป็นตัวแทนมากกว่า

### 3.2 ทางลัดที่ทำให้เป็นไปได้: DPU

AMD ให้ **DPU (Deep-learning Processing Unit)** มาเป็น IP สำเร็จรูป — เป็นวงจรเร่งความเร็ว CNN
ที่ยัดลงส่วน FPGA ได้เลย **ไม่ต้องเขียน RTL เอง** แค่แปลงโมเดลให้อยู่ในรูปที่ DPU รับได้

```
โมเดล PyTorch  →  [แปลง]  →  ไฟล์ .xmodel  →  DPU รันได้เลย
                              (ไม่ต้องแตะ Verilog)
```

**แต่ทางลัดนี้มีราคาที่ต้องจ่าย 2 ข้อ — ซึ่งกลายเป็นแก่นของงานวิจัยนี้:**

| ข้อจำกัด | ความหมาย | ผลที่ตามมา |
|---|---|---|
| **รันได้เฉพาะ INT8** | ต้องบีบเลขทศนิยม 32 บิต → จำนวนเต็ม 8 บิต | ต้อง quantize · เกิดคำถามว่าเสียความแม่นยำเท่าไร |
| **รองรับ operation จำกัด** | op ที่ไม่รองรับต้องไปรันบน CPU | ต้องเลือก/ดัดแปลงโมเดลให้เข้ากับ DPU |

### 3.3 ทำไมเลือกศึกษา KV260 ตัวเดียว

**เหตุผลตรงไปตรงมา: งบและเวลาจำกัด จึงต้องเลือกศึกษาให้ลึกหนึ่งตัว แทนที่จะศึกษาหลายตัวแบบผิวเผิน**

KV260 ตอบโจทย์เพราะ:
- เป็นชิปแบบ **MPSoC** — มีทั้ง CPU (ARM) และ FPGA อยู่ในตัวเดียว จึงรัน Linux และคุมงานทั้งหมดได้ในบอร์ดเดียว ไม่ต้องมีเครื่องโฮสต์
- เป็น **Vision AI Starter Kit** — ออกแบบมาสำหรับงานกล้องโดยเฉพาะ
- มี DPU + toolchain (Vitis AI) พร้อมใช้ ไม่ต้องสร้างเอง

> การเลือกบอร์ดเดียวเป็น**ข้อจำกัดที่ประกาศไว้ล่วงหน้า** ไม่ใช่ข้อบกพร่องที่ซ่อนไว้
> ส่วนบอร์ดยี่ห้ออื่น (เช่น Efinix) ถูกย้ายไปเป็น **future work** — ดู §9

## 4. ระบบทำงานอย่างไร

### 4.1 ภาพรวม

บอร์ดแบ่งเป็น 2 ฝั่ง และงานถูกแบ่งกันทำ:
- **PS (Processing System)** = CPU ARM Cortex-A53 รัน Linux
- **PL (Programmable Logic)** = ส่วน FPGA ที่มี DPU อยู่ข้างใน

```
┌──────────────────────────── KV260 ────────────────────────────┐
│                                                                │
│  เฟรมวิดีโอ                                                     │
│      │                                                         │
│      ▼                                                         │
│  ┌─────────────────── PS (ARM Linux) ──────────────────┐       │
│  │ ① Preprocess: resize 640×640 → BGR→RGB → /255      │       │
│  │              → quantize เป็น int8                    │       │
│  └──────────────────────┬──────────────────────────────┘       │
│                         ▼                                      │
│  ┌─────────────────── PL (DPU B4096) ──────────────────┐       │
│  │ ② รันโครงข่าย CNN ทั้งตัวด้วย INT8                    │       │
│  │    → ออกมาเป็น 3 หัว ขนาด [H, W, 65]                 │       │
│  └──────────────────────┬──────────────────────────────┘       │
│                         ▼                                      │
│  ┌─────────────────── PS (ARM Linux) ──────────────────┐       │
│  │ ③ Dequantize → ④ DFL decode → ⑤ sigmoid → ⑥ NMS    │       │
│  │ ⑦ Tracker (centroid) → ⑧ นับเมื่อข้ามเส้น            │       │
│  └──────────────────────┬──────────────────────────────┘       │
│                         ▼                                      │
│                   จำนวนที่นับได้                                 │
└────────────────────────────────────────────────────────────────┘
```

### 4.2 แต่ละขั้นทำอะไร

**① Preprocess (บน PS)**
ย่อภาพเป็น 640×640, สลับช่องสีจาก BGR เป็น RGB, หารด้วย 255 ให้อยู่ในช่วง 0–1
แล้วแปลงเป็นจำนวนเต็ม 8 บิตด้วยค่า scale ที่ compiler ฝังไว้ในโมเดล

**② DPU inference (บน PL)**
DPU รันโครงข่ายทั้งหมดในครั้งเดียว ได้ผลลัพธ์ออกมา 3 ระดับความละเอียด (สำหรับวัตถุเล็ก/กลาง/ใหญ่)
แต่ละหัวมี **65 ช่อง** = 64 ช่องสำหรับตำแหน่งกล่อง + 1 ช่องสำหรับความมั่นใจว่าเป็นพัสดุ

**③ Dequantize (บน PS)**
แปลงจำนวนเต็มกลับเป็นทศนิยม เพื่อคำนวณต่อ

**④ DFL decode (บน PS)**
64 ช่องนั้นไม่ใช่พิกัดกล่องตรง ๆ แต่เป็น **การกระจายความน่าจะเป็นของระยะทาง 4 ด้าน × 16 ระดับ**
ต้องถ่วงน้ำหนักหาค่าคาดหวังก่อน ถึงจะได้ระยะจริงจากจุดอ้างอิงไปยังขอบกล่องทั้งสี่ด้าน
แล้วคูณด้วย stride ของแต่ละระดับ (8 / 16 / 32) เพื่อกลับเป็นพิกัดบนภาพ

**⑤ sigmoid → ⑥ NMS (บน PS)**
แปลงค่าดิบเป็นคะแนนความมั่นใจ 0–1 แล้วกำจัดกล่องที่ทับซ้อนกันให้เหลือกล่องเดียวต่อวัตถุ

**⑦ Tracker (บน PS)**
จับคู่กล่องในเฟรมนี้กับเฟรมก่อนหน้าด้วยระยะห่างจุดศูนย์กลาง (centroid) เพื่อให้รู้ว่าเป็น "ชิ้นเดิม"

**⑧ Line-crossing counter (บน PS)**
นับ +1 เมื่อวัตถุที่ติดตามอยู่ **ข้ามเส้นสมมติครั้งแรก** — การใช้เส้นแทนการนับกล่องในเฟรม
ป้องกันการนับซ้ำวัตถุเดียวกันหลายเฟรม

### 4.3 ทำไมต้องแบ่งงาน PS/PL แบบนี้

ไม่ได้แบ่งตามใจ แต่เป็นผลของข้อจำกัดจริง 2 ข้อ:

1. **DPU ทำได้เฉพาะ convolution และ op ที่รองรับ** — ขั้นตอน decode มีการคำนวณแบบ softmax
   ซึ่ง DPU ทำไม่ได้ จึงต้องอยู่บน PS
2. **ถ้าปล่อยให้ decode อยู่ในกราฟ compile จะล้ม** ด้วย error `XIR don't support multi-outputs op`
   จึงต้องตัดหัวโมเดลให้คืนค่าดิบออกมา แล้วไป decode เองบน PS

## 5. เส้นทางจากโมเดลถึงบอร์ด

```
โมเดล YOLO มาตรฐาน (.pt)
        │
        │ ⓐ สลับ activation: SiLU → LeakyReLU  แล้ว fine-tune ใหม่
        ▼
โมเดลที่ DPU รองรับ (.pt)
        │
        │ ⓑ vai_q_pytorch — quantize เป็น INT8 โดยใช้ภาพ calibration จากโดเมนจริง
        ▼
โมเดล INT8 + กราฟ XIR
        │
        │ ⓒ vai_c_xir — compile ให้ตรงกับ DPU B4096
        ▼
    .xmodel  ──► โหลดด้วย VART บนบอร์ด
```

### 5.1 ⓐ ทำไมต้องเปลี่ยน activation

YOLO มาตรฐานใช้ฟังก์ชัน **SiLU** ซึ่งต้องคำนวณ exponential — **DPU ทำไม่ได้**
จึงต้องเปลี่ยนเป็น **LeakyReLU ที่ความชัน 0.1015625** ✅ (ค่านี้ไม่ได้สุ่มมา — เป็นค่าที่แทนได้พอดีในระบบ fixed-point ของ DPU)

**แต่เปลี่ยนเฉย ๆ ไม่ได้** เพราะน้ำหนักที่เทรนมากับ SiLU ไม่เข้ากับ activation ใหม่ → ความแม่นยำพัง
**ต้อง fine-tune ใหม่หลังเปลี่ยน** ซึ่งพิสูจน์แล้วว่าได้ความแม่นยำกลับมาเกือบเท่าเดิม 🔄

> **ข้อค้นพบเชิงวิธีการ:** ข้อจำกัดเรื่อง activation ของ DPU เป็น **ต้นทุนเวลาเทรน ไม่ใช่ต้นทุนความแม่นยำ**

### 5.2 ⓑ ทำไม calibration ต้องใช้ภาพจากโดเมนจริง

การ quantize ต้องรู้ว่า "ค่าที่ไหลผ่านแต่ละชั้นอยู่ในช่วงไหน" เพื่อคำนวณ scale ของ INT8
วิธีรู้คือป้อนภาพตัวอย่างเข้าไปแล้วเก็บสถิติ

```
ใช้ภาพทั่วไป (คน รถ สัตว์)     →  สถิติของภาพหลากหลาย
                                    ↓
ใช้งานจริงกับภาพสายพาน           →  scale ไม่พอดี → ความแม่นยำตกโดยไม่จำเป็น
```

จึงต้องใช้ **ภาพจากงานจริง** เป็น calibration set

### 5.3 ⓒ กติกาตัดสินว่า "compile ผ่าน" คืออะไร

เมื่อ compiler เจอ op ที่ DPU ทำไม่ได้ มัน**ตัดกราฟตรงนั้น**แล้วส่งไปรันบน CPU แทน

```
ดี  (1 subgraph):  input → [═══════ DPU ทั้งหมด ═══════] → output

แย่ (3 subgraph):  input → [══ DPU ══] → [CPU] → [══ DPU ══] → [CPU] → [══ DPU ══] → output
                                      ↑ ต้องคัดลอกข้อมูลกลับ RAM แล้วส่งไปใหม่ทุกรอยตัด
```

**กติกาที่ตั้งไว้ตั้งแต่ต้นและไม่แก้ระหว่างทาง:**
> gate เดียวที่นับคือ log ของ `vai_c_xir` ที่ระบุ `DPU subgraph number 1`
> ไม่ใช่ op histogram ไม่ใช่ผลจากเครื่องมือ Inspector

เหตุผล: Inspector เป็นแค่คำแนะนำ (ดูจากรายชื่อ op) ส่วน compiler รู้เรื่องที่ Inspector ไม่รู้ —
ขนาด tensor เทียบหน่วยความจำของ DPU, รูปแบบการเชื่อมชั้น, ข้อจำกัดเฉพาะรุ่น

✅ **ผลจริง: โมเดลที่ใช้ compile ได้เป็น 1 DPU subgraph** บน DPUCZDX8G_ISA1_B4096
fingerprint `0x101000056010407` ตรงกับบอร์ดจริง

## 6. การปรับแต่งที่ทำและเหตุผล

| การปรับ | เหตุผล | ผลที่วัดได้ |
|---|---|---|
| SiLU → LeakyReLU(0.1015625) | DPU ไม่รองรับ SiLU | ✅ ทำให้ map ลง DPU ได้ · ความแม่นยำกลับมาหลัง fine-tune |
| ตัด decode ออกจากกราฟ | เลี่ยง `XIR don't support multi-outputs op` | ✅ ได้ 1 subgraph |
| ลดเหลือ 1 คลาส (`package`) | งานนี้ต้องการตรวจแค่พัสดุ ไม่ต้องการ 80 คลาส | ✅ output 144 → **65 ช่อง** · 🔄 throughput 68 → 82.5 FPS |
| calibration จากโดเมนจริง | scale ของ INT8 ต้องตรงกับภาพที่จะเจอจริง | 🔄 ความแม่นยำหลัง quantize ดีขึ้น |

> การที่ FPS เพิ่มขึ้นจากการลดจำนวนคลาส เป็นหลักฐานว่า **ชั้น output มีต้นทุน runtime จริง**
> ไม่ใช่แค่ทฤษฎี — เป็นตัวอย่างของการ optimize โมเดลให้ตรงกับงาน

## 7. งานที่ใช้พิสูจน์ — ระบบนับพัสดุ

การพิสูจน์ว่า "detect ได้" ยังไม่พอ เพราะโมเดลอาจตรวจจับแม่นแต่ tracking ผิดพลาด
ทำให้พัสดุชิ้นเดียวถูกนับสองครั้ง **งานปลายทางจึงต้องเป็นการนับ ไม่ใช่การตรวจจับ**

**วิธีวัด:** ใช้วิดีโอสายพานจริงที่**นับด้วยมือ**ไว้เป็น ground truth แล้วเทียบกับที่ระบบนับได้

**สองโหมดการทำงานที่แยกกันโดยตั้งใจ:**

| โหมด | ทำอะไร | ใช้เมื่อไร |
|---|---|---|
| **production** | detect → track → count → ส่งออกแค่ตัวเลข | ใช้วัดผลทุกอย่าง |
| **debug / demo** | บันทึกกล่องเป็น JSON แล้วนำไป render เป็นวิดีโอบนเครื่องโฮสต์ | ใช้ตรวจสอบและสาธิต |

> **ทำไมต้องแยก:** การวาดกล่องและ encode วิดีโอ **ไม่ใช่ส่วนของระบบจริง** — ระบบนับที่หน้างานส่งออกแค่ตัวเลข
> ถ้าเอาเวลา render ไปรวมในการวัดความเร็ว จะทำให้ผลบิดเบือนและไม่ยุติธรรมกับฝั่ง ARM

## 8. จะพิสูจน์ว่าดีกว่าอย่างไร

เทียบ **4 ระบบ** ที่รันงานเดียวกันทุกประการ:

| ระบบ | บทบาท |
|---|---|
| **KV260** | ข้อเสนอของโครงงาน |
| **Jetson Nano** | คู่แข่ง edge โดยตรง (คนละสถาปัตยกรรม: GPU ฝังตัว) |
| **คอม + GPU** | ระบบเดิมแบบมีการ์ดจอ |
| **คอม CPU ล้วน** | ระบบเดิมแบบไม่มีการ์ดจอ (พบบ่อยที่หน้างาน) |

วัด 4 มิติ: **ความแม่นยำ · ความเร็ว · พลังงาน · ความถูกต้องของการนับ**

**หัวใจของการเทียบคือ "ที่ความเร็วเท่ากัน ใครกินไฟน้อยกว่า"** (iso-throughput) —
เพราะข้อเสนอของโครงงานไม่ใช่ "เร็วกว่า" แต่คือ "เร็วพอ ในงบไฟที่ต่ำกว่า"

> รายละเอียดว่าจะทำให้การเทียบยุติธรรมได้อย่างไร — ขอบเขตการวัดพลังงาน, precision ที่แต่ละเครื่องทำได้ไม่เท่ากัน,
> เครื่องมือวัด, จำนวนรอบการทดลอง — อยู่ใน [`METHODOLOGY.md`](METHODOLOGY.md) ทั้งหมด

## 9. เรื่องที่เคยตั้งใจทำแต่ปรับบทบาทแล้ว

### 9.1 YOLO26 — จากเป้าหมายหลัก เป็นเหตุผลประกอบการเลือกโมเดล

เดิมตั้งใจใช้ **YOLO26** ซึ่งเป็นโมเดลรุ่นใหม่ แต่เมื่อวิเคราะห์กราฟ operation แล้วพบว่า
**map ลง DPU รุ่นนี้ไม่ได้ทั้งตัว** ✅ โดยติดที่จุดที่ไม่คาดคิด:

- ❌ **ไม่ได้ติดที่ NMS-free head** อย่างที่คาดกันทั่วไป (ตั้งค่า flag เดียวก็แก้ได้)
- ✅ **ติดที่ attention block 2 จุดกลางกราฟ** (ตำแหน่ง ~32% และ ~69%) ซึ่งใช้ `MatMul → Softmax → MatMul`

**ทำไม DPU ทำไม่ได้ — 2 เหตุผลอิสระ:**
1. DPU ออกแบบบนสมมติฐานว่า**ตัวคูณฝั่งหนึ่งเป็นน้ำหนักคงที่**ที่โหลดล่วงหน้าได้
   แต่ attention คูณข้อมูลสองก้อนที่เปลี่ยนทุกครั้ง
2. Softmax ต้องใช้ exponential — เหตุผลเดียวกับที่ทำ SiLU ไม่ได้

**ข้อสรุปเชิงกลไกที่มีค่าที่สุดจากเรื่องนี้:**
> **op ที่ DPU ไม่รองรับจะร้ายแรงแค่ไหน ขึ้นกับว่ามันอยู่ "ตรงไหน" ในกราฟ**
> อยู่ปลายกราฟ = ไม่กระทบ (ยังเป็น 1 subgraph) · อยู่กลางกราฟ = ตัด pipeline เป็นชิ้น

และเมื่อขยายผล ข้อค้นพบนี้ไม่ได้จำกัดแค่ YOLO26 แต่ครอบคลุม **โมเดลตระกูล attention-based ทั้งกลุ่ม**
ซึ่งเป็นทิศทางที่วงการกำลังเดินไป ขณะที่ DPU รุ่นนี้ออกแบบมาสำหรับยุค CNN ล้วน

**บทบาทใหม่:** เขียนเป็นหัวข้อ **"ทำไมจึงเลือกโมเดลที่ใช้"** ความยาว 1–2 หน้า
ไม่ใช่บทหลัก — เพราะแก่นของโครงงานคือการเทียบพลังงาน ไม่ใช่การไล่ตามโมเดลรุ่นใหม่

### 9.2 Efinix Ti375 — ย้ายไป Future Work

เดิมตั้งใจ port ระบบเดียวกันไปบอร์ด Efinix (สถาปัตยกรรมคนละแบบ: soft RISC-V + TFLite)
**ย้ายเป็น future work** เพราะเวลาไม่พอ และเพื่อไม่ให้ขัดกับเหตุผลที่ประกาศไว้ว่าเลือกศึกษาบอร์ดเดียว

แต่งานส่วนที่ทำไปแล้วยังมีค่า เพราะแสดงให้เห็นว่า **ไปป์ไลน์ที่สร้างขึ้นผูกกับแพลตฟอร์มพอสมควร**
— ย้ายไปบอร์ดอื่นแล้วเจอข้อจำกัดคนละชุด ซึ่งเป็นประเด็นที่ควรพูดถึงในเล่ม
