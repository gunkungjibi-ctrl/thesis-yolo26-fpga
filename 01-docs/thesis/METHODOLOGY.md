# METHODOLOGY — เอกสารล็อกวิธีวัด (Frozen Measurement Protocol)

**โครงงาน:** Real-Time Video-Based Object Counting on FPGA (KV260)
**สร้าง:** 23 สิงหาคม 2026 · **สถานะ:** 🟡 ร่าง — ยังไม่ freeze
**Deadline โครงงาน:** 1–2 เดือน (ประมาณ 23 ก.ย. – 23 ต.ค. 2026)

---

## 0. วิธีใช้เอกสารนี้

เอกสารนี้คือ **สัญญาที่ทำกับตัวเองก่อนลงมือวัด** — ใช้หลักการเดียวกับกติกา `vai_c_xir` ที่ตั้งไว้แต่แรก
และพิสูจน์แล้วว่ากันการหลอกตัวเองได้จริง

**กฎการใช้งาน:**
1. ทุกช่อง `[REF-xx]` คือจุดที่ต้องหาเปเปอร์/แหล่งอ้างอิงมาสนับสนุน (ดู §11)
2. เมื่อเติมครบและตัดสินใจครบ → เปลี่ยนสถานะเป็น **FROZEN** พร้อมลงวันที่
3. **หลัง freeze ห้ามแก้วิธีวัดระหว่างเก็บข้อมูล** — ถ้าจำเป็นต้องแก้ ต้องบันทึกเหตุผลและ**วัดใหม่ทั้งชุด**
4. ตัวเลขที่วัดก่อน freeze ถือเป็น pilot run ใช้ debug ได้ แต่ไม่เข้าเล่ม

> **หลักการเรื่องเปเปอร์ (ตามที่ตกลงไว้):** เปเปอร์มีไว้ **สนับสนุน** methodology ที่เราออกแบบ
> ไม่ใช่มาเปลี่ยนคอนเซปต์ของเรา — แต่ถ้าเจอเปเปอร์ที่**ขัด**กับวิธีของเรา ให้บันทึกไว้ใน §10
> แล้วเขียนเหตุผลว่าทำไมเราเลือกต่างจากเขา (ดีกว่าปล่อยให้กรรมการเจอเอง)

## 1. คอนเซปต์ที่ล็อกแล้ว (ห้ามแก้)

**โครงเรื่อง:**
```
ปัญหาพลังงานของระบบเดิม → เสนอ KV260 เป็นทางเลือก → พิสูจน์ด้วยงานจริง (นับพัสดุ) → วัด 4 มิติเทียบระบบเดิม
```

**ประโยคหลักของโครงงาน:**
> ระบบเดิมทำเรียลไทม์ได้ **แต่ต้องแลกด้วยพลังงาน ขนาด และต้นทุนต่อจุดตรวจที่สเกลไม่ไหว**
> โครงงานนี้เสนอ KV260 เป็นทางเลือกที่ให้**ความเร็วเพียงพอต่องาน**ในงบพลังงานที่ต่ำกว่ามาก

**สิ่งที่ห้ามเคลม:**
- ❌ "FPGA เร็วกว่า GPU" — ข้อมูลของเราเองขัด (GPU e2e เร็วกว่า)
- ❌ "FPGA ดีกว่าทุกมิติ" — ต้องระบุมิติเสมอ
- ❌ "ระบบเดิมทำเรียลไทม์ไม่ได้" — ทำได้ แต่แพงด้านพลังงาน

**สิ่งที่ยอมรับได้และควรพูด:**
- ✅ KV260 มีข้อจำกัด (PS-bound, throughput ต่ำกว่า) — การแสดงว่า **"KV260 ไม่ใช่พระเจ้า"** ทำให้เล่มน่าเชื่อถือขึ้น ไม่ใช่ลดค่า

## 2. นิยามเชิงปฏิบัติการ (ต้องล็อกก่อนวัด)

### 2.1 "เรียลไทม์" คืออะไร

**นิยามที่เลือก:**
> **เรียลไทม์ = ประมวลผลได้เร็วพอที่จะไม่พลาดวัตถุที่ต้องนับ ภายใต้อัตราการเกิดเหตุการณ์ของ use case**

**เกณฑ์ผ่านเชิงตัวเลข (ต้องเติม):**

| รายการ | ค่า | ที่มา |
|---|---|---|
| อัตราการเกิดวัตถุ | 1 ชิ้น / ~2.8 วินาที | วัดจากคลิป GT (215 ชิ้น / 600 วิ) |
| เวลาที่วัตถุอยู่ในเฟรม (transit time) | 🕓 **เลื่อนไปทำทีหลัง** | วัดจาก `dets600.json` — สำคัญกว่าอัตราการเกิด |
| จำนวนเฟรมขั้นต่ำต่อวัตถุที่ tracker ต้องการ | 🕓 **เลื่อน** | `[REF-05]` |
| → **FPS ขั้นต่ำที่ต้องการ** | 🕓 **เลื่อน** — คำนวณจาก 2 ค่าบน | — |

> ⚠️ **ห้ามข้ามขั้นนี้ตอนเข้าเล่ม** — ถ้าไม่มีตัวเลข FPS ขั้นต่ำที่คำนวณจาก use case จริง
> คำว่า "เพียงพอ" จะเป็นแค่ความเห็น และจะโดนถามทันทีว่า "เพียงพอตามใคร"
>
> 🕓 **สถานะ:** ตกลงกันแล้วว่าเลื่อนไปทำหลังจากแก่นแข็งแรง — **แต่ต้องทำก่อนกำหนดค่า iso-throughput ใน §4.3**
> เพราะค่า FPS ที่ใช้บังคับทุกระบบต้องมาจากตัวเลขนี้ ไม่ใช่เลือกลอย ๆ

**หลักฐานสนับสนุนที่มีอยู่แล้ว:** ระบบนับถูก 215/215 ขณะประมวลผลที่ ~10 FPS
→ เป็นหลักฐานเชิงประจักษ์ว่า 10 FPS เพียงพอสำหรับ use case นี้ (แต่ต้องวัดใหม่ตาม protocol นี้)

### 2.2 "ระบบเดิม" คืออะไร

> **ระบบเดิม = การรัน object detection บนคอมพิวเตอร์ทั่วไปแบบโลคอล 100%**
> (ไม่พึ่ง cloud) ซึ่งเป็นรูปแบบที่ผู้ใช้ส่วนใหญ่คุ้นเคยและเข้าถึงได้

แยกเป็น 2 กรณีย่อย เพราะไม่ใช่ทุกเครื่องมี GPU:
- **ระบบเดิม-A:** คอม + discrete GPU
- **ระบบเดิม-B:** คอม CPU ล้วน (พบบ่อยที่หน้างานจริง)

### 2.3 "ความแฟร์" คืออะไร

> **การเทียบจะถือว่าแฟร์ก็ต่อเมื่อ ทุกแพลตฟอร์มได้ใช้ toolchain ที่ดีที่สุดของตัวเอง
> ภายใต้ขอบเขตการวัด นิยาม metric และ workload ที่เหมือนกันทุกประการ**

หมายความว่า **ต้องไม่**ทำให้ฝั่งใดฝั่งหนึ่งเสียเปรียบด้วยเหตุผลทางวิศวกรรมซอฟต์แวร์
(เช่น รัน GPU ด้วย PyTorch เปล่าแล้วบอกว่า FPGA ชนะ — ไม่แฟร์กับ GPU)

### 4.1 F2 ขยาย — ปัญหา precision ที่เทียบตรง ๆ ไม่ได้ และทางออก

**ตารางความสามารถจริงของแต่ละแพลตฟอร์ม:**

| ระบบ | INT8 | FP16 | FP32 | ข้อจำกัด |
|---|:---:|:---:|:---:|---|
| S1 KV260 (DPU) | ✅ | ❌ | ❌ | DPU รันได้เฉพาะ INT8 |
| S2 Jetson Nano | ❌ | ✅ | ✅ | Maxwell ไม่มีฮาร์ดแวร์ INT8 |
| S3 Laptop GPU (Turing) | ✅ | ✅ | ✅ | ทำได้ครบ |
| S4 CPU | ✅ | — | ✅ | ผ่าน OpenVINO/ONNX Runtime |

> **ไม่มี precision ตัวไหนที่ทุกระบบทำได้เหมือนกัน** — นี่ไม่ใช่ความผิดพลาดของการออกแบบการทดลอง
> แต่เป็น**ข้อจำกัดเชิงสถาปัตยกรรมที่ติดมากับฮาร์ดแวร์แต่ละรุ่น** ซึ่งเป็นส่วนหนึ่งของ trade-off ที่กำลังศึกษาอยู่

**ทางออก 3 ชั้น:**

1. **หลักการ:** ให้ทุกแพลตฟอร์มรัน **precision ที่ดีที่สุดที่ตัวเองรองรับ** (สอดคล้องกับ F5 — ทุกฝั่งได้ใช้ของดีที่สุดของตัวเอง)
2. **ตัวปรับให้แฟร์:** ใช้ ⭐ **iso-accuracy** เป็นแกนหลักคู่กับ iso-throughput — ถ้าทุกระบบทำ mAP ได้ใกล้เคียงกัน
   การเทียบพลังงาน/ความเร็วก็ยุติธรรมในระดับ **ผลลัพธ์ของงาน** แม้ precision ต่างกัน
3. **ตัวควบคุม (control):** ⭐ **S3 (laptop GPU) ทำได้ครบทุก precision** → ใช้เป็นตัวชี้วัดว่า
   "การเปลี่ยน precision อย่างเดียวมีผลต่อ accuracy/speed/power เท่าไร" บนฮาร์ดแวร์เดียวกัน
   → ทำให้แยกได้ว่าความต่างที่เห็นมาจาก **precision** หรือมาจาก **สถาปัตยกรรม**

> 💡 **นี่เปลี่ยนจากปัญหาเป็นข้อค้นพบได้:** "ความสามารถด้าน precision เป็นข้อจำกัดตามรุ่นฮาร์ดแวร์
> KV260 บังคับ INT8 ส่วน Jetson Nano บังคับ FP16 — ทั้งคู่คือข้อจำกัดของยุคที่ออกแบบมา"
> เขียนเป็นเนื้อหาได้เต็ม ๆ และแสดงว่าเข้าใจสถาปัตยกรรมจริง

### 4.2 F8 ขยาย — ไปป์ไลน์ฝั่งระบบที่นำมาเทียบ

เอกสารเดิมกำหนดไปป์ไลน์ฝั่ง KV260 ไว้ละเอียด แต่ไม่ได้กำหนดฝั่งที่เอามาเทียบ
ซึ่งเป็นช่องโหว่ เพราะ **ความแฟร์ครึ่งหนึ่งอยู่ที่ฝั่งนั้น**

**โครงสร้างที่ทุกระบบต้องเหมือนกัน:**

```
เตรียมภาพ → [ รันโมเดล ] → ถอดรหัสกรอบ → คัดกรอบซ้อนทับ → ติดตาม → นับ
                  ▲
        ส่วนเดียวที่ต่างกันตามแพลตฟอร์ม
```

| ระบบ | ตัวรันโมเดล | เส้นทางแปลงโมเดล | precision |
|---|---|---|---|
| S1 KV260 | DPU (PL) | `.pt` → `vai_q_pytorch` → `vai_c_xir` → `.xmodel` → VART | INT8 |
| S2 Jetson Nano | GPU Maxwell | `.pt` → ONNX → TensorRT (`trtexec`) → `.engine` | FP16 / FP32 |
| S3 Laptop GPU | GPU Turing | `.pt` → ONNX → TensorRT | FP32 / FP16 / INT8 |
| S4 CPU | CPU | `.pt` → ONNX → OpenVINO IR หรือ ONNX Runtime | FP32 / INT8 |

**กฎ 3 ข้อที่ต้องบังคับใช้:**

1. **โมเดลชุดเดียวกัน — export ONNX ครั้งเดียวแล้วให้ทุกแพลตฟอร์มแปลงจากไฟล์นั้น**
   → ความต่างที่วัดได้จึงมาจากฮาร์ดแวร์และ precision เท่านั้น
   ☐ **ต้องตัดสิน:** ทุกระบบใช้โมเดล **LeakyReLU** (ตัวเดียวกับที่ KV260 ต้องใช้) หรือให้ S2–S4 ใช้ SiLU ตัวเดิม
   → **แนะนำ: ใช้ LeakyReLU ทุกระบบเป็นผลหลัก** เพราะคุมตัวแปรได้ดีที่สุด และ LeakyReLU ถูกกว่า SiLU
   เล็กน้อยจึงไม่ได้ทำให้ฝั่ง GPU/CPU เสียเปรียบ · จะรายงานผลตัว SiLU บน S3/S4 เป็นเชิงอรรถก็ได้

2. **โค้ด postprocess ชุดเดียวกันทุกระบบ** (decode / NMS / tracker / counter)
   → ถ้าใช้คนละ implementation ผลที่ต่างจะแยกไม่ออกว่ามาจากฮาร์ดแวร์หรือซอฟต์แวร์
   ☐ **ต้องตัดสิน:** ใช้โค้ด Python ชุดเดิมทุกระบบ หรือพอร์ตเป็น C++ ทุกระบบ — **ต้องเป็นแบบเดียวกันหมด**

3. **แต่ละแพลตฟอร์มใช้ toolchain ที่ดีที่สุดของตนเอง** (สอดคล้อง F5) — ห้ามรัน PyTorch เปล่าบน GPU/CPU

> ⚠️ **ผลข้างเคียงที่ต้องรายงานตรง ๆ:** postprocess รันบน CPU ของแต่ละระบบ ซึ่ง x86 เร็วกว่า
> Cortex-A53 มาก ผล end-to-end จึงวัด "ทั้งระบบ" ไม่ใช่ "ตัวเร่ง" — เป็นเหตุผลที่ F4 บังคับให้รายงาน 2 ระดับ

### 4.3 F7 ขยาย — จุดเทียบ 3 แบบ (แกนที่สำคัญที่สุดของเล่ม)

| แบบ | วิธี | ตอบคำถามว่า |
|---|---|---|
| **iso-throughput** ⭐ | บังคับทุกระบบให้วิ่งที่ FPS เท่ากัน (= FPS ขั้นต่ำจาก §2.1) แล้ววัดพลังงาน | "ถ้าต้องการงานคุณภาพเท่ากัน ระบบไหนกินไฟน้อยกว่า" |
| **iso-power** | จำกัดพลังงานเท่ากัน แล้ววัดว่าได้ FPS เท่าไร | "ในงบไฟเท่ากัน ระบบไหนทำงานได้มากกว่า" |
| **iso-accuracy** | ปรับให้ mAP เท่ากัน แล้ววัดทั้ง FPS และ W | "ถ้าคุณภาพการตรวจจับเท่ากัน ต้นทุนต่างกันแค่ไหน" |

> **iso-throughput คือจุดเทียบที่ตรงกับข้อเสนอของโครงงานที่สุด** เพราะคอนเซปต์คือ
> "ให้ความเร็วเพียงพอต่องาน ในงบพลังงานที่ต่ำกว่า" — ต้องพิสูจน์ตรงๆ ว่าที่ FPS เท่ากัน KV260 กินไฟน้อยกว่า

**วิธีบังคับ FPS ให้เท่ากัน:** ใส่ frame limiter (sleep ให้ครบ period) ในทุกระบบ แล้ววัดพลังงานเฉลี่ยตลอดช่วง
รวมช่วงที่ระบบ idle รอเฟรมถัดไป — **ห้ามตัดช่วง idle ออก** เพราะระบบจริงก็ต้องรอเหมือนกัน

| Metric | นิยาม | หน่วย | หมายเหตุ |
|---|---|---|---|
| **Accuracy** | mAP@0.5 และ mAP@0.5:0.95 | — | ต้องใช้ evaluator ตัวเดียวกันทุกระบบ |
| **Latency (accel-only)** | เวลา inference บนตัวเร่งอย่างเดียว | ms | ไม่รวม pre/post |
| **Latency (e2e)** | เฟรมเข้า → ได้ผลนับ | ms | **ไม่รวม** การวาด/encode วิดีโอ |
| **Throughput** | เฟรมต่อวินาที ที่ batch=1 | FPS | |
| **Power (DC board)** | กำลังไฟที่ขั้ว DC input ของบอร์ด | W | S1, S2 เท่านั้น |

| **Efficiency** | FPS/W | — | ต้องระบุเสมอว่าใช้ power ตัวไหน |

## 7. Protocol การวัด (ต้องเหมือนกันทุกระบบ)

```
1. ปิดโปรเซสอื่นให้หมด บันทึกสถานะระบบ (temp, freq governor, background load)
2. Warm-up: รัน ☐N เฟรม ทิ้ง (จนอุณหภูมิและ FPS นิ่ง)
3. วัด idle power ☐T วินาที (ก่อนเริ่มงาน)
4. รันงานจริง ☐M เฟรม พร้อมบันทึก power ต่อเนื่อง (sampling ≥ ☐Hz)
5. บันทึก: timestamp เริ่ม/จบ ให้ตรงกับ power trace (สำคัญมาก)
6. ทำซ้ำข้อ 2–5 ทั้งหมด ≥5 รอบ
7. รายงาน mean ± std ทุกค่า + ระบุจำนวนรอบ
```

**ค่าที่ต้องกำหนดก่อน freeze:** N (warm-up), T (idle), M (จำนวนเฟรม), sampling rate, จำนวนรอบ

**สิ่งที่ต้องบันทึกทุกรอบ (reproducibility):**
- เวอร์ชัน toolchain / driver / OS ทุกฝั่ง
- อุณหภูมิเริ่มต้นและสูงสุด
- CPU governor / power mode (Jetson มีหลาย power mode — **ต้องระบุว่าใช้โหมดไหน**)
- คำสั่งที่รันแบบเต็ม

> ⚠️ **ตัวเลขชุดเดิมทั้งหมดวัดครั้งเดียว ไม่มี variance** — นี่เป็นเหตุผลเชิงวิชาการที่ต้องวัดใหม่จริง
> ไม่ใช่แค่เพราะเปลี่ยน dataset

## 8. เครื่องมือวัดพลังงาน — ผลการค้นข้อมูล ⭐

### 8.1 มาตรฐานอ้างอิง

**MLPerf Power** คือ methodology มาตรฐานของวงการสำหรับวัดพลังงาน ML ตั้งแต่ระดับ µW ถึง MW
โดย**กำหนดให้ใช้ power analyzer ที่ผ่านการรับรอง SPEC เช่น Yokogawa WT310**
(ความแม่นยำ ±0.1% ของค่าอ่าน + 0.05% ของ range) — ราคาระดับหลายหมื่นถึงแสนบาท เกินงบ

**ท่าทีที่ควรใช้ในเล่ม:** อ้าง MLPerf Power เป็น reference standard → ระบุว่าเราใช้เครื่องมือระดับรองลงมา
→ **รายงาน uncertainty ของเครื่องมือเราอย่างตรงไปตรงมา** วิธีนี้ทำให้ผลยังน่าเชื่อถือและกรรมการเห็นว่ารู้ว่ากำลังทำอะไร

### 8.2 🚨 คำเตือนสำคัญ — smart plug ราคาถูก "ใช้ไม่ได้" สำหรับงานวิจัย

มีงานวิจัยที่ทดสอบ smart plug วัดพลังงาน 5 ยี่ห้อ (Belkin, TP-Link, Etekcity, Emporia, Sonoff) พบว่า:

| ประเด็น | ผล |
|---|---|
| ความคลาดเคลื่อนพลังงาน | **Belkin ไม่เกิน 1.7%** แต่ **อีก 4 ยี่ห้อ 54–100%** |
| เมื่อโหลดแกว่ง | ทุกยี่ห้อคลาดเคลื่อนมาก แม้โหลดแกว่งช้าแค่ 0.01–0.05 Hz |
| ความหน่วงในการรายงาน | 3–6 วินาที บางตัวถึง 20 วินาที |

**ทำไมเรื่องนี้ร้ายแรงกับงานเรา:** งาน inference คือโหลดที่**แกว่งตลอดเวลา** (burst ตอนประมวลผล
แล้ว idle ตอนรอเฟรม) ซึ่งเป็นสภาวะที่ smart plug คลาดเคลื่อนมากที่สุดพอดี

**Shelly Plug S** โดยเฉพาะ: sense resistor 1mΩ ความแม่นยำ 10–20% และชิป HLW8012 ส่งค่าเป็นความถี่
ที่โหลดต่ำความถี่จะต่ำมาก (12W ได้แค่ 1Hz) → **วัด KV260 ที่ 5–10W แทบไม่ได้เลย**

> ✅ **ข้อดี:** เรื่องนี้กลายเป็น**เนื้อหาในเล่ม**ได้ — เป็นเหตุผลเชิงวิชาการว่าทำไมเราเลือกเครื่องมือแบบที่เลือก
> พร้อมอ้างอิงงานวิจัยรองรับ ตรงกับที่คุณต้องการเน้นเรื่องความน่าเชื่อถือ

### 8.3 ตัวเลือกที่แนะนำ

| ตัวเลือก | ราคา | ข้อดี | ข้อเสีย |
|---|---|---|---|
| ⭐ **A. INA226/INA228 breakout + MCU** วัด DC ที่ขั้ว 12V ของบอร์ด | ~฿200–600 | แม่นที่กระแสต่ำ · sample rate สูง · ดึงข้อมูลผ่าน I2C/serial ตรง · **มีงานวิจัย FPGA ใช้วิธีนี้** · คุณมีประสบการณ์ INA260 อยู่แล้ว | ใช้ได้เฉพาะ DC (S1, S2) · ต้องต่อวงจรเอง |
| **B. ElmorLabs PMD-USB** | ~$60 (฿2,100) | turnkey · USB-C logging + oscilloscope · 0–15.5V/0–60A · ความคลาดเคลื่อนกระแส ≤3% · **ซีรีส์ Edge AI Power Benchmarking ใช้ตัวนี้** | คอนเนกเตอร์เป็นแบบ PC (EPS/PCIe) ต้องทำสายแปลงเข้า barrel jack เอง |
| **C. Belkin smart plug** (สำหรับฝั่ง AC) | ~฿800–1,500 | เป็นยี่ห้อเดียวในงานวิจัยที่คลาดเคลื่อน <1.7% | ความหน่วง 3–6 วิ · ไม่เหมาะโหลดแกว่ง · หาซื้อในไทยยาก |
| **D. AC power meter + logging** | ฿1,500–5,000 | วัดฝั่ง AC ได้ทุกระบบรวมโน้ตบุ๊ก | ต้องตรวจสเปกความแม่นยำที่โหลดต่ำก่อนซื้อ |

### 8.4 เซนเซอร์ในตัวบอร์ด — ของฟรีที่มีอยู่แล้ว (แต่มีเงื่อนไข)

| บอร์ด | เซนเซอร์ในตัว | อ่านยังไง | วัดอะไร |
|---|---|---|---|
| KV260 | **INA260** (`ina260_u14`) | sysfs | ราง SOM |
| Jetson Nano 4GB | **INA3221** | `/sys/bus/i2c/drivers/ina3221x/6-0040/iio:device0/in_power1_input` | ราง POM (แยกช่อง) |

⚠️ **แต่ใช้เทียบกันตรง ๆ ไม่ได้ เพราะวัดคนละราง** — ขอบเขตต่างกันคือสิ่งเดียวกับที่เราตำหนิว่าไม่แฟร์ในเวอร์ชันเก่า

⚠️ **และเซนเซอร์ในตัวมีข้อจำกัดที่มีงานวิจัยระบุไว้:** วัดได้เป็นค่าเฉลี่ย **จับ peak ไม่ทัน**
และ sampling rate มีผลต่อความแม่นยำ — มีงานวิจัยเรื่องการ calibrate เซนเซอร์ภายในของ Jetson โดยเฉพาะ `[REF-10]`

### 8.5 ข้อเสนอ — แผนวัดพลังงาน 2 ชั้น

```
ชั้นที่ 1 (หลัก — เทียบ S1 vs S2 อย่างแม่นยำ):
  INA226 ต่อ inline ที่ "ขั้ว DC input" ของทั้ง KV260 และ Jetson Nano
  → ขอบเขตเดียวกัน (ทั้งบอร์ด) วิธีเดียวกัน เครื่องมือเดียวกัน = แฟร์ที่สุด
  → ใช้เซนเซอร์ในตัว (INA260 / INA3221) เป็น cross-check เท่านั้น ไม่ใช่ตัวเลขหลัก

ชั้นที่ 2 (บริบท — เทียบ edge vs ระบบเดิม):
  AC wall power ทุกระบบรวมโน้ตบุ๊ก
  → ตอบคำถาม "ถ้าติดตั้งจริงที่หน้างาน ค่าไฟต่างกันแค่ไหน"
```

**เหตุผลที่ต้องมี 2 ชั้น:** ชั้นที่ 1 แฟร์เชิงเทคนิค (accelerator ต่อ accelerator)
ชั้นที่ 2 แฟร์เชิงการใช้งานจริง (ผู้ใช้จ่ายค่าไฟที่ปลั๊ก ไม่ใช่ที่ชิป)
— **และชั้นที่ 2 คือชั้นที่เข้าข้างข้อเสนอของโครงงานมากที่สุด** เพราะคอมทั้งเครื่องที่วิ่ง 10 FPS
ยังกินระดับหลายสิบวัตต์ ขณะที่ KV260 ทั้งบอร์ดกินระดับ 5–10 W

**ประโยชน์เพิ่ม:** การมีทั้งเซนเซอร์ในตัวและเครื่องวัดภายนอกทำให้**เทียบสองวิธีกันเองได้**
→ เขียนเป็นหัวข้อ "ความน่าเชื่อถือของการวัด" ในเล่มได้ พร้อมอ้าง `[REF-10]` รองรับ

☐ **ต้องตัดสินใจ:** จะซื้อ INA226 breakout หรือ PMD-USB / วัดฝั่ง AC ด้วยอะไร

| เครื่องมือวัดพลังงานไม่ใช่ระดับ SPEC-certified | ตัวเลขพลังงานมี uncertainty สูงกว่ามาตรฐาน MLPerf | รายงาน uncertainty ตรงไปตรงมา + ใช้ INA226 ที่แม่นที่กระแสต่ำ |

| ARM Cortex-A53 ช้ากว่า CPU เดสก์ท็อปมาก | e2e ของ KV260 ดูแพ้ ทั้งที่ DPU ไม่ได้ช้า | รายงาน 2 ระดับตาม F4 + อธิบายว่าเป็นข้อจำกัดของ PS ไม่ใช่ accelerator |
| ชุดข้อมูล application เล็ก | mAP มี variance สูง | ใช้ COCO เป็นชั้น benchmark คู่กัน |
| counting วัดบนคลิปเดียว | ไม่ generalize | ☐ ตัดคลิปที่ 2 จากวิดีโอ 12 ชม. ต้นฉบับ (ต้นทุนต่ำ ผลตอบแทนสูง) |
| **precision เทียบข้ามระบบไม่เท่ากัน** (INT8 vs FP16) | อาจถูกแย้งว่าเทียบไม่แฟร์ | ใช้ iso-accuracy เป็นตัวปรับ + ใช้ S3 เป็น control ที่รันได้ทุก precision (§4.1) |
| Jetson Nano เป็นรุ่นเก่า/EOL ไม่มี tensor core | อาจถูกมองว่าเลือกคู่แข่งที่อ่อน | ระบุตรง ๆ ว่าเลือกเพราะ**อยู่ในยุคและระดับราคาใกล้เคียง KV260** + เป็นสิ่งที่มีอยู่ (ข้อจำกัดงบ) |
| เซนเซอร์ในตัวบอร์ดจับ peak ไม่ทัน | พลังงานที่รายงานอาจต่ำกว่าจริง | ใช้เครื่องวัดภายนอกเป็นตัวเลขหลัก + cross-check กับเซนเซอร์ในตัว `[REF-10]` |
