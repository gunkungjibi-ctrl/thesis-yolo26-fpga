## 1. โครงงานนี้ทำอะไร

โครงงานนี้สร้าง **ระบบนับพัสดุบนสายพานลำเลียงจากภาพวิดีโอ** ให้ทำงานได้จริงบนบอร์ด FPGA
แล้วเปรียบเทียบกับการทำงานแบบเดิมที่รันบนคอมพิวเตอร์ เพื่อตอบคำถามว่า
**การย้ายงานประมวลผล AI จากคอมพิวเตอร์ไปยัง FPGA คุ้มค่าตรงไหน และต้องแลกกับอะไร**

ระบบที่สร้างขึ้นรับภาพวิดีโอเข้ามา ตรวจจับพัสดุด้วยโมเดล YOLO ที่รันบนหน่วยเร่งความเร็วในตัวบอร์ด
ติดตามพัสดุแต่ละชิ้นข้ามเฟรม และนับเมื่อพัสดุเคลื่อนที่ข้ามเส้นที่กำหนดไว้ ทั้งหมดนี้ทำงานอยู่ในบอร์ดเดียว
ที่ใช้กำลังไฟฟ้าระดับไม่กี่วัตต์ โดยไม่ต้องต่อกับคอมพิวเตอร์เครื่องอื่น

**ข้อเสนอของโครงงาน:**

> ระบบเดิมที่รันบนคอมพิวเตอร์ทำงานแบบเรียลไทม์ได้ แต่ต้องแลกด้วยการใช้พลังงาน ขนาดอุปกรณ์
> และต้นทุนต่อจุดตรวจที่ขยายระบบได้ยาก โครงงานนี้เสนอบอร์ด FPGA เป็นทางเลือกที่ให้
> **ความเร็วเพียงพอต่อลักษณะงาน ภายใต้การใช้พลังงานที่ต่ำกว่ามาก**

## 2. ปัญหาที่ต้องการแก้

งานนับพัสดุบนสายพานต้องทำงานต่อเนื่องตลอดเวลาที่หน้างานจริง ไม่ใช่บนเซิร์ฟเวอร์ในห้องคอมพิวเตอร์
เมื่อพิจารณาการติดตั้งจริง วิธีเดิมที่ใช้คอมพิวเตอร์ประมวลผลมีข้อจำกัดดังนี้

| ประเด็น | ลักษณะของระบบเดิม | ผลกระทบ |
|---|---|---|
| กำลังไฟฟ้า | คอมพิวเตอร์ทั้งเครื่องใช้ไฟหลายสิบวัตต์ แม้ขณะโหลดต่ำ | ค่าไฟสะสม และต้องมีระบบระบายความร้อน |
| ขนาด | ต้องมีเครื่องคอมพิวเตอร์เต็มรูปแบบ | ติดตั้งข้างสายพานหรือบนเสากล้องได้ยาก |
| ต้นทุนต่อจุดตรวจ | ต้องมีเครื่องประมวลผลประจำแต่ละจุด | ขยายไปหลายกล้องแล้วไม่คุ้มค่า |
| ความทนทาน | ฮาร์ดแวร์สำหรับสำนักงาน | ไม่เหมาะกับฝุ่น ความร้อน และการสั่นสะเทือน |

ประเด็นสำคัญคือ **ระบบเดิมไม่ได้ทำงานไม่ได้** — มันทำงานได้ดี แต่ต้นทุนที่ต้องจ่ายเพื่อให้ได้สมรรถนะนั้น
ไม่เหมาะกับการติดตั้งใช้งานจริงหลายจุด

## 3. แนวทางที่เลือกใช้

### 3.1 ทำไมต้อง FPGA

FPGA คือชิปที่กำหนดโครงสร้างวงจรภายในได้ตามงานที่ต้องการ จึงสร้างวงจรเฉพาะทางสำหรับการคำนวณ
แบบหนึ่ง ๆ ได้ วงจรที่ออกแบบมาตรงกับงานย่อมใช้พลังงานต่อการคำนวณน้อยกว่าชิปอเนกประสงค์
อย่าง CPU หรือ GPU

ข้อจำกัดตามปกติของ FPGA คือต้องออกแบบวงจรด้วยภาษาอย่าง Verilog หรือ VHDL ซึ่งการออกแบบ
วงจรเร่งความเร็วสำหรับโครงข่าย YOLO ทั้งตัวเป็นงานขนาดใหญ่ที่เกินกรอบเวลาของโครงงานนี้

นอกจากเรื่องเวลาแล้ว ยังมีเหตุผลเชิงระเบียบวิธีที่สำคัญกว่า คือ **คำถามของโครงงานนี้คือการเปรียบเทียบ
แพลตฟอร์มในสภาพการใช้งานจริง ไม่ใช่การออกแบบวงจรเร่งความเร็วขึ้นใหม่** หากใช้วงจรที่ออกแบบเอง
ผลการเปรียบเทียบจะไม่สะท้อนสิ่งที่ผู้ใช้งานทั่วไปจะได้รับเมื่อนำแพลตฟอร์มนี้ไปใช้จริง
การใช้ชุดเครื่องมือมาตรฐานของผู้ผลิตจึงเป็นทางเลือกที่ทำให้ผลการศึกษามีความเป็นตัวแทนมากกว่า

### 3.2 DPU — ทางลัดที่ทำให้โครงงานนี้เป็นไปได้

AMD จัดเตรียม **DPU (Deep-learning Processing Unit)** มาให้ในรูปแบบวงจรสำเร็จรูปที่นำไปวาง
ในส่วน FPGA ได้เลย DPU เป็นวงจรที่ออกแบบมาเพื่อเร่งการคำนวณของโครงข่ายประสาทเทียมแบบ CNN
โดยเฉพาะ ผู้พัฒนาจึงไม่ต้องออกแบบวงจรเอง เพียงแปลงโมเดลให้อยู่ในรูปแบบที่ DPU รับได้

```
โมเดล PyTorch  →  [ ชุดเครื่องมือ Vitis AI ]  →  ไฟล์ .xmodel  →  DPU รันได้ทันที
                                                              (ไม่ต้องเขียน Verilog)
```

การใช้ทางลัดนี้มีเงื่อนไขสองข้อที่ต้องยอมรับ และเงื่อนไขทั้งสองนี้เองที่กลายเป็นโจทย์หลักของโครงงาน

| เงื่อนไข | หมายความว่า | โจทย์ที่ตามมา |
|---|---|---|
| **DPU รันได้เฉพาะ INT8** | ต้องบีบตัวเลขจากทศนิยม 32 บิต เหลือจำนวนเต็ม 8 บิต | บีบแล้วโมเดลยังแม่นอยู่หรือไม่ |
| **DPU รองรับ operation จำกัด** | operation ที่ไม่รองรับต้องไปรันบน CPU แทน | ต้องเลือกและดัดแปลงโมเดลให้เข้ากับข้อจำกัด |

### 3.3 ทำไมเลือก KV260

โครงงานนี้เลือกศึกษาบอร์ดเดียวอย่างละเอียด แทนการศึกษาหลายบอร์ดแบบผิวเผิน เนื่องจากข้อจำกัด
ด้านงบประมาณและระยะเวลา

AMD Kria KV260 ตอบโจทย์เพราะ

- เป็นชิปแบบ **MPSoC** คือมีทั้ง CPU (ARM Cortex-A53) และส่วน FPGA อยู่ในชิปเดียวกัน
  จึงรันระบบปฏิบัติการ Linux และคุมงานทั้งหมดได้ในบอร์ดเดียว ไม่ต้องมีคอมพิวเตอร์แม่ข่าย
- เป็นชุดพัฒนาสำหรับงานกล้องโดยเฉพาะ (Vision AI Starter Kit)
- มี DPU และชุดเครื่องมือ Vitis AI พร้อมใช้งาน

## 4. ระบบทำงานอย่างไร

### 4.1 ภาพรวม

บอร์ดแบ่งเป็นสองส่วนและแบ่งงานกันทำ

- **PS (Processing System)** — CPU ARM ที่รัน Linux รับผิดชอบการเตรียมข้อมูลและการประมวลผลผลลัพธ์
- **PL (Programmable Logic)** — ส่วน FPGA ที่มี DPU อยู่ข้างใน รับผิดชอบการคำนวณของโครงข่าย

```
        ภาพจากกล้องหรือไฟล์วิดีโอ
                  │
    ┌─────────────▼─────────────────────────────────────┐
    │  PS   ① เตรียมภาพ                                  │
    │       ย่อเป็น 640×640 · แปลงช่องสี · ปรับช่วงค่า      │
    │       · แปลงเป็นจำนวนเต็ม 8 บิต                      │
    └─────────────┬─────────────────────────────────────┘
                  │
    ┌─────────────▼─────────────────────────────────────┐
    │  PL   ② DPU รันโมเดล YOLO ทั้งตัว                   │
    │       ได้ผลลัพธ์ 3 ระดับความละเอียด                  │
    │       แต่ละระดับมี 65 ช่องข้อมูล                      │
    └─────────────┬─────────────────────────────────────┘
                  │
    ┌─────────────▼─────────────────────────────────────┐
    │  PS   ③ แปลงค่ากลับเป็นทศนิยม                        │
    │       ④ ถอดรหัสเป็นพิกัดกรอบ                         │
    │       ⑤ คำนวณคะแนนความมั่นใจ                        │
    │       ⑥ ตัดกรอบที่ซ้อนทับกัน                          │
    │       ⑦ ติดตามพัสดุข้ามเฟรม                          │
    │       ⑧ นับเมื่อข้ามเส้น                              │
    └─────────────┬─────────────────────────────────────┘
                  │
             จำนวนที่นับได้
```

### 4.2 แต่ละขั้นทำอะไร

**① เตรียมภาพ** — ย่อภาพให้เป็น 640 × 640 พิกเซล สลับลำดับช่องสีจาก BGR เป็น RGB
หารด้วย 255 เพื่อให้ค่าอยู่ในช่วง 0 ถึง 1 แล้วแปลงเป็นจำนวนเต็ม 8 บิตด้วยค่าสเกลที่กำหนดไว้
ตอนแปลงโมเดล

**② DPU รันโมเดล** — DPU ประมวลผลโครงข่ายทั้งหมดในครั้งเดียว ให้ผลลัพธ์ออกมา 3 ระดับ
สำหรับตรวจจับวัตถุขนาดเล็ก กลาง และใหญ่ ผลลัพธ์แต่ละระดับมี 65 ช่องข้อมูล แบ่งเป็น
**64 ช่องสำหรับตำแหน่งกรอบ และ 1 ช่องสำหรับคะแนนว่าเป็นพัสดุหรือไม่**

**③ แปลงค่ากลับ** — ผลลัพธ์จาก DPU เป็นจำนวนเต็ม ต้องคูณด้วยค่าสเกลเพื่อแปลงกลับเป็นทศนิยม

**④ ถอดรหัสเป็นพิกัดกรอบ** — ข้อมูล 64 ช่องไม่ใช่พิกัดกรอบโดยตรง แต่เป็นการกระจายความน่าจะเป็น
ของระยะทางจากจุดอ้างอิงไปยังขอบกรอบทั้งสี่ด้าน ด้านละ 16 ระดับ ระบบจึงต้องคำนวณค่าเฉลี่ยถ่วงน้ำหนัก
เพื่อให้ได้ระยะจริง แล้วคูณด้วยอัตราส่วนของแต่ละระดับ (8, 16 และ 32) เพื่อแปลงกลับเป็นพิกัดบนภาพเดิม

**⑤ คำนวณคะแนนความมั่นใจ** — แปลงค่าดิบในช่องที่ 65 ให้เป็นคะแนนในช่วง 0 ถึง 1

**⑥ ตัดกรอบที่ซ้อนทับ** — วัตถุหนึ่งชิ้นมักถูกตรวจพบหลายกรอบ ต้องคัดให้เหลือกรอบเดียวต่อวัตถุ

**⑦ ติดตามพัสดุข้ามเฟรม** — จับคู่กรอบในเฟรมปัจจุบันกับเฟรมก่อนหน้าโดยดูระยะห่างของจุดศูนย์กลาง
กรอบที่อยู่ใกล้กันที่สุดถือว่าเป็นพัสดุชิ้นเดียวกัน

**⑧ นับเมื่อข้ามเส้น** — เพิ่มจำนวนนับเมื่อพัสดุที่ติดตามอยู่เคลื่อนที่ข้ามเส้นอ้างอิงเป็นครั้งแรก
การใช้เกณฑ์การข้ามเส้น แทนการนับจำนวนกรอบที่เห็นในเฟรม ป้องกันไม่ให้พัสดุชิ้นเดียวถูกนับซ้ำหลายครั้ง

### 4.3 ทำไมต้องแบ่งงานแบบนี้

การแบ่งงานระหว่าง PS กับ PL ไม่ได้เลือกตามความสะดวก แต่เป็นผลจากข้อจำกัดจริงสองข้อ

1. **ขั้นตอนที่ 4 มีการคำนวณที่ DPU ทำไม่ได้** — การถอดรหัสตำแหน่งกรอบต้องใช้การคำนวณ
   แบบ softmax ซึ่งอยู่นอกชุด operation ที่ DPU รองรับ
2. **ถ้าปล่อยขั้นตอนถอดรหัสไว้ในโมเดล การคอมไพล์จะล้มเหลว** — จึงต้องปรับให้โมเดลส่งคืน
   ค่าดิบออกมาก่อน แล้วไปถอดรหัสเองบน CPU

## 5. การนำโมเดลลงบอร์ด

```
โมเดล YOLO มาตรฐาน (.pt)
        │
        │ ขั้นที่ 1  เปลี่ยน activation จาก SiLU เป็น LeakyReLU แล้วฝึกซ้ำ
        ▼
โมเดลที่ DPU รองรับ (.pt)
        │
        │ ขั้นที่ 2  แปลงเป็น INT8 ด้วย vai_q_pytorch โดยใช้ภาพสอบเทียบจากงานจริง
        ▼
โมเดล INT8
        │
        │ ขั้นที่ 3  คอมไพล์ด้วย vai_c_xir ให้ตรงกับ DPU รุ่นบนบอร์ด
        ▼
   ไฟล์ .xmodel  ──►  โหลดด้วยไลบรารี VART บนบอร์ด
```

### 5.1 ขั้นที่ 1 — เปลี่ยน activation

YOLO มาตรฐานใช้ activation ชื่อ **SiLU** ซึ่งต้องคำนวณ exponential — DPU ทำไม่ได้
จึงต้องเปลี่ยนเป็น **LeakyReLU ที่ค่าความชัน 0.1015625** ค่านี้ไม่ได้เลือกมาลอย ๆ แต่เป็นค่าที่
แทนได้พอดีในระบบเลขทศนิยมตำแหน่งตายตัวของ DPU

**การเปลี่ยนเฉย ๆ ไม่พอ** เพราะน้ำหนักที่ฝึกมากับ SiLU ไม่เข้ากับ activation ใหม่ ทำให้ความแม่นยำตกทันที
จึงต้องฝึกโมเดลซ้ำหลังเปลี่ยน ซึ่งพบว่าความแม่นยำกลับมาอยู่ในระดับเดิมได้

> ข้อสังเกต: ข้อจำกัดเรื่อง activation ของ DPU เป็น **ต้นทุนด้านเวลาฝึกโมเดล ไม่ใช่ต้นทุนด้านความแม่นยำ**

### 5.2 ขั้นที่ 2 — สอบเทียบก่อนแปลงเป็น INT8

การแปลงเป็น INT8 ต้องรู้ก่อนว่าค่าที่ไหลผ่านแต่ละชั้นของโครงข่ายอยู่ในช่วงไหน เพื่อคำนวณค่าสเกล
ที่เหมาะสม วิธีรู้คือป้อนภาพตัวอย่างเข้าไปแล้วเก็บสถิติ ภาพชุดนี้เรียกว่า **calibration set**

หากใช้ภาพทั่วไปที่หน้าตาไม่เหมือนงานจริง ค่าสเกลที่ได้จะไม่พอดีกับข้อมูลที่ระบบจะเจอตอนใช้งาน
ทำให้ความแม่นยำตกโดยไม่จำเป็น โครงงานนี้จึงใช้ภาพจากสายพานจริงเป็น calibration set

### 5.3 ขั้นที่ 3 — เกณฑ์ตัดสินว่าคอมไพล์สำเร็จ

เมื่อคอมไพเลอร์เจอ operation ที่ DPU ทำไม่ได้ มันจะ **ตัดโมเดลตรงนั้น** แล้วส่งส่วนนั้นไปรันบน CPU แทน
การถูกตัดทำให้ต้องคัดลอกข้อมูลระหว่าง DPU กับหน่วยความจำหลักหลายรอบ ซึ่งกระทบสมรรถนะอย่างมาก

```
กรณีที่ต้องการ      ภาพเข้า → [ ═══ DPU ทั้งหมด ═══ ] → ผลลัพธ์

กรณีที่ไม่ต้องการ    ภาพเข้า → [ DPU ] → [ CPU ] → [ DPU ] → [ CPU ] → [ DPU ] → ผลลัพธ์
                                      ↑ ต้องย้ายข้อมูลไปกลับทุกรอยตัด
```

โครงงานนี้จึงตั้งเกณฑ์ไว้ตั้งแต่เริ่มงานและไม่แก้ระหว่างทางว่า

> **เกณฑ์ที่ใช้ตัดสินคือ log จากคอมไพเลอร์ `vai_c_xir` ที่ระบุว่าได้ `DPU subgraph number 1`
> ไม่ใช่ผลจากเครื่องมือวิเคราะห์เชิงคาดการณ์**

เหตุผลคือเครื่องมือวิเคราะห์เชิงคาดการณ์ (Inspector) ดูเพียงรายชื่อ operation ในขณะที่คอมไพเลอร์
พิจารณาปัจจัยที่เครื่องมือนั้นไม่รู้ เช่น ขนาดข้อมูลเทียบกับหน่วยความจำของ DPU รูปแบบการเชื่อมต่อ
ระหว่างชั้น และข้อจำกัดเฉพาะของ DPU รุ่นนั้น

**ผลที่ได้:** โมเดลที่ใช้คอมไพล์ผ่านเป็น **1 subgraph** บน DPU รุ่น DPUCZDX8G_ISA1_B4096
และมีรหัสระบุรุ่นตรงกับ DPU บนบอร์ดจริง

## 6. ปัญหาที่ต้องแก้ระหว่างทาง และวิธีแก้

| ปัญหา | สาเหตุ | วิธีแก้ | ผลที่ได้ |
|---|---|---|---|
| DPU ไม่รองรับ SiLU | ต้องคำนวณ exponential | เปลี่ยนเป็น LeakyReLU(0.1015625) แล้วฝึกซ้ำ | โมเดลรันบน DPU ได้ โดยความแม่นยำไม่ตก |
| คอมไพล์ล้มที่หัวโมเดล | ขั้นตอนถอดรหัสมี operation ที่ DPU ไม่รองรับ | ตัดขั้นตอนถอดรหัสออกจากโมเดล ให้ส่งค่าดิบออกมาแทน | คอมไพล์ผ่านเป็น 1 subgraph |
| โมเดลมาตรฐานมี 80 ประเภทวัตถุ แต่งานนี้ต้องการแค่พัสดุ | ชั้นผลลัพธ์ใหญ่เกินจำเป็น | ฝึกโมเดลใหม่ให้เหลือประเภทเดียว | ชั้นผลลัพธ์ลดจาก 144 เหลือ 65 ช่อง และประมวลผลได้เร็วขึ้น |
| ความแม่นยำตกหลังแปลง INT8 มากกว่าที่ควร | ใช้ภาพสอบเทียบผิดโดเมน | เปลี่ยนมาใช้ภาพจากสายพานจริง | ค่าสเกลตรงกับข้อมูลใช้งานจริงมากขึ้น |

การที่ความเร็วเพิ่มขึ้นจากการลดจำนวนประเภทวัตถุ เป็นหลักฐานที่วัดได้ว่า **ชั้นผลลัพธ์ของโมเดล
มีต้นทุนด้านเวลาจริง** ไม่ใช่เพียงข้อสังเกตทางทฤษฎี

## 7. ข้อมูลที่ใช้

โครงงานนี้ใช้ข้อมูล **2 ชุด ซึ่งทำหน้าที่ต่างกันโดยตั้งใจ**

### 7.1 ชุดที่ 1 — ข้อมูลมาตรฐานสำหรับเปรียบเทียบกับงานวิจัยอื่น

ใช้ชุดข้อมูล **COCO** ซึ่งเป็นชุดข้อมูลมาตรฐานที่งานวิจัยด้านการตรวจจับวัตถุใช้กันแพร่หลาย
ร่วมกับโมเดล YOLO รุ่นมาตรฐานที่มีการรายงานผลไว้ในงานวิจัยอื่น

**เหตุผล:** เพื่อให้ตัวเลขที่วัดได้จากโครงงานนี้ **เทียบเคียงกับผลของงานวิจัยอื่นได้**
หากใช้เฉพาะข้อมูลของตนเอง จะไม่มีจุดอ้างอิงว่าผลที่ได้อยู่ในระดับใดเมื่อเทียบกับงานที่มีอยู่แล้ว

### 7.2 ชุดที่ 2 — ข้อมูลของงานจริงที่โครงงานนี้ออกแบบขึ้น

ชุดข้อมูลภาพพัสดุบนสายพานลำเลียง สำหรับตรวจจับวัตถุประเภทเดียว

| รายการ | จำนวน |
|---|---|
| ภาพสำหรับฝึกโมเดล | 208 ภาพ |
| ภาพสำหรับตรวจสอบความแม่นยำ | 57 ภาพ (มีพัสดุรวม 289 ชิ้น) |
| ภาพสำหรับทดสอบ | 28 ภาพ |
| ภาพสำหรับสอบเทียบตอนแปลงเป็น INT8 | 208 ภาพ (คัดจากชุดฝึก) |

ชุดสอบเทียบใช้ภาพจากงานจริงตามเหตุผลในหัวข้อ 5.2 คือค่าสเกลของ INT8 ต้องคำนวณจากข้อมูล
ที่มีลักษณะเดียวกับที่ระบบจะพบตอนใช้งานจริง

### 7.3 วิดีโอสำหรับวัดความถูกต้องของการนับ

การวัดความแม่นยำจากภาพนิ่งบอกได้แค่ว่าโมเดลตรวจจับดีแค่ไหน แต่ไม่ได้บอกว่า **นับถูกหรือไม่**
จึงต้องมีวิดีโอที่มีค่าอ้างอิงจากการนับด้วยมือ

| รายการ | ต้นฉบับ | คลิปที่ใช้จริง |
|---|---|---|
| ความยาว | 12 ชั่วโมง | 600 วินาที (10 นาที) |
| จำนวนเฟรม | ประมาณ 1.3 ล้านเฟรม | 18,001 เฟรม |
| ความละเอียด | 640 × 360 พิกเซล ที่ 30 เฟรมต่อวินาที | เท่าเดิม |
| ค่าอ้างอิง | — | **215 ชิ้น (นับด้วยมือ)** |

**เหตุผลที่ต้องตัดคลิป:** วิดีโอ 12 ชั่วโมงยาวเกินกว่าจะนับด้วยมือให้ครบได้ ความยาว 10 นาที
เป็นจุดสมดุลระหว่าง "ยาวพอที่ผลจะมีความหมาย" กับ "สั้นพอที่จะนับด้วยมือได้จริง"
โดยตัดด้วยวิธีคัดลอกสตรีมโดยไม่เข้ารหัสใหม่ เพื่อไม่ให้คุณภาพของภาพเปลี่ยนไปจากต้นฉบับ

ความหนาแน่นของเหตุการณ์คือมีพัสดุผ่านประมาณ 1 ชิ้นทุก 2.8 วินาที ซึ่งอยู่ในระดับที่สมจริง
สำหรับสายพานลำเลียง

## 8. งานที่ใช้พิสูจน์ระบบ

การแสดงว่าระบบ "ตรวจจับพัสดุได้" ยังไม่พอ เพราะโมเดลอาจตรวจจับแม่นยำ แต่หากการติดตาม
ข้ามเฟรมผิดพลาด พัสดุชิ้นเดียวจะถูกนับสองครั้ง **งานเป้าหมายของโครงงานจึงเป็นการนับ ไม่ใช่การตรวจจับ**

การพิสูจน์ทำโดยใช้วิดีโอจากสายพานจริงที่**นับด้วยมือ**ไว้เป็นค่าอ้างอิง แล้วเทียบกับจำนวนที่ระบบนับได้

ระบบออกแบบให้มีสองโหมดการทำงานที่แยกกันโดยตั้งใจ

| โหมด | ทำอะไร | ใช้เมื่อไร |
|---|---|---|
| **โหมดใช้งานจริง** | ตรวจจับ ติดตาม นับ แล้วส่งออกเฉพาะตัวเลข | ใช้วัดสมรรถนะทุกรายการ |
| **โหมดตรวจสอบและสาธิต** | บันทึกผลตรวจจับรายเฟรมเป็นไฟล์ แล้วนำไปสร้างวิดีโอแสดงผลบนคอมพิวเตอร์ | ใช้ตรวจความถูกต้องและนำเสนอ |

เหตุผลที่ต้องแยก คือ **การวาดกรอบและเข้ารหัสวิดีโอไม่ใช่ส่วนหนึ่งของระบบที่ใช้งานจริง**
ระบบนับที่หน้างานส่งออกแค่ตัวเลข ถ้านำเวลาที่ใช้วาดวิดีโอไปรวมในการวัดความเร็ว
ผลที่ได้จะไม่ตรงกับสภาพการใช้งานจริง

## 9. จะพิสูจน์ว่าคุ้มค่าอย่างไร

### 9.1 ระบบที่นำมาเปรียบเทียบ

การประเมินทำโดยให้ระบบ 4 แบบรันงานเดียวกันภายใต้เงื่อนไขเดียวกัน

| ระบบ | บทบาท |
|---|---|
| **AMD Kria KV260** | แนวทางที่โครงงานนี้เสนอ |
| **NVIDIA Jetson Nano** | อุปกรณ์ประมวลผลที่หน้างานเหมือนกัน แต่ใช้สถาปัตยกรรมต่างกัน (GPU ฝังตัว) |
| **คอมพิวเตอร์ + GPU แยก** | ระบบเดิมแบบที่มีการ์ดจอ |
| **คอมพิวเตอร์ CPU อย่างเดียว** | ระบบเดิมแบบที่ไม่มีการ์ดจอ ซึ่งพบบ่อยที่หน้างาน |

### 9.2 ไปป์ไลน์ของระบบที่นำมาเปรียบเทียบ

ทุกระบบต้องทำงาน **ขั้นตอนเดียวกันทั้งหมด** ตั้งแต่รับเฟรมจนถึงได้จำนวนนับ ตามที่อธิบายไว้ในหัวข้อ 4
สิ่งที่ต่างกันมีเพียงสองอย่าง คือ **ตัวประมวลผลที่รันโมเดล** และ **เส้นทางแปลงโมเดลของแต่ละแพลตฟอร์ม**

```
        ทุกระบบใช้โครงสร้างเดียวกัน
        ┌────────────────────────────────────────────────────────┐
        │  เตรียมภาพ  →  [ รันโมเดล ]  →  ถอดรหัสกรอบ            │
        │                     ▲            → คัดกรอบซ้อนทับ       │
        │                     │            → ติดตาม → นับ         │
        └─────────────────────┼──────────────────────────────────┘
                              │
                  ส่วนเดียวที่ต่างกันตามแพลตฟอร์ม
```

| ระบบ | ตัวที่รันโมเดล | เส้นทางแปลงโมเดล | ความละเอียดตัวเลข |
|---|---|---|---|
| KV260 | DPU ในส่วน FPGA | PyTorch → Vitis AI (`vai_q_pytorch` → `vai_c_xir`) → `.xmodel` → VART | INT8 |
| Jetson Nano | GPU ฝังตัว | PyTorch → ONNX → TensorRT | FP16 / FP32 |
| คอม + GPU | การ์ดจอแยก | PyTorch → ONNX → TensorRT | FP32 / FP16 / INT8 |
| คอม CPU | CPU | PyTorch → ONNX → OpenVINO หรือ ONNX Runtime | FP32 / INT8 |

**หลักการสำคัญ 3 ข้อที่ทำให้การเปรียบเทียบยุติธรรม**

**หนึ่ง — ใช้โมเดลชุดเดียวกันทุกระบบ** ทุกแพลตฟอร์มรันโมเดลที่ผ่านการฝึกมาจากไฟล์เดียวกัน
โดยส่งออกเป็นไฟล์กลาง (ONNX) หนึ่งครั้ง แล้วให้แต่ละแพลตฟอร์มแปลงจากไฟล์เดียวกันนั้น
การทำเช่นนี้ทำให้ **ความแตกต่างที่วัดได้มาจากฮาร์ดแวร์และความละเอียดตัวเลขเท่านั้น**
ไม่ได้มาจากการที่แต่ละระบบใช้โมเดลคนละตัว

**สอง — ใช้โค้ดประมวลผลผลลัพธ์ชุดเดียวกัน** ขั้นตอนถอดรหัสกรอบ คัดกรอบซ้อนทับ ติดตาม และนับ
ใช้โค้ดเดียวกันทุกระบบ หากแต่ละระบบใช้วิธีคัดกรอบหรือวิธีติดตามคนละแบบ ผลที่ต่างกันจะไม่สามารถ
สรุปได้ว่ามาจากฮาร์ดแวร์หรือมาจากซอฟต์แวร์

**สาม — ให้แต่ละแพลตฟอร์มใช้เครื่องมือที่ดีที่สุดของตนเอง** ฝั่ง NVIDIA ใช้ TensorRT
ฝั่ง Intel ใช้ OpenVINO ฝั่ง AMD ใช้ Vitis AI ไม่ใช้ PyTorch ธรรมดารันทุกระบบ
เพราะจะทำให้ระบบที่มีเครื่องมือปรับแต่งเฉพาะทางเสียเปรียบโดยไม่จำเป็น
และผลที่ได้จะไม่สะท้อนสมรรถนะที่แท้จริงของแพลตฟอร์มนั้น

> **ข้อสังเกตที่ต้องรายงานตามจริง:** ขั้นตอนหลังการรันโมเดลทำงานบน CPU ของแต่ละระบบ
> ซึ่ง CPU ของคอมพิวเตอร์เร็วกว่า CPU บนบอร์ดฝังตัวอย่างมีนัยสำคัญ ผลการวัดแบบครบวงจร
> จึงสะท้อนสมรรถนะของทั้งระบบ ไม่ใช่ของตัวเร่งความเร็วเพียงอย่างเดียว
> ด้วยเหตุนี้โครงงานจึงรายงานผล **สองระดับเสมอ** คือระดับตัวเร่งความเร็วอย่างเดียว
> และระดับทั้งระบบ เพื่อให้เห็นว่าความแตกต่างมาจากส่วนใด

### 9.3 สิ่งที่วัดและหลักการเปรียบเทียบ

**สิ่งที่วัด** มี 4 มิติ ได้แก่ ความแม่นยำในการตรวจจับ ความเร็วในการประมวลผล กำลังไฟฟ้าที่ใช้
และความถูกต้องของการนับเทียบกับค่าอ้างอิง

**หลักการเปรียบเทียบ** — เปรียบเทียบที่ **ความเร็วเท่ากัน แล้วดูว่าระบบใดใช้ไฟน้อยกว่า**
เนื่องจากข้อเสนอของโครงงานไม่ใช่การอ้างว่า FPGA ประมวลผลได้เร็วกว่า (โดยทั่วไป GPU ให้ความเร็วดิบสูงกว่า)
แต่คือการเสนอว่า FPGA ให้ความเร็วที่เพียงพอต่องานนี้ ภายใต้การใช้ไฟที่ต่ำกว่ามาก

**นิยามของคำว่า "เพียงพอ"** — โครงงานนี้ไม่ได้นิยามความเป็นเรียลไทม์จากอัตราเฟรมของวิดีโอต้นทาง
แต่นิยามจาก **อัตราการเกิดเหตุการณ์ในงานจริง** กล่าวคือ ระบบต้องประมวลผลได้เร็วพอที่จะไม่พลาด
พัสดุที่เคลื่อนผ่าน หากพัสดุผ่านทุก 2.8 วินาที ระบบไม่จำเป็นต้องประมวลผลครบทุกเฟรมที่กล้องส่งมา
เกณฑ์นี้จึงเป็นข้อกำหนดที่มาจากลักษณะงาน ไม่ใช่จากคุณสมบัติของอุปกรณ์รับภาพ

โครงงานได้จัดทำเอกสารกำหนดวิธีการวัดไว้ต่างหาก ครอบคลุมเรื่องขอบเขตการวัดพลังงาน
ความแตกต่างด้านความละเอียดตัวเลขที่แต่ละแพลตฟอร์มรองรับ การเลือกเครื่องมือวัด และจำนวนรอบการทดลอง
เพื่อให้การเปรียบเทียบยุติธรรมและทำซ้ำได้

## 10. การสาธิตระบบ

นอกจากผลการทดลองที่เป็นตัวเลขแล้ว โครงงานจะจัดทำการสาธิตเพื่อให้เห็นการทำงานของระบบ
ในสถานการณ์ที่ใกล้เคียงการใช้งานจริง

**รูปแบบการสาธิต** — ป้อนไฟล์วิดีโอเข้าสู่บอร์ดเพื่อจำลองภาพที่ส่งมาจากกล้องวงจรปิดที่ติดตั้ง
เหนือสายพานลำเลียง โดยบอร์ดทำงานทั้งหมดด้วยตัวเอง ไม่ต้องต่อกับคอมพิวเตอร์เครื่องอื่น

**สิ่งที่ผู้ชมจะเห็น**

- กรอบที่ระบบตรวจจับพัสดุแต่ละชิ้นได้
- เส้นอ้างอิงที่ใช้เป็นเกณฑ์การนับ
- หมายเลขกำกับพัสดุแต่ละชิ้นที่ระบบติดตามอยู่ ซึ่งแสดงให้เห็นว่าระบบแยกแยะพัสดุแต่ละชิ้นได้จริง
- จำนวนนับสะสมที่เพิ่มขึ้นเมื่อมีพัสดุข้ามเส้น

**ข้อพิจารณาด้านเทคนิค** — ตามที่อธิบายไว้ในหัวข้อ 8 การวาดกรอบและแสดงผลเป็นวิดีโอ
อยู่ในโหมดตรวจสอบและสาธิต ซึ่งแยกออกจากโหมดใช้งานจริงที่ใช้วัดสมรรถนะ ภาพที่ผู้ชมเห็น
จึงเป็นการแสดงผลเพื่อการสื่อสาร ไม่ใช่ภาระงานที่ระบบต้องแบกในการใช้งานจริง

**สถานะ** — กำหนดแนวทางไว้แล้ว อยู่ระหว่างพัฒนารายละเอียด โดยจะดำเนินการหลังจาก
ผลการทดลองเชิงเปรียบเทียบเสร็จสมบูรณ์

## 11. YOLO26 — โมเดลที่ศึกษาแล้วพบว่าใช้ไม่ได้ และเหตุผลที่เรื่องนี้มีค่า

เดิมโครงงานตั้งใจใช้ **YOLO26** ซึ่งเป็นโมเดลตรวจจับวัตถุรุ่นใหม่กว่า แต่จากการวิเคราะห์โครงสร้าง
ของโมเดลพบว่า **ไม่สามารถรันบน DPU รุ่นนี้ได้ทั้งตัว** โดยติดที่จุดที่ไม่ตรงกับที่คาดไว้

**สิ่งที่คาดว่าจะเป็นปัญหาแต่ไม่ใช่:** โครงสร้างส่วนหัวแบบ NMS-free ของ YOLO26 ซึ่งแก้ได้ด้วย
การตั้งค่าตัวเลือกเดียวตอนแปลงโมเดล

**ตัวที่เป็นปัญหาจริง:** บล็อก **attention** จำนวน 2 จุดที่อยู่ตรงกลางโมเดล (ประมาณตำแหน่ง 32%
และ 69% ของโครงสร้าง) ซึ่งใช้ลำดับการคำนวณแบบ `MatMul → Softmax → MatMul`

**สาเหตุที่ DPU ทำไม่ได้ มีสองข้อที่เป็นอิสระจากกัน**

1. DPU ออกแบบบนสมมติฐานว่า **ตัวคูณฝั่งหนึ่งเป็นน้ำหนักคงที่** ที่โหลดไว้ล่วงหน้าได้
   แต่ attention คูณข้อมูลสองก้อนที่เปลี่ยนไปทุกครั้งที่ประมวลผล
2. Softmax ต้องใช้การคำนวณ exponential ซึ่งเป็นเหตุผลเดียวกับที่ DPU ทำ SiLU ไม่ได้

**ข้อค้นพบที่สำคัญที่สุดจากเรื่องนี้:**

```
operation ที่ DPU ไม่รองรับ ถ้าอยู่ปลายโมเดล  → ไม่ตัดโมเดล ยังเป็น 1 subgraph
operation เดียวกัน ถ้าอยู่กลางโมเดล           → ตัดโมเดลเป็นหลายชิ้น สมรรถนะพัง
```

> **ความรุนแรงของปัญหาขึ้นอยู่กับตำแหน่งของ operation ในโมเดล ไม่ใช่แค่ชนิดของ operation**
> ซึ่งเป็นข้อมูลที่การดูรายชื่อ operation เพียงอย่างเดียวไม่บอก

ข้อค้นพบนี้ไม่ได้จำกัดอยู่ที่ YOLO26 เท่านั้น แต่ครอบคลุม **โมเดลตรวจจับวัตถุกลุ่มที่ใช้ attention ทั้งกลุ่ม**
ซึ่งเป็นทิศทางที่วงการกำลังพัฒนาไป ในขณะที่ DPU รุ่นที่ใช้ออกแบบมาสำหรับโครงข่ายแบบ CNN ล้วน
เรื่องนี้จึงถูกใช้เป็นเหตุผลประกอบการเลือกโมเดลที่นำมาใช้จริงในโครงงาน

## 12. ขอบเขตและข้อจำกัด

**ขอบเขตที่กำหนดไว้**

- ศึกษาบอร์ด FPGA เพียงรุ่นเดียวอย่างละเอียด ตามข้อจำกัดด้านงบประมาณและเวลา
- มุ่งที่การรันโมเดล ไม่ครอบคลุมการออกแบบและฝึกโมเดลจากศูนย์
- ตรวจจับวัตถุประเภทเดียวตามลักษณะงานเป้าหมาย
- ทดสอบภายใต้สภาพแวดล้อมที่ควบคุม ได้แก่ แสง มุมกล้อง และความเร็วสายพานที่คงที่

**ข้อจำกัดของแพลตฟอร์มที่พบและจะรายงานตามจริง**

โครงงานนี้ไม่ได้มีเป้าหมายเพื่อแสดงว่า FPGA ดีกว่าในทุกด้าน ผลที่ชี้ให้เห็นข้อจำกัดของแพลตฟอร์ม
ถือเป็นผลการศึกษาที่มีคุณค่าเช่นกัน โดยเฉพาะประเด็นการกระจายภาระงานระหว่าง CPU กับ DPU
ภายในบอร์ดเดียวกัน ซึ่งเป็นลักษณะเฉพาะของชิปที่รวมหน่วยประมวลผลหลายแบบไว้ด้วยกัน

## 13. สถานะปัจจุบันและงานในอนาคต

**สถานะปัจจุบัน** — ระบบทำงานได้ครบวงจรบนบอร์ดจริงแล้ว ตั้งแต่รับวิดีโอจนถึงรายงานผลการนับ
โมเดลผ่านเกณฑ์การคอมไพล์ที่ตั้งไว้ และเครื่องมือสำหรับวัดผลทั้ง 4 มิติจัดทำไว้ครบแล้ว
ขั้นตอนที่กำลังดำเนินการคือการกำหนดวิธีวัดเชิงเปรียบเทียบให้รัดกุม และเก็บข้อมูลผลการทดลองตามวิธีนั้น

**งานในอนาคต**

- **ปรับปรุงส่วนที่เป็นคอขวดของระบบ** ซึ่งระบุตำแหน่งได้แล้วจากการวิเคราะห์สมรรถนะ
- **ขยายการศึกษาไปยังบอร์ด Efinix Ti375** ซึ่งใช้สถาปัตยกรรมและชุดเครื่องมือคนละแบบกับ AMD
  (ใช้ soft RISC-V processor และ TensorFlow Lite แทน DPU และ Vitis AI) เพื่อตรวจสอบว่า
  ข้อสรุปที่ได้จากโครงงานนี้ผูกกับแพลตฟอร์มเฉพาะ หรือเป็นลักษณะทั่วไปของอุปกรณ์ประมวลผลที่หน้างาน
  — งานส่วนนี้เริ่มศึกษาไว้บางส่วนแล้ว และพบว่าไปป์ไลน์ที่พัฒนาขึ้นสำหรับ KV260
  ไม่สามารถย้ายไปใช้กับบอร์ดอื่นได้โดยตรง ซึ่งเป็นประเด็นที่น่าศึกษาต่อในตัวมันเอง
- **ขยายการทดสอบไปยังสภาพแวดล้อมที่หลากหลายขึ้น** เพื่อตรวจสอบความทนทานของระบบ
