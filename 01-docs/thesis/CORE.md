## 0. Thesis statement (ย่อหน้าเดียว)

โครงงานนี้ deploy โมเดลตรวจจับวัตถุตระกูล YOLO ลงบน **AMD Kria KV260** (Zynq UltraScale+ MPSoC,
DPUCZDX8G_ISA1_B4096) ด้วย Vitis AI 3.0 แล้วต่อยอดเป็น **ระบบนับพัสดุบนสายพานจากวิดีโอ**
โดยวัดผลเชิงประจักษ์ครบ 4 มิติ (ความแม่นยำ / ความหน่วง / พลังงาน / ความถูกต้องของการนับ)
เทียบกับ GPU baseline ที่วัดเองด้วยเงื่อนไขเดียวกัน ผลหลักคือระบบนับได้ **215/215 กล่อง (error 0.0%)**
บนคลิป 10 นาที โดยจ่ายค่าความแม่นยำจาก INT8 quantization เพียง **1.5% mAP** และใช้พลังงาน

**YOLO26n map ลง DPU รุ่นนี้ไม่ได้ทั้งตัวเพราะ attention block 2 จุดกลางกราฟ ไม่ใช่เพราะ NMS-free head
อย่างที่คาดกันทั่วไป** ซึ่งเป็นองค์ความรู้ที่ยังไม่มีรายงานสาธารณะ

## 1. โจทย์และเหตุผล

**สถานการณ์:** งานนับวัตถุบนสายพาน (พัสดุ) ต้องรันต่อเนื่อง 24 ชม. ที่หน้างาน ไม่ใช่บนเซิร์ฟเวอร์

**ทำไม GPU ไม่ตอบโจทย์ที่ edge:**

| ประเด็น | GPU (คลาส laptop/desktop) | ข้อจำกัดที่หน้างาน |
|---|---|---|
| กำลังไฟ | 20–60 W ต่อโหนด | ต้องมีระบบไฟ/ระบายความร้อน |
| ขนาด/ความทนทาน | การ์ด + เครื่องโฮสต์ | ติดตั้งข้างสายพานลำบาก |
| ต้นทุนต่อจุดตรวจ | สูงเมื่อขยายหลายสายพาน | สเกลไม่คุ้ม |

**ทำไม FPGA เป็นไปได้จริงในกรอบเวลาของโครงงาน:** AMD ให้ **DPU** (soft IP สำหรับ CNN) มาสำเร็จรูป
— ไม่ต้องเขียน RTL เอง แต่ **ต้องแลกด้วยข้อจำกัดว่า DPU รองรับ operation จำกัด และรันได้เฉพาะ INT8**
ข้อแลกเปลี่ยนนี้เองคือที่มาของคำถามวิจัยทั้งหมด

## 3. ขอบเขตและกติกาตัดสิน

**กติกาหลักที่ตั้งไว้ตั้งแต่ต้นและไม่แก้ระหว่างทาง:**

> **"gate เดียวที่นับคือ log ของ `vai_c_xir` ที่ระบุ `DPU subgraph number 1`
> ไม่ใช่ op histogram ไม่ใช่ผลจาก Inspector"**

เหตุผล: Inspector เป็นแค่ advisory (วิเคราะห์รายชื่อ op ไม่จำลอง compiler จริง) ส่วน compiler รู้เรื่องที่
Inspector ไม่รู้ — ขนาด tensor เทียบ memory ของ DPU, pattern การเชื่อม layer, ข้อจำกัดเฉพาะ arch
การมี subgraph เดียวหมายถึงข้อมูลเข้า-ออก DPU ครั้งเดียว ถ้าถูกตัดเป็นหลายชิ้น ต้องคัดลอก feature map
กลับ RAM แล้วส่งกลับใหม่ทุกรอยตัด และ op ที่ตกไป CPU (เช่น Softmax บน tensor ใหญ่) ช้ามากบน ARM

**กติกาย่อยที่ตั้งเพิ่มหลังเจอบทเรียนจริง:**

| กติกา | ที่มา |
|---|---|
| verify artifact จริง ไม่เชื่อ log | สคริปต์รายงานสำเร็จเพราะ `set +e` ทั้งที่ไม่มีไฟล์ออก |
| ตรวจ identity จาก channel count ไม่ใช่ชื่อไฟล์ | เจอไฟล์ชื่อ `yolo26n_*.xmodel` ที่ข้างในเป็น YOLOv8n |
| verify md5 หลังโอนไฟล์ทุกครั้ง | กันไฟล์เพี้ยนแบบเงียบ |
| "ติดตั้งสำเร็จ ≠ ได้ของที่ต้องการ" | `pip install torch` ผ่าน แต่ได้ CPU build |

**สิ่งที่อยู่นอกขอบเขต:** การออกแบบ custom accelerator ใน PL (optional, ไม่ผูกเป็นเงื่อนไขจบ) ·
การเทรนโมเดลจากศูนย์ · การรองรับหลายคลาส

## 4. ระบบที่สร้าง

### 4.1 Dataflow

```
วิดีโอ/ภาพ ─► [PS] preprocess: resize 640x640, BGR→RGB, /255, quantize→int8
           ─► [PL] DPU B4096 : YOLOv8n INT8 ทั้งตัว (1 subgraph)  ─► 3 หัว x [H,W,65]
           ─► [PS] dequantize → DFL decode → sigmoid → NMS       ─► กล่อง+score
           ─► [PS] centroid tracker (greedy) → line-crossing counter ─► จำนวนนับ
```

การแบ่งงาน PS/PL ไม่ใช่การเลือกตามใจ แต่เป็นผลของกติกา 1-subgraph: **ต้องตัด decode ออกจากกราฟ**
ให้ DPU รับผิดชอบเฉพาะส่วน convolution ล้วน มิฉะนั้น op ปลายกราฟจะทำให้ compile ล้ม
(`XIR don't support multi-outputs op`)

### 4.2 ฮาร์ดแวร์และ runtime

| รายการ | ค่า |
|---|---|
| บอร์ด | AMD Kria KV260 Vision AI Starter Kit (Zynq UltraScale+ MPSoC) |
| PS | ARM Cortex-A53 quad-core |
| PL accelerator | **DPUCZDX8G_ISA1_B4096** (4096 op/cycle) |
| Fingerprint | `0x101000056010407` (ตรงกับที่ compile ไว้ก่อนบอร์ดมาถึง) |
| OS / runtime | PetaLinux starter-kit 2022.2 / VART 3.0 |
| GPU baseline | NVIDIA GTX 1660 Ti Max-Q, FP32 |

### 4.3 Toolchain

```
PyTorch (.pt)  --vai_q_pytorch-->  INT8 quantized  --vai_c_xir-->  .xmodel (B4096)  --> VART บนบอร์ด
   ^                                    ^
   |                                    +-- calibration 208 ภาพจากโดเมนจริง
   +-- fine-tune หลังสลับ SiLU → LeakyReLU(0.1015625)
```

### 4.4 โมเดลและข้อมูล

| รายการ | ค่า |
|---|---|
| โมเดล | YOLOv8n, 1 คลาส (`package`), activation LeakyReLU(0.1015625) |
| Dataset | Roboflow `package-conveyo v2` — train 208 / valid 57 (289 กล่อง GT) / test 28 |
| Calibration | 208 ภาพจาก train (โดเมนจริง ไม่ใช่ COCO) |
| วิดีโอทดสอบนับ | `clip_600s_gt215.mp4` — 600 วิ, 18,001 เฟรม, 640x360@30fps, **GT = 215 กล่อง (นับมือ)** |
| ขนาดโมเดล | float 6.30 MB → **INT8 xmodel 3.99 MB** (1.6x) |
| Workload | **8.10 GOP/ภาพ** → ที่ 82.5 FPS ≈ 668 GOPS |
| Output head | 3 สเกล x [H,W,**65**] = 4x16 (DFL) + 1 (class) |

## 5. การตัดสินใจเชิงออกแบบ 3 ข้อที่มีผลต่อผลลัพธ์ (และเหตุผลที่วัดได้)

### 5.1 SiLU → LeakyReLU + fine-tune (ไม่ใช่แค่สลับ)

DPU ไม่รองรับ SiLU (ต้องคำนวณ exponential) จึงต้องสลับเป็น LeakyReLU ที่ค่าชัน **0.1015625**
(ค่าที่แทนได้พอดีใน fixed-point ของ DPU) — แต่การสลับเฉย ๆ ทำให้ความแม่นยำพัง เพราะ weight
ที่เทรนมากับ SiLU ไม่เข้ากับ activation ใหม่ จึงต้อง fine-tune ใหม่

| โมเดล | mAP@0.5 หลัง fine-tune (Colab T4, 400 epochs) |
|---|---|
| yolov8n + LeakyReLU | **0.884** |
| yolo26n + LeakyReLU | 0.831 |

> **ข้อค้นพบเชิงวิธีการ:** activation swap **ไม่ทำให้ accuracy ตก ถ้าเทรนพอ** —
> ข้อจำกัดของ DPU เรื่อง activation จึงเป็นต้นทุนเวลาเทรน ไม่ใช่ต้นทุนความแม่นยำ

### 5.2 ลดเหลือ 1 คลาส

| ผล | ค่า |
|---|---|
| output channel | 144 → **65** (ลด 55%) |
| throughput | 68 → **82.5 FPS** (+21%) |

> เป็นหลักฐานวัดได้ว่า **output layer มีต้นทุน runtime จริง** ไม่ใช่แค่ทฤษฎี

### 5.3 calibration set ต้องมาจากโดเมนจริง

calibration คือการเก็บสถิติช่วงค่าที่ไหลผ่านแต่ละ layer เพื่อคำนวณ scale ของ INT8
ถ้าใช้ภาพ COCO จะได้สถิติของ "ภาพทั่วไป" ซึ่งไม่ตรงกับฉากสายพาน (แสงคงที่ วัตถุคล้ายกัน)
→ scale ไม่พอดี → ความแม่นยำตกโดยไม่จำเป็น จึงเปลี่ยนไปใช้ 208 ภาพจาก train set

## 7. Track B — YOLO26n: ผลวิเคราะห์ (สถานะ: ยังไม่ compile จริง)

**เครื่องมือที่ควรใช้ (nndct Inspector) ใช้ไม่ได้** เพราะ environment ในคอนเทนเนอร์แยก Python คนละเวอร์ชัน
(Vitis AI 3.0 = py3.7 ส่วน ultralytics รุ่นที่โหลด YOLO26 ได้ต้องการ py3.9+) → **จึงวิเคราะห์ ONNX op graph เอง**

**ผล 2 ข้อ:**

**(1) ข่าวดี — NMS-free head ไม่ใช่ปัญหา (ตรงข้ามกับที่คาด)**
ตั้ง `end2end=False` แล้ว watchlist ops หายหมด: ไม่มี TopK / GatherElements / GatherND / ReduceMax /
Mod / ScatterND / NonMaxSuppression / Range → decode+NMS ทำเองบน PS เหมือน Track A ที่สำเร็จแล้ว

**(2) ตัวบล็อกจริง — attention block 2 จุด "กลางกราฟ"**

| ตำแหน่ง | โมดูล | ops |
|---|---|---|
| node ~148–153 (**~32% ของกราฟ**) | `/model.10/m/m.0/attn` | MatMul → Softmax → MatMul |
| node ~315–320 (**~69% ของกราฟ**) | `/model.22/m.0/m.0.1/attn` | MatMul → Softmax → MatMul |

**ทำไม DPUCZDX8G ทำไม่ได้ (2 เหตุผลอิสระ):**
1. **MatMul แบบ data x data** — DPU ออกแบบบนสมมติฐานว่าตัวคูณฝั่งหนึ่งเป็น weight คงที่ (โหลดล่วงหน้าได้)
   แต่ attention คูณ tensor สองตัวที่เปลี่ยนทุก inference
2. **Softmax** — ต้องใช้ exponential + normalize ข้าม element (เหตุผลเดียวกับที่ทำ SiLU ไม่ได้)

**กลไกที่ทำให้ล้ม gate — ตำแหน่งสำคัญกว่าตัว operation ⭐**

```
Sigmoid ที่ ~99.6% (ปลายสุด):   [=== DPU ===]--[Sigmoid บน CPU]--> out   → ยังเป็น 1 subgraph ✅
attention ที่ 32% และ 69%:      [DPU]-[attn]-[DPU]-[attn]-[DPU]--> out   → ตัดเป็น ~3 subgraph ❌
```

> **ข้อสรุปเชิงกลไก:** *"operation ที่ DPU ไม่รองรับจะร้ายแรงแค่ไหน ขึ้นกับว่ามันอยู่ตรงไหนในกราฟ"*
> — ปลายกราฟ = ไม่กระทบ · กลางกราฟ = ตัด pipeline เป็นชิ้น ซึ่ง op histogram เฉย ๆ ไม่บอก

**op ที่ตรวจแล้วไม่ใช่ปัญหา:** MaxPool×3 (~28%, SPPF) ✅ · Resize×2 (~37%/~46%, FPN upsample nearest) ✅ ·
Sigmoid×1 (~99.6%) ✅ — การตัดตัวเลือกออกสำคัญเท่ากับการหาตัวที่มีปัญหา

**ยังเหลือ:** compile จริงด้วย `vai_c_xir` เพื่อปิดตามกติกาของตัวเอง — ออกทางไหนก็เป็น finding
(เห็น `DPU subgraph number 3` = ยืนยัน mechanism · เห็น error ระบุ op = ยืนยันตรงกว่าเดิม + ได้ error เป็นหลักฐาน)

## 9. Contributions

1. **ระบบนับวัตถุแบบเรียลไทม์บน heterogeneous FPGA SoC พร้อมผลวัดครบ 4 มิติ** เทียบ GPU baseline
   ที่วัดเองด้วยเงื่อนไขเดียวกัน (ไม่ใช่อ้างตัวเลขจากเปเปอร์อื่น)
2. **องค์ความรู้เรื่องข้อจำกัดของการ deploy YOLO รุ่นใหม่บน DPU stack เดิม** — ระบุถึงระดับ
   operation, ตำแหน่งในกราฟ, และ *เหตุผลเชิงสถาปัตยกรรม* ว่าทำไมตำแหน่งจึงสำคัญ
3. **หลักฐานเชิงระบบว่า accelerator-only benchmark ให้ภาพลวง** — ตัวเลข 82.5 FPS (DPU) กับ 12.8 FPS
   (ทั้งระบบ) ต่างกัน 6.4x บนฮาร์ดแวร์เดียวกัน
4. *(ส่วนขยาย)* **cross-platform comparison** — port ระบบเดียวกันไป Efinix Ti375 (soft RISC-V +
   TinyML accelerator + TFLite แทน hard DPU + Vitis AI) เพื่อเทียบว่าข้อสรุปข้างบนผูกกับแพลตฟอร์มหรือไม่

## 11. งานที่เหลือและทิศทางต่อยอด

**เหลือเพื่อปิดโครงงาน:**
1. **compile YOLO26n จริง** (`vai_c_xir`, TARGET B4096) → ปิด RQ1 ตามกติกาของตัวเอง — น้ำหนักพร้อม (mAP 0.831), ไม่ต้องใช้บอร์ด
2. **เรียบเรียงเป็นเล่ม + สไลด์** (M14)

**ทิศทางต่อยอดที่มีตัวเลขรองรับ:**
- **แก้คอขวด preprocess** (F2): port เป็น C++ / NEON SIMD / hardware scaler ใน PL —
  ถ้าลด 49.7 ms → 10 ms จะได้ e2e 78.3 → 38.6 ms = **12.8 → 25.9 FPS (+103%)** โดยไม่ต้องแตะ DPU
- **cross-platform** (Efinix Ti375) — ทดสอบว่า F2 เป็นสมบัติของ DPU/ARM คู่นี้ หรือเป็นรูปแบบทั่วไปของ edge SoC

## 12. ประเมินตัวเอง: แก่นแข็งพอหรือยัง

**จุดที่แข็งแล้ว**
- ✅ **ปิดวงจรครบ** ตั้งแต่โมเดล → quantize → compile → บอร์ดจริง → แอปนับ → ตัวเลขเทียบ GT
- ✅ **มี baseline ที่วัดเอง** ไม่ใช่ตัวเลขยืมจากเปเปอร์ → การเปรียบเทียบมีน้ำหนัก
- ✅ **มี finding เชิงกลไกไม่ใช่แค่ตัวเลข** (F2, F3) — ตอบได้ว่า *ทำไม* ไม่ใช่แค่ *เท่าไร*
- ✅ **มี negative/ขัดความคาดหมายที่อธิบายได้** (NMS-free ไม่ใช่ปัญหา / คอขวดไม่ใช่ DPU) ซึ่งมีค่ากว่าผลที่คาดเดาได้
- ✅ **มี sensitivity analysis** รองผลเด่น (215/215) จึงไม่ถูกโจมตีว่าฟลุ๊ก
- ✅ **กติกาตัดสินตั้งไว้ล่วงหน้า** และไม่แก้ระหว่างทาง → กันข้อครหาว่าปรับเกณฑ์ให้ผ่าน

**จุดที่ยังเปราะ (เรียงตามความน่าจะโดนถาม)**
1. 🔴 **Track B ยังไม่ผ่าน gate ของตัวเอง** — นี่คือจุดที่กรรมการจะจิ้มก่อน เพราะชื่อโครงงานมีคำว่า YOLO26
   → **ต้องทำให้เสร็จ** ไม่ใช่แค่เขียนอธิบาย
2. 🟠 **ชุดข้อมูลเล็ก** (208/57/28) — ต้องเขียนข้อจำกัดไว้เอง และ *อย่า* เคลม mAP เกินระดับที่ set นี้รองรับ
3. 🟠 **การนับวัดคลิปเดียว** — ถ้ามีเวลา ควรตัดคลิปที่ 2 จากวิดีโอ 12 ชม. ต้นฉบับมานับมือเพิ่ม
   (แม้แค่ 300 วิ) จะทำให้ RQ4 แข็งขึ้นมาก ด้วยต้นทุนต่ำ
4. 🟡 **ยังไม่มีงานวิจัยที่เกี่ยวข้องเป็นรูปเป็นร่าง** — ยังไม่มีการ position งานนี้เทียบ prior work
   (`06-references/` ยังว่าง) เป็นช่องว่างเดียวที่ *ไม่ใช่* งานทดลอง แต่จำเป็นสำหรับเล่ม
5. 🟡 **ยังไม่ได้รันเทียบ latency ของ Efinix** — ส่วนขยายจึงยังเป็นเชิงคุณภาพ

mechanism) จุดอ่อนที่เหลือมี 2 ประเภทเท่านั้น — (ก) งานที่ *รู้วิธีทำแล้วและใช้เวลาไม่มาก*
(compile Track B, คลิปที่ 2) และ (ข) งานเขียน (related work) ซึ่งไม่มีความเสี่ยงเชิงเทคนิค
