# 02 — สถาปัตยกรรมและคอนเซปต์ที่ล็อกแล้ว

> **สรุปไฟล์นี้ใน 3 บรรทัด**
> ระบบแบ่งงานระหว่าง ARM CPU (PS) กับ DPU (PL) ในชิปเดียวกัน
> การแปลงโมเดลมี 3 ขั้น (export → quantize → compile) โดยมี **กติกาตัดสินข้อเดียว**
> คือ compiler ต้องบอกว่า `DPU subgraph number 1` และเดินสองเส้นทางขนานเพื่อบริหารความเสี่ยง

---

## 1. สถาปัตยกรรมระบบ (Dataflow)

### 1.1 ภาพรวม

```
                    วิดีโอ / กล้อง
                          │
                          ▼
        ┌─────────────────────────────────────┐
        │ [PS] อ่านเฟรม + preprocess          │  49.7 ms  ◄── คอขวด!
        │  • resize 640×640 (plain resize)     │
        │  • BGR → RGB                         │
        │  • หาร 255 (normalize เป็น 0..1)     │
        │  • quantize เป็น int8 (×64)          │
        └─────────────────────────────────────┘
                          │  NHWC int8 [1,640,640,3]
                          ▼
        ┌─────────────────────────────────────┐
        │ [PL] DPUCZDX8G B4096                 │  12.5 ms
        │  รัน YOLOv8n INT8 ทั้งโมเดล          │
        │  (1 DPU subgraph = ไม่มีการเด้งกลับ) │
        └─────────────────────────────────────┘
                          │  int8 × 3 หัว [80,80,65] [40,40,65] [20,20,65]
                          ▼
        ┌─────────────────────────────────────┐
        │ [PS] postprocess                     │  16.1 ms
        │  • dequantize (×2^-fixpos)           │
        │  • DFL decode → กล่อง                │
        │  • sigmoid → คะแนน                   │
        │  • NMS → ตัดกล่องซ้ำ                 │
        └─────────────────────────────────────┘
                          │  รายการกล่อง (x1,y1,x2,y2,score)
                          ▼
        ┌─────────────────────────────────────┐
        │ [PS] centroid tracker                │
        │  จับคู่กล่องเฟรมนี้กับ track เดิม     │
        │  ด้วยระยะจุดศูนย์กลาง (max_dist=60)  │
        └─────────────────────────────────────┘
                          │  track ที่มี ID + เส้นทางการเคลื่อนที่
                          ▼
        ┌─────────────────────────────────────┐
        │ [PS] line-crossing logic             │
        │  ถ้า track ข้ามเส้น x = 0.40·W       │
        │  ครั้งแรก → count += 1               │
        └─────────────────────────────────────┘
                          │
                          ▼
                  จำนวนที่นับได้ / แสดงผล
```

### 1.2 เหตุผลของการแบ่งงานแต่ละขั้น

| ขั้น | ทำไมต้องอยู่ที่นั่น |
|---|---|
| preprocess ที่ PS | ต้องอ่านไฟล์/กล้อง ซึ่งเป็นงาน I/O ที่ต้องผ่าน OS |
| inference ที่ PL | convolution คือการคูณ-บวกซ้ำๆ นับพันล้านครั้ง = งานที่ฮาร์ดแวร์เฉพาะทางชนะขาด |
| decode + NMS ที่ PS | **ถูกบังคับ** — เราตัดส่วนนี้ออกจากกราฟตอน compile (เหตุผลในข้อ 3.3) |
| tracking ที่ PS | เป็น logic ที่แตกกิ่งเยอะ (if-else, การจับคู่) ซึ่งขนานยาก → CPU เหมาะกว่า |
| counting ที่ PS | เงื่อนไขง่ายๆ ไม่คุ้มที่จะเร่ง |

### 1.3 ข้อสังเกตที่กลายเป็นข้อค้นพบ

ดูเวลาที่กำกับไว้ในแผนภาพ: **49.7 / 12.5 / 16.1 ms**

> ส่วนที่เราคิดว่าเป็นพระเอก (DPU) ใช้เวลาน้อยที่สุด
> ส่วนที่คิดว่าเป็นงานเตรียมของ (preprocess) กลับกินเวลามากที่สุด
>
> → นี่คือที่มาของข้อค้นพบว่าระบบเป็น **PS-bound** (รายละเอียดไฟล์ 07)

## 2. ฮาร์ดแวร์ที่ใช้

### 2.1 สเปคบอร์ด

| รายการ | ค่า | ความหมาย |
|---|---|---|
| บอร์ด | AMD Kria KV260 Vision AI Starter Kit | บอร์ดสำเร็จรูปสำหรับงาน vision |
| ชิป | Zynq UltraScale+ MPSoC | CPU + FPGA ในชิปเดียว |
| CPU (PS) | ARM Cortex-A53 quad-core | รัน Linux ได้ปกติ |
| AI accelerator (PL) | **DPUCZDX8G_ISA1_B4096** | ดูคำอธิบายข้างล่าง |
| Fingerprint | `0x101000056010407` | ลายนิ้วมือของ DPU ตัวนี้ |
| OS | PetaLinux starter-kit 2022.2 | Linux ที่ AMD ทำมาให้บอร์ดนี้ |
| Runtime | VART 3.0 | ไลบรารีที่ใช้สั่งงาน DPU จากโปรแกรม |

### 2.2 เลข B4096 หมายถึงอะไร

DPU มีหลายขนาดให้เลือก (B512, B800, B1024, B1600, B2304, B3136, **B4096**)
ตัวเลขบอก **จำนวน operation ที่ทำได้ต่อ 1 clock cycle**

```
B4096 = ทำได้ 4096 operations ต่อ cycle
        ↑ ยิ่งใหญ่ยิ่งเร็ว
        ↓ แต่กินทรัพยากรใน PL (LUT, DSP, BRAM) มากขึ้น
```

**ทำไมเรื่องนี้สำคัญ:** โมเดลต้อง compile ให้ตรงกับขนาด DPU ที่อยู่บนบอร์ดจริง
ถ้า compile ผิดขนาด โมเดลจะโหลดไม่ขึ้น → เป็นที่มาของ **"วิกฤตที่ 3"** ในไฟล์ 03

**ตัวเลขจริงที่วัดได้:** โมเดลของเราใช้ **8.10 GOP ต่อ 1 ภาพ** และทำได้ 82.5 FPS
→ throughput เชิงคำนวณ = 8.10 × 82.5 ≈ **668 GOPS**

### 2.3 Fingerprint คืออะไร ทำไมต้องเช็ค

Fingerprint คือ **ค่าที่บอกว่า DPU ตัวนี้มีคุณสมบัติอะไรบ้าง** (ขนาด, feature ที่รองรับ, เวอร์ชัน ISA)
โมเดลที่ compile แล้วจะมี fingerprint ฝังอยู่ ถ้าไม่ตรงกับบอร์ด → runtime ปฏิเสธไม่ยอมรัน

> ในโครงงานนี้ เรา compile โมเดลไว้ **ก่อนที่บอร์ดจะมาถึง** โดยอ้างอิงจากเอกสาร
> ดังนั้นวินาทีที่บอร์ดมาถึงและรัน `xdputil query` แล้วเห็น fingerprint `0x101000056010407` **ตรงเป๊ะ**
> คือวินาทีที่ความเสี่ยงใหญ่ที่สุดของโครงงานถูกปิดลง (รายละเอียดไฟล์ 06)

## 3. Toolchain: จากโมเดล PyTorch ไปสู่บอร์ด

### 3.1 ภาพรวม 3 ขั้น

```
  yolov8n_leaky_pkg_ft.pt  (PyTorch, FP32, 6.30 MB)
            │
            │  ขั้นที่ 1: EXPORT
            │  เดินกราฟโมเดล แปลงเป็นรูปแบบกลางที่เครื่องมือถัดไปอ่านได้
            ▼
     กราฟที่ trace แล้ว
            │
            │  ขั้นที่ 2: QUANTIZE  (vai_q_pytorch)
            │  • PASS 1: ป้อนภาพ calibration 32 ภาพ → เก็บสถิติค่าที่ไหลผ่านแต่ละ layer
            │  • PASS 2: คำนวณ scale ที่เหมาะ → แปลง FP32 → INT8 → export XIR
            ▼
     BackboneHead_int.xmodel  (12.3 MB, INT8 แต่ยังไม่ผูกกับฮาร์ดแวร์)
            │
            │  ขั้นที่ 3: COMPILE  (vai_c_xir)
            │  จัดสรร layer ลง DPU, วางแผน memory, สร้าง instruction
            ▼
     yolov8n_pkg_kv260.xmodel  (3.99 MB, พร้อมรันบน B4096)
            │
            │  โอนขึ้นบอร์ด (HTTP + wget, verify md5)
            ▼
          รันด้วย VART
```

### 3.2 แต่ละขั้นทำอะไรจริงๆ

**ขั้น EXPORT** — แปลงจากโค้ด Python ที่มี if-else ให้เป็น**กราฟคงที่**
เพราะฮาร์ดแวร์รันโค้ดที่แตกกิ่งไม่ได้ ต้องรู้ล่วงหน้าว่าข้อมูลไหลไปทางไหน

**ขั้น QUANTIZE** — หัวใจคือการหา "มาตราส่วน" ที่ดีที่สุด
```
ค่าจริง (FP32) ในช่วง [-8.0, +8.0]
        ↓ ต้องบีบให้อยู่ใน int8 ที่มีแค่ 256 ระดับ [-128, +127]
เลือก scale = 16  →  ค่า 1 หน่วยของ int8 = 0.0625 ของค่าจริง
        ↓
ค่า 3.7 → round(3.7 × 16) = 59 → เก็บเป็น 59
อ่านกลับ: 59 / 16 = 3.6875  (คลาดเคลื่อน 0.0125)
```
ถ้าเลือก scale ผิด (เล็กไป) → ค่าที่เกินช่วงจะถูก **clamp** ทิ้ง = ข้อมูลหายถาวร
**นี่คือสาเหตุที่ calibration set ต้องเป็นภาพจากโดเมนจริง** — ถ้าใช้ภาพผิดโดเมน สถิติจะเพี้ยน scale จะผิด
(โครงงานนี้เคยใช้ COCO เป็น calibration แล้วต้องเปลี่ยนเป็นภาพสายพานจริง 208 ภาพ)

**ขั้น COMPILE** — ตัวที่ตัดสินว่าโมเดล "ผ่าน" หรือไม่ (ดูข้อ 4)

### 3.3 ทำไมต้องตัด decode ออกจากกราฟ

โมเดล YOLO ต้นฉบับมีขั้นตอนสุดท้ายที่แปลง output ดิบให้เป็นพิกัดกล่อง
ขั้นตอนนี้ใช้ operation อย่าง `split_with_sizes` และ `chunk` ที่**รูปแบบ XIR ไม่รองรับ** (ไม่รองรับ op ที่มีหลาย output)

**วิธีแก้ที่ใช้:** สร้าง wrapper class ชื่อ `BackboneHead` ที่เดิน layer เอง แล้ว return **output ดิบ**
(`cat(cv2, cv3)`) โดยไม่แตะส่วน decode เลย

**ผลที่ตามมา:** ต้องเขียน decode ขึ้นมาใหม่เองบน PS (ทำในไฟล์ `yolo_dpu_detect.py`)
รายละเอียดการ decode อยู่ในไฟล์ 06

> นี่เป็น trade-off ที่ต้องยอมรับ: **แลกความง่ายในการ deploy กับการต้องเขียน postprocess เอง**
> และมันกลายเป็นส่วนหนึ่งของ 16.1 ms ในตาราง latency

### 3.4 การ pin เวอร์ชัน Docker

ใช้ image `xilinx/vitis-ai-pytorch-cpu:ubuntu2004-3.0.0.106` — **ห้ามใช้ `:latest`**

| เหตุผล | รายละเอียด |
|---|---|
| `:latest` = Vitis AI 3.5 | ซึ่ง**ไม่มี prebuilt สำหรับ KV260** |
| ไม่มี `arch.json` ของ KV260 | → compile ไม่ได้เลย |
| ไม่มี `board_setup/mpsoc` | → ไม่มีสคริปต์เตรียมบอร์ด |

> **บทเรียนเชิงปฏิบัติ:** ในงานที่ต้องทำซ้ำได้ (reproducible) การ pin เวอร์ชันสำคัญพอๆ กับตัวโค้ด

## 4. กติกาตัดสินที่ตั้งไว้ตั้งแต่ต้น (สำคัญที่สุด)

> ### "gate เดียวที่นับคือ log ของ `vai_c_xir` ที่บอกว่า `DPU subgraph number 1`
> ### ไม่ใช่ op histogram ไม่ใช่ผลจาก Inspector"

### 4.1 subgraph คืออะไร ทำไม 1 ถึงสำคัญ

เมื่อ compiler เจอ operation ที่ DPU ทำไม่ได้ มันจะ**ตัดกราฟตรงนั้น** แล้วส่งส่วนที่ทำไม่ได้ไปรันบน CPU

```
กรณีที่ดี (1 subgraph):
  input → [═══════ DPU ทั้งหมด ═══════] → output
          ข้อมูลเข้า-ออก DPU ครั้งเดียว

กรณีที่แย่ (3 subgraph):
  input → [══ DPU ══] → [CPU] → [══ DPU ══] → [CPU] → [══ DPU ══] → output
                    ↑ ต้องคัดลอกข้อมูลจาก DPU กลับมา RAM
                      แล้วส่งกลับไปใหม่ ทำ 4 รอบ
```

**ราคาของการตัด subgraph:**
1. การโอนข้อมูลระหว่าง DPU กับ CPU ใช้เวลา (feature map กลางเน็ตมีขนาดใหญ่)
2. operation ที่ตกไป CPU เช่น Softmax บน tensor ใหญ่ = ช้ามากบน ARM
3. DPU ต้องหยุดรอ = ประสิทธิภาพพัง

### 4.2 ทำไมไม่เชื่อ Inspector

Vitis AI มีเครื่องมือชื่อ **Inspector** ที่บอกล่วงหน้าว่า op ไหนน่าจะรันบน DPU ได้
แต่มันเป็นแค่ **advisory** — วิเคราะห์จากรายชื่อ op ไม่ได้จำลอง compiler จริง

**ตัวที่ตัดสินจริงคือ compiler** เพราะ compiler รู้เรื่องที่ Inspector ไม่รู้:
- ขนาด tensor พอดีกับ memory ของ DPU หรือไม่
- pattern การเชื่อมต่อของ layer รองรับหรือไม่
- ข้อจำกัดเฉพาะของ arch นั้น

> **กติกานี้ช่วยกันการ "หลอกตัวเอง"** — เคยเจอกรณีที่ Inspector บอกว่า
> `All the operators are assigned to the DPU` แต่ยังต้องไปยืนยันด้วย compile จริงอยู่ดี
>
> และกติกานี้ยังใช้กับ Track B ด้วย: ตอนนี้เรารู้จาก ONNX analysis แล้วว่า YOLO26 น่าจะตัดเป็น ~3 subgraph
> แต่**ยังต้อง compile จริงเพื่อยืนยัน** (ดูไฟล์ 11 งานที่เหลือลำดับ 1)

### 4.3 กติกาย่อยที่ตั้งเพิ่มระหว่างทาง

| กติกา | ที่มา |
|---|---|
| **verify artifact จริง ไม่ใช่เชื่อ log** | เจอกรณีสคริปต์บอกสำเร็จเพราะ `set +e` ทั้งที่ไม่มีไฟล์ออกมา |
| **ตรวจ identity จาก channel count ไม่ใช่ชื่อไฟล์** | เจอไฟล์ชื่อ `yolo26n_*.xmodel` ที่ข้างในเป็น YOLOv8n |
| **verify md5 ทุกครั้งหลังโอนไฟล์** | ป้องกันไฟล์เพี้ยนระหว่างโอนแบบเงียบๆ |
| **"ลงสำเร็จ ≠ ได้ของที่ต้องการ"** | เจอกรณี pip install torch ผ่าน แต่ได้ CPU build |

## 5. กลยุทธ์สองเส้นทางขนาน (Two-Track Strategy)

### 5.1 ปัญหาเชิงบริหารความเสี่ยง

ชื่อโครงงานระบุ **YOLO26** ซึ่งเป็นโมเดลรุ่นใหม่ที่:
- ไม่อยู่ใน Vitis AI Model Zoo (ไม่มีใครเคยทำ)
- ใช้ NMS-free head ที่มี operation แปลกๆ
- ต้องการ ultralytics เวอร์ชันใหม่ที่ต้องการ Python ใหม่กว่าที่ container มี

**ถ้าเดิมพันกับ YOLO26 อย่างเดียวแล้วมันไม่ผ่าน → โครงงานจะไม่มีผลอะไรเลย**

### 5.2 ทางออก: เดินสองทางพร้อมกัน

| | **Track A — YOLOv8n** | **Track B — YOLO26n** |
|---|---|---|
| บทบาท | baseline ที่พิสูจน์แล้ว / **ตาข่ายนิรภัย** | โมเดลเป้าหมายตามชื่อโครงงาน |
| ทำไมเลือกตัวนี้ | มี prior work เยอะ อยู่ใน Model Zoo โครงสร้างเข้าใจดี | เป็นรุ่นล่าสุด มีคุณค่าเชิงวิชาการ |
| ความเสี่ยง | ต่ำ | สูง |
| สิ่งที่ได้ถ้าสำเร็จ | ระบบนับที่ใช้งานได้จริง + ตัวเลขครบ | เป็นคนแรกที่ deploy YOLO26 บน DPU นี้ |
| สิ่งที่ได้ถ้าล้ม | (ไม่ล้ม — สำเร็จแล้ว ✅) | **องค์ความรู้ว่าติดตรงไหน เพราะอะไร** |
| สถานะจริง | ✅ สำเร็จครบวงจรบนบอร์ด | 🔴 พิสูจน์แล้วว่า compile ทั้งตัวไม่ได้ + รู้สาเหตุแน่ชัด |

### 5.3 ประเด็นสำคัญ: Track B "ล้ม" ก็ยังเป็น contribution

นี่ไม่ใช่การหาข้ออ้าง แต่เป็นธรรมชาติของงานวิจัยเชิงระบบ:

> **คำถามวิจัยคือ "YOLO รุ่นใหม่ deploy ลง DPU ได้แค่ไหน"**
> คำตอบว่า **"ไม่ได้ เพราะติดที่ attention block ตำแหน่ง X และ Y ด้วยกลไก Z"**
> เป็นคำตอบที่สมบูรณ์พอๆ กับคำตอบว่า "ได้"
>
> และมีประโยชน์กับคนอ่านมากกว่าด้วยซ้ำ เพราะคนที่จะทำต่อจะรู้ว่าต้องเตรียมรับมืออะไร

สิ่งที่ทำให้มันเป็น contribution จริงคือ **ความเจาะจงของคำตอบ** — เราไม่ได้บอกแค่ "มันไม่ทำงาน"
แต่บอกได้ถึงระดับ node ในกราฟ (ไฟล์ 08)

```
   เริ่มโครงงาน ────────┤
                         └─→ Track B ไม่ผ่าน ──→ กลายเป็น finding เชิงวิชาการ ✅ (เกิดขึ้นจริง)

   ผลลัพธ์: ได้ทั้งระบบที่ใช้งานได้ และองค์ความรู้ใหม่ — ไม่มีสถานการณ์ที่โครงงานว่างเปล่า
```
