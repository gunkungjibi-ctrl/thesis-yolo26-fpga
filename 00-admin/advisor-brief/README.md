## สรุป 1 หน้า

### โจทย์
สร้างระบบนับวัตถุ (กล่องพัสดุบนสายพาน) แบบเรียลไทม์จากวิดีโอ โดยรัน YOLO บน **FPGA** แทน **GPU**
แล้วพิสูจน์ด้วยตัวเลขว่าคุ้มค่าตรงไหน เสียอะไรไปบ้าง

### สถานะ
**ระบบทำงานครบวงจรบนบอร์ดจริงแล้ว และเก็บผลวัดครบทั้ง 4 หมวดแล้ว**

### ตัวเลขที่ได้

| หัวข้อ | ผลลัพธ์ |
|---|---|
| โมเดลบน DPU | YOLOv8n INT8 · **1 DPU subgraph** · 8.10 GOP/ภาพ · 3.99 MB |
| ความเร็ว DPU ล้วน | **82.5 FPS** (single-thread) / 89.6 FPS (4 threads) |
| ความเร็วทั้งระบบ | 12.8 FPS (คอขวดคือ preprocessing บน ARM ไม่ใช่ DPU) |
| ความแม่นยำ float | mAP@0.5 = 0.8846 |
| ความแม่นยำ INT8 | **mAP@0.5 = 0.8713 → ตกแค่ 1.5%** |
| กำลังไฟ | 9.27 W (เต็มโหลด) · 5.10 W (แอปจริง) · idle 4.85 W |
| ประสิทธิภาพพลังงาน | **9.67 FPS/W** เทียบ GPU ดีสุด 4.51 → **ดีกว่า 2.1×** |
| กินไฟเทียบ GPU | 9.27 W vs 58.5 W → **น้อยกว่า 6.3×** |
| **งานนับกล่อง** | GT = 215 → ระบบนับได้ **215 → error 0.0%** |

### สามข้อค้นพบที่จะเขียนเข้าเล่ม

**1. Quantization INT8 แทบไม่ทำให้ความแม่นยำเสีย**
mAP ตก 1.5% แต่ประหยัดไฟ 6.3 เท่า → คุ้มค่าอย่างชัดเจนสำหรับงาน edge
*(รายละเอียด: ไฟล์ 07 ตารางที่ 2)*

**2. คอขวดไม่ได้อยู่ที่ตัวเร่ง AI แต่อยู่ที่ CPU**
DPU ใช้เวลาแค่ 16% ของ pipeline ส่วน preprocessing บน ARM กิน 63%
ยืนยันด้วยหลักฐาน 2 ชิ้นที่วัดคนละวิธี → เป็นข้อค้นพบเชิงระบบที่ชี้ทิศทาง optimization ชัดเจน
*(รายละเอียด: ไฟล์ 07 ตารางที่ 3 และ 4)*

**3. YOLO26 map ลง DPU รุ่นนี้ไม่ได้ทั้งตัว — และเรารู้แล้วว่าติดตรงไหนเป๊ะ**
ไม่ได้ติดที่ NMS-free head อย่างที่คาด แต่ติดที่ **attention block 2 จุดกลางกราฟ**
(MatMul แบบ data×data + Softmax ที่ ~32% และ ~69% ของกราฟ)
เป็นองค์ความรู้ที่ยังไม่มีใครรายงาน เพราะ YOLO26 ไม่อยู่ใน Vitis AI Model Zoo
*(รายละเอียด: ไฟล์ 08)*

### หนึ่งประโยคสำหรับปิดท้าย
> ระบบนับพัสดุทำงานได้จริงบนบอร์ดที่กินไฟระดับ 5 วัตต์ นับได้ 215 จาก 215 กล่อง
> โดยเสียความแม่นยำจากการ quantize เพียง 1.5% และประหยัดไฟกว่า GPU ถึง 6 เท่า
