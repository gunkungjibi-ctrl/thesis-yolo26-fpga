## 2. อุปสรรคชั้นแรก: toolchain เก่ากว่าโมเดล

### 2.1 เครื่องมือที่ควรใช้: nndct Inspector

Vitis AI มีเครื่องมือชื่อ **Inspector** ที่บอกล่วงหน้าว่า operation ไหนจะรันบน DPU ได้บ้าง

| แพ็กเกจที่ต้องใช้ | อยู่ที่ | ต้องการ Python |
|---|---|---|
| `pytorch_nndct` (Inspector + quantizer) | conda env `vitis-ai-pytorch` **เท่านั้น** | **3.7.12** |
| `ultralytics==8.4.71` (โหลด YOLO26n ได้) | ต้องติดตั้งเอง | บังคับ **≥ 3.8** |

### 2.3 สำรวจ environment ทั้งหมดในคอนเทนเนอร์


## 4. ผลการวิเคราะห์: สองข้อค้นพบ

### 4.1 ✅ ข่าวดี: NMS-free head ไม่ใช่ปัญหา (ตรงข้ามกับที่คาดไว้)

**สิ่งที่คาดไว้:** YOLO26 ใช้ NMS-free head ซึ่งฝัง postprocess เข้าไปในโมเดล
→ น่าจะมี TopK, GatherElements ที่ DPU ทำไม่ได้

**สิ่งที่พบจริง:** ตั้ง `end2end=False` แล้ว → **watchlist ops หายหมด**

```
ตรวจแล้วไม่มี:  TopK ✗  GatherElements ✗  GatherND ✗  ReduceMax ✗
                Mod ✗  ScatterND ✗  NonMaxSuppression ✗  Range ✗
```

**ทำไมถึงหาย:**
```
end2end=True   →  โมเดลรวม postprocess ไว้ในกราฟ
                   (สร้าง TopK×2 + GatherElements×2)

end2end=False  →  โมเดลคืนแค่ output ดิบ
                   → เราไป decode/NMS เองบน ARM PS ตอน deploy
                   → เหมือนที่ทำสำเร็จแล้วกับ Track A
```

**การตรวจสอบเพิ่ม:** SiLU → LeakyReLU แทนครบ (0 SiLU / 105+ LeakyReLU)

> **ข้อสรุปที่มีค่า:** ปัญหาที่คนคาดว่าจะใหญ่ที่สุด (NMS-free head) **แก้ได้ด้วยการตั้ง flag เดียว**
> — ข้อมูลนี้มีประโยชน์กับคนที่จะทำต่อ เพราะประหยัดเวลาไปกังวลเรื่องผิดจุด

### 4.2 🔴 ตัวบล็อกจริง: attention block 2 จุด "กลาง" เน็ตเวิร์ก

| ตำแหน่งในกราฟ | โมดูล | operations |
|---|---|---|
| node ~148–153 (**~32% ของกราฟ**) | `/model.10/m/m.0/attn` | MatMul → Softmax → MatMul |
| node ~315–320 (**~69% ของกราฟ**) | `/model.22/m.0/m.0.1/attn` | MatMul → Softmax → MatMul |

### 4.3 โครงสร้างที่พบคืออะไร

รูปแบบ `MatMul → Softmax → MatMul` คือ **self-attention** ที่ใช้ใน Transformer:

```
        Q (query)   K (key)      V (value)
           │          │             │
           └────┬─────┘             │
                ▼                   │
          MatMul (Q · Kᵀ)           │     ← "แต่ละตำแหน่งควรสนใจตำแหน่งไหนบ้าง"
                │                   │
                ▼                   │
            Softmax                 │     ← แปลงเป็นน้ำหนักที่รวมกันได้ 1
                │                   │
                └─────────┬─────────┘
                          ▼
                   MatMul (× V)           ← ถ่วงน้ำหนักข้อมูลตามความสนใจ
```

YOLO26 ใช้บล็อกนี้ในโมดูลชื่อ A2C2f / PSA เพื่อให้โมเดลมองเห็นความสัมพันธ์ระยะไกลได้ดีขึ้น

### 4.4 ทำไม DPUCZDX8G ทำไม่ได้ (2 เหตุผล)

**เหตุผลที่ 1 — MatMul แบบ data × data**

```
Convolution ปกติ:                    Attention MatMul:
  ┌──────────┐   ┌──────────┐         ┌──────────┐   ┌──────────┐
  │  ข้อมูล   │ × │  weight  │         │  ข้อมูล   │ × │  ข้อมูล   │
  │ (เปลี่ยน) │   │(คงที่!)  │         │ (เปลี่ยน) │   │(เปลี่ยน!) │
  └──────────┘   └──────────┘         └──────────┘   └──────────┘
        ↓                                    ↓
  DPU โหลด weight ไว้ล่วงหน้าได้        ต้องคำนวณทั้งสองฝั่งใหม่ทุกครั้ง
  → ออกแบบวงจรให้เร็วมากได้             → DPU ไม่มีวงจรรองรับ
```

DPU ถูกออกแบบมาโดยสมมติว่า **ตัวคูณฝั่งหนึ่งเป็นค่าคงที่** (คือ weight ที่เทรนมาแล้ว)
สมมติฐานนี้ทำให้มันวางวงจรได้อย่างมีประสิทธิภาพสูงมาก — แต่ก็ทำให้มันทำ attention ไม่ได้

**เหตุผลที่ 2 — Softmax**

```
softmax(x_i) = e^(x_i) / Σ e^(x_j)
```
ต้องคำนวณ exponential + การหารแบบ normalize ข้าม element
→ ไม่ใช่ DPU op → ต้องเด้งไปรันบน ARM PS

*(เป็นเหตุผลเดียวกับที่ DPU ทำ SiLU ไม่ได้ — ดูไฟล์ 05 ข้อ 2)*

### 4.5 กลไกที่ทำให้ล้ม gate ⭐ — ตำแหน่งสำคัญกว่าตัว operation

นี่คือส่วนที่ต้องอธิบายให้ชัด เพราะเป็นแก่นของ finding:

```
กรณี Sigmoid ที่ตำแหน่ง ~99.6% (ปลายสุด):
  ┌═══════════════ DPU ═══════════════┐──[Sigmoid บน CPU]──► output
                                        ↑
                              อยู่ท้ายสุด → ไม่ตัดอะไร
                              → ยังนับเป็น 1 DPU subgraph ✅


กรณี attention ที่ตำแหน่ง 32% และ 69% (กลางกราฟ):
  ┌═ DPU ═┐──[attn]──┌═══ DPU ═══┐──[attn]──┌═ DPU ═┐──► output
    0-32%   บน CPU      32-69%     บน CPU     69-100%
      ↑                    ↑                     ↑
   subgraph 1          subgraph 2           subgraph 3
                → ตัดเป็น ~3 ชิ้น → gate "1 subgraph" ผ่านไม่ได้ ❌
```

**ราคาที่ต้องจ่ายถ้ายอมให้ตัด:**
1. ต้องคัดลอก feature map จาก DPU กลับมา RAM แล้วส่งกลับไปใหม่ — **4 รอบ**
2. feature map กลางเน็ตมีขนาดใหญ่ → การโอนใช้เวลามาก
3. Softmax บน tensor ใหญ่ทำบน ARM = ช้ามาก
4. DPU ต้องหยุดรอทุกครั้ง

> **ข้อสรุปเชิงกลไก:**
> **"operation ที่ DPU ไม่รองรับ จะร้ายแรงแค่ไหน ขึ้นกับว่ามันอยู่ตรงไหนในกราฟ"**
> — ปลายกราฟ = ไม่เป็นไร · กลางกราฟ = ตัด pipeline เป็นชิ้น
>
> นี่คือความรู้ที่ op histogram เฉยๆ ไม่บอก ต้องดูตำแหน่งประกอบด้วย

### 4.6 operation อื่นที่ตรวจแล้วไม่ใช่ปัญหา

| operation | ตำแหน่ง | สถานะ |
|---|---|---|
| MaxPool × 3 | ~28% (ใน SPPF) | ✅ DPU รองรับ |
| Resize × 2 | ~37% / ~46% (FPN upsample, nearest) | ✅ DPU รองรับ |
| Sigmoid × 1 | ~99.6% (ปลายสุด, decode) | ✅ อยู่ปลายกราฟ ไม่ตัด subgraph |

> การตรวจ operation เหล่านี้สำคัญเท่ากับการหาตัวที่มีปัญหา —
> เพราะมันช่วย**ตัดตัวเลือกที่ไม่ใช่ออก** และยืนยันว่า attention คือตัวบล็อกจริงตัวเดียว

### 5.1 ความเจาะจงของคำตอบ

### 5.2 องค์ความรู้ที่ส่งต่อได้

คนที่จะทำงานต่อจากเราจะได้รู้ 3 อย่างทันที:

**1. ไม่ต้องไปกังวลเรื่อง NMS-free head** — แก้ได้ด้วย `end2end=False`
(ประหยัดเวลาไปหลายวันที่จะเสียไปกับการแก้ปัญหาผิดจุด)

**2. ตัวบล็อกจริงคือ attention** — และมันอยู่ตำแหน่งที่แย่ที่สุด (กลางกราฟ)

**3. ทางเลือกที่เหลือมี 3 ทาง:**

| ทางเลือก | สิ่งที่ต้องทำ | ผลที่ได้ | ความยาก |
|---|---|---|---|
| **(a) ยอมรับ multi-subgraph** | ปล่อยให้ attention รันบน PS แล้ววัด latency penalty จริง | ได้ตัวเลขว่า "ราคาของ attention บน DPU stack = เท่าไร" | ต่ำ |
| **(b) ถอด/แทน attention** | เปลี่ยนเป็นบล็อก conv-only แล้ว retrain | อาจเหลือ 1 subgraph | สูง + กระทบ accuracy |
| **(c) รอ DPU รุ่นใหม่** | ใช้ DPU ที่รองรับ attention (เช่น DPUCVDX8G บน Versal) | ได้ทั้งตัว | ต้องเปลี่ยนฮาร์ดแวร์ |

### 5.3 ทำไมยังไม่มีใครรายงาน

| เหตุผล | รายละเอียด |
|---|---|
| YOLO26 ไม่อยู่ใน Model Zoo | AMD ไม่ได้ทดสอบ → ไม่มีเอกสารทางการ |
| เป็นโมเดลใหม่ | ยังไม่มีเวลาให้ชุมชนทดลอง |
| ต้องมีทั้งฮาร์ดแวร์และ toolchain | ไม่ใช่งานที่ทำได้จากการอ่านเอกสารอย่างเดียว |

### 5.4 การเชื่อมโยงกับคำถามวิจัย

> **คำถามวิจัยข้อ 1: "YOLO รุ่นใหม่ deploy ลง DPU ได้จริงแค่ไหน ติดข้อจำกัดอะไร"**
>
> **คำตอบที่ได้:** ติด 2 ชั้น —
> **ชั้นที่ 1 (toolchain):** ติดตั้ง library ร่วมกันไม่ได้เพราะ Python คนละเวอร์ชัน
> **ชั้นที่ 2 (op mapping):** attention block ที่ DPU map ไม่ได้ และอยู่ตำแหน่งที่ตัด pipeline
>
> **นี่คือคำตอบที่สมบูรณ์** — ตอบทั้งว่า "ไม่ได้" และ "เพราะอะไร" และ "ทำอะไรต่อได้บ้าง"

## 6. สิ่งที่ยังต้องทำเพื่อปิด Track B ให้สมบูรณ์

### 6.1 งานที่เหลือ: compile จริงเพื่อยืนยัน

**ตอนนี้เรามี:** ผลจาก ONNX op analysis ที่**ทำนาย**ว่าจะตัดเป็น ~3 subgraph
**ที่ยังขาด:** ผลจาก `vai_c_xir` จริงที่**ยืนยัน**ว่าตัดเป็นกี่ subgraph

### 6.2 ทำไมต้องทำ

> **เพราะเราตั้งกติกาไว้เองในไฟล์ 02 ข้อ 4 ว่า:**
> *"gate เดียวที่นับคือ log ของ `vai_c_xir` — ไม่ใช่ op histogram ไม่ใช่ Inspector"*
>
> ถ้าเราไม่ทำตามกติกาที่ตั้งเอง จะโดนถามได้ทันทีว่า **"แน่ใจได้อย่างไรว่ามันตัดจริง"**
> และเราจะตอบไม่ได้ เพราะ op histogram เป็นแค่ advisory ตามที่เราเองบอกไว้

### 6.3 คุณสมบัติของงานนี้

| รายการ | ค่า |
|---|---|
| ต้องใช้บอร์ดไหม | **ไม่ต้อง** — ทำในคอนเทนเนอร์ได้ |
| น้ำหนักโมเดลพร้อมหรือยัง | **พร้อม** — `yolo26n_leaky_pkg_ft.pt` (mAP 0.831) |
| สคริปต์พร้อมหรือยัง | มีอยู่ (`quantize_yolo26n_pytorch.py`, TARGET แก้เป็น B4096 แล้ว) |
| ความสำคัญ | **ลำดับ 1 ในงานที่เหลือ** (ดูไฟล์ 11) |

### 6.4 ผลลัพธ์ที่คาดหวัง 2 แบบ (ทั้งคู่ใช้ได้)

| ถ้า compile ได้ | ถ้า compile ล้ม |
|---|---|
| จะเห็น `DPU subgraph number 3` (หรือใกล้เคียง) | จะเห็น error ระบุ op ที่มีปัญหา |
| → **ยืนยัน mechanism ที่วิเคราะห์ไว้** | → **ยืนยันตรงกว่าเดิมด้วยซ้ำ** |
| + วัด latency penalty ได้ (ทางเลือก a) | + ได้ error message เป็นหลักฐานเข้าเล่ม |

> **ไม่ว่าผลออกทางไหน ก็ได้หลักฐานที่แข็งขึ้น** — จึงเป็นงานที่คุ้มค่าที่จะทำ

## 7. สรุป Track B

| หัวข้อ | สถานะ |
|---|---|
| M2-B1 — วิเคราะห์ op | ✅ เสร็จ (ผ่าน ONNX op analysis) |
| M2-B2 — fine-tune หลังสลับ activation | ✅ เสร็จ (mAP 0.831) |
| M2-B3 — compile → gate | ☐ **เหลืออยู่ — ลำดับ 1** |

**สิ่งที่รู้แล้ว:**
- NMS-free head **ไม่ใช่ปัญหา** (`end2end=False` แก้ได้)
- ตัวบล็อกจริง = **attention 2 จุด** ที่ ~32% และ ~69% ของกราฟ
- กลไก = MatMul data×data + Softmax ที่ DPU map ไม่ได้ + อยู่กลางกราฟจึงตัด subgraph
- toolchain compatibility เป็นอุปสรรคชั้นแรกก่อนถึงเรื่อง op ด้วยซ้ำ

**สิ่งที่ยังต้องยืนยัน:**
- จำนวน subgraph จริงจาก `vai_c_xir` log
