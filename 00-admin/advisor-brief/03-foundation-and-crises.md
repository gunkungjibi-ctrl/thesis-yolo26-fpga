# 03 — วางรากฐาน และวิกฤต 3 เรื่องที่เกือบทำโครงงานพัง

> **สรุปไฟล์นี้ใน 3 บรรทัด**
> หลังตั้ง toolchain และ compile ผ่านครั้งแรก เราไปตรวจหลักฐานย้อนหลังแล้วพบ 3 ปัญหาร้ายแรง:
> หลักฐานทั้งหมดอยู่ในที่เดียวที่เคยพังมาแล้ว · ไฟล์ผลลัพธ์ตั้งชื่อผิดจนเกือบรายงานผลผิดทั้งเล่ม
> · และเอกสารระบุขนาด DPU ขัดกันเอง — ทั้ง 3 เรื่องปิดจบด้วยการตรวจหลักฐานจากหลายแหล่ง

## ส่วนที่ 1 — วางรากฐาน (องก์ที่ 1)

### 1.1 หลักคิด: พิสูจน์ "เส้นทาง" ก่อนพูดเรื่อง "โมเดล"

ก่อนจะไปสนใจว่าโมเดลไหนแม่นกว่ากัน สิ่งที่ต้องพิสูจน์ก่อนคือ

> **"เส้นทางจากโมเดล PyTorch ไปถึงฮาร์ดแวร์จริง มันมีอยู่จริงและเดินได้"**

เพราะถ้าเส้นทางนี้ไม่มี ไม่ว่าโมเดลจะดีแค่ไหนก็ไม่มีประโยชน์

### 1.2 สิ่งที่ทำ

| งาน | ผลลัพธ์ |
|---|---|
| เปรียบเทียบและเลือกบอร์ด | เลือก KV260 → `01-docs/platform_selection.docx` |
| ตั้ง Vitis AI 3.0 container | ได้ environment ที่ครบ flow |
| รัน flow ครบวงจรครั้งแรก | `export → quantize → compile` ผ่าน |
| เขียน RUNBOOK | `03-model/RUNBOOK_phase0_ORIGINAL.md` — บันทึกทุกคำสั่งเพื่อทำซ้ำได้ |

### 1.3 เหตุผลที่เลือก KV260

| เกณฑ์ | KV260 |
|---|---|
| มี DPU สำเร็จรูป | ✅ — ไม่ต้องออกแบบวงจรเอง |
| มี Vitis AI stack สมบูรณ์ | ✅ — มี arch.json, board_setup, prebuilt image |
| ราคาเข้าถึงได้ | ✅ — เป็น starter kit ระดับนักศึกษา |

### 1.4 ผลลัพธ์องก์ที่ 1

✅ **Track A (YOLOv8n) compile ผ่าน gate ได้ `DPU subgraph number 1`**

ณ จุดนี้ ในบันทึกเขียนไว้ว่า *"Phase 0 ผ่านแล้ว"* — แต่เมื่อไปตรวจหลักฐานภายหลัง กลับพบเรื่องที่ไม่คาดคิด

## ส่วนที่ 2 — วิกฤตที่ 1: หลักฐานทั้งหมดอยู่ในที่เดียว และที่นั้นเคยพังมาแล้ว

### 2.1 สถานการณ์

artifact ทั้งหมดของโครงงาน — ไฟล์ `.xmodel`, compile log, calibration images, ผลวัด —
อยู่ใน **WSL virtual disk (`.vhdx`)** ซึ่งเป็นไฟล์เดียวที่วางอยู่บนไดรฟ์ C: ของ Windows

### 2.2 ทำไมถึงอันตราย: มันเคยพังมาแล้วจริงๆ

ระหว่างการติดตั้ง PyTorch เพื่อทำ GPU baseline เกิดเหตุการณ์นี้:

```
เริ่มติดตั้ง torch (~6 GB)
      ↓
ไดรฟ์ C: เหลือแค่ 1.22 GB
      ↓
.vhdx พยายามขยายตัว → ขยายไม่ได้เพราะ C: เต็ม
      ↓
Linux kernel ตรวจพบว่าเขียนดิสก์ไม่ได้
      ↓
remount filesystem เป็น read-only เพื่อป้องกันข้อมูลเสียหาย
      ↓
คำสั่งพื้นฐานเริ่มพัง: touch → "Read-only file system"
                        df    → "Bus error"
                        rm    → "Segmentation fault"
```

**ระบบไฟล์พังทั้งลูก** — โชคดีที่ครั้งนั้น artifact ไม่หาย เพราะเขียนเสร็จไปนานแล้วก่อนดิสก์เต็ม

### 2.3 ความเสี่ยงที่ยังคงอยู่

ถ้ามันพังอีกครั้งในจังหวะที่แย่กว่านี้ → **หลักฐานเข้าเล่มหายหมด ต้องทำใหม่ทั้งหมด**
ซึ่งหมายถึงการ re-quantize + re-compile + วัดผลใหม่ = เสียเวลาหลายสัปดาห์

### 2.4 สิ่งที่ทำ (งาน P0 — จัดลำดับให้ทำก่อนทุกอย่าง)

กู้โฟลเดอร์ `phase0/` ทั้งหมดออกจาก WSL มาไว้บนเดสก์ท็อป

| รายการตรวจสอบ | ผล |
|---|---|
| จำนวนไฟล์ | **162 ไฟล์** |
| ขนาดรวม | **43,042,717 ไบต์** |
| การตรวจสอบ | **byte-exact ทั้งสองฝั่ง** |
| md5 ของ xmodel | `69adf8bcd1276feeff6de220bcb39b3e` — **ตรงกับที่ compiler บันทึกไว้ใน `md5sum.txt`** |

ปลายทาง: `03-model/phase0-wsl-recovered/`
บวกกับ `results_fp32_final.json` → `05-benchmarks/gpu-baseline/`

### 2.5 บทเรียน

> **งานวิจัยที่ผลลัพธ์อยู่ในที่เดียว = ยังไม่มีผลลัพธ์**
>
> และการ verify ต้องทำที่ระดับ **checksum** ไม่ใช่แค่ดูว่าจำนวนไฟล์เท่ากัน
> เพราะไฟล์อาจโอนมาไม่ครบหรือเพี้ยนโดยไม่มีอาการ

### 2.6 หมายเหตุ

artifact เหล่านี้อยู่ใน `.gitignore` (เพราะเป็นไฟล์ binary ขนาดใหญ่: `*.xmodel`, `*.log`, `*.pt`)
→ มันจึงเป็น **สำเนากายภาพ** ไม่ใช่สิ่งที่ git track ไว้ ซึ่งต้องระวังเรื่องนี้ตอนย้ายเครื่อง

## ส่วนที่ 3 — วิกฤตที่ 2: ไฟล์ชื่อ `yolo26n_kv260.xmodel` แต่ข้างในเป็น YOLOv8n

### 3.1 จุดที่เอะใจ

ตอนตรวจ artifact ที่กู้มา บันทึกเดิมเขียนว่า **"Phase 0 ผ่านแล้วด้วย YOLO26n"**
และไฟล์ผลลัพธ์ชื่อ `yolo26n_kv260.xmodel` ซึ่งดูสอดคล้องกันดี

แต่มีสิ่งผิดสังเกต: สคริปต์ที่ใช้ quantize ชื่อ `quantize_yolo_pytorch.py`
ไม่ใช่ `quantize_yolo26n.py` ที่มีอยู่แยกต่างหาก

### 3.2 การตรวจสอบ: หาหลักฐานจาก 5 แหล่งอิสระ

หลักการคือ **อย่าตัดสินจากชื่อไฟล์** ให้ดูที่โครงสร้างจริงของโมเดล

| # | หลักฐาน | ค่าที่พบ | ตีความ |
|---|---|---|---|
| 1 | จำนวน output channel ของหัวโมเดล | **144 ch** | 144 = 4×16 (DFL) + 80 (COCO classes) = **หัวแบบ YOLOv8** |
| 2 | ถ้าเป็น yolo26n ต้องเป็นเท่าไร | 84 ch (reg_max=1, ตัด DFL ทิ้ง) | **ไม่ตรง** |
| 3 | `source range` ของ output node | ชี้ไปที่ `quantize_yolo_pytorch.py(162) forward` | สคริปต์ของ v8 ไม่ใช่ของ 26n |
| 4 | โครงหัวใน inspect report | `Detect[22] / cv2 / cv3` | โครง Detect head แบบ v8 คลาสสิก |
| 5 | ค่า default ของ `--weights` ในสคริปต์ | `yolov8n.pt` | น้ำหนักต้นทาง = v8n |

### 3.3 การอธิบายเลข channel (สำหรับผู้ฟังที่ไม่คุ้น)

YOLO output แต่ละตำแหน่งบน feature map จะมีตัวเลขหลายตัวต่อกัน:

```
YOLOv8 (80 คลาส):
┌──────────────────────────────┬────────────────┐
│  box: 4 ด้าน × 16 bin = 64   │  class: 80     │  = 144 channel
└──────────────────────────────┴────────────────┘

YOLO26n (ตัด DFL, reg_max=1):
┌──────────────┬────────────────┐
│  box: 4      │  class: 80     │  = 84 channel
└──────────────┴────────────────┘

โมเดลของเราตอนนี้ (YOLOv8, 1 คลาส "package"):
┌──────────────────────────────┬────────┐
│  box: 4 ด้าน × 16 bin = 64   │ cls: 1 │  = 65 channel
└──────────────────────────────┴────────┘
```

> **เลข channel เป็นเหมือนลายนิ้วมือของโมเดล** — บอกได้ทั้งว่าเป็นสถาปัตยกรรมไหน และมีกี่คลาส
> เราใช้เทคนิคนี้ซ้ำอีกครั้งตอน deploy โมเดลใหม่ขึ้นบอร์ด (เห็น 65 ch = ยืนยันว่าเป็นโมเดล 1 คลาสจริง)

### 3.4 ข้อสรุป

> **ไฟล์ตั้งชื่อผิด — สิ่งที่ผ่าน gate คือ YOLOv8n ไม่ใช่ YOLO26n**
> → **Track B ยังไม่เคยผ่าน gate เลย**

### 3.5 ความเสียหายที่ป้องกันได้

ถ้าไม่เจอตรงนี้ โครงงานจะ**รายงานผลผิดทั้งเล่ม** — อ้างว่า deploy YOLO26 สำเร็จทั้งที่ไม่จริง
ซึ่งเป็นความผิดพลาดระดับที่กระทบความน่าเชื่อถือของงานทั้งหมด

### 3.6 การแก้ไข

1. **เปลี่ยนชื่อ artifact ให้ตรงความจริง** — `yolo26n_kv260.xmodel` → `yolov8n_kv260_B4096.xmodel`
   ทำกับ**สำเนา** ไม่แตะ backup ต้นฉบับ เพื่อรักษาหลักฐานไว้
2. **แก้ field `filename` ใน `meta.json`** ให้สอดคล้อง
3. **เขียน `PROVENANCE.md`** กำกับ rename map + หลักฐานทั้ง 5 ข้อ เพื่อให้ตรวจสอบย้อนหลังได้
4. **verify md5 หลังเปลี่ยนชื่อ** — ยังเป็น `69adf8...` = เนื้อไฟล์ไม่เปลี่ยน

### 3.7 กับดักที่เกือบพลาด

มี pipeline สำหรับ yolo26n อยู่จริงในโปรเจค:
```
export_yolo26n_for_dpu.py → yolo26n_o2m_leakyrelu.onnx → quantize_yolo26n.py
```
และไฟล์ `yolo26n.pt` (md5 `cf3cca69...`) ก็มีอยู่จริง แยกจาก `yolov8n.pt` (md5 `03056081...`)

**แต่ pipeline นี้ยังไม่เคยผลิต xmodel ที่ผ่าน gate**
→ การมีสคริปต์และมีไฟล์น้ำหนักอยู่ **ไม่ได้แปลว่าเคยรันสำเร็จ**

### 3.8 บทเรียน

> **อย่าตัดสิน identity จากชื่อไฟล์หรือชื่อสคริปต์ — ให้ดู channel count และ source range เสมอ**
>
> และในงานที่ทำต่อเนื่องหลายเดือน บันทึกที่เขียนไว้เองก็อาจผิดได้
> การกลับไปตรวจหลักฐานดิบเป็นระยะจึงจำเป็น

## ส่วนที่ 4 — วิกฤตที่ 3: เอกสารระบุขนาด DPU ขัดกันเอง (B3136 vs B4096)

### 4.1 ปัญหา

| แหล่ง | ระบุ |
|---|---|
| สคริปต์ compile ของทั้งสอง track | `TARGET = DPUCZDX8G_ISA1_B3136` |
| เอกสาร handover / pre-staging | B4096 + fingerprint `0x101000056010407` |
| `platform_selection.docx` | B4096 |

### 4.2 ทำไมเรื่องนี้ร้ายแรง

**ถ้าเลือกผิด → ต้อง re-quantize + re-compile ใหม่ทั้ง Track A และ Track B**
และที่แย่กว่านั้นคือ ถ้าไม่รู้ตัวจนกระทั่งบอร์ดมาถึง จะเสียเวลาไปกับการ debug ที่หน้างาน

จึงจัดให้เป็นงาน **P1 — ต้องเคลียร์ก่อน compile รอบต่อไป**

### 4.3 การตรวจสอบ: หา 3 แหล่งที่เป็นหลักฐานจริง (ไม่ใช่ comment)

| แหล่ง | สิ่งที่พบ |
|---|---|
| `vai_c_xir_*.log` บรรทัดที่ 3 (**log จากการ compile จริง**) | `Target architecture: DPUCZDX8G_ISA1_B4096` |
| `meta.json` (**metadata ที่ฝังอยู่ใน xmodel**) | `"target": "DPUCZDX8G_ISA1_B4096"` |
| `arch.json` default ของ KV260 ใน Vitis AI 3.0 | B4096 |

**ทั้ง 3 แหล่งตรงกัน → arch จริงคือ B4096**

และ md5 ของ xmodel ตรงกับ `md5sum.txt` → ยืนยันว่า log/meta/xmodel เป็นชุดเดียวกัน ไม่ได้ปะปนจากคนละรอบ

### 4.4 แล้ว B3136 มาจากไหน

ตรวจแล้วพบว่า **ทุกจุดที่ปรากฏ B3136 เป็นข้อความ ไม่ใช่การ compile จริง:**

| ตำแหน่ง | ประเภท |
|---|---|
| `compile_yolo26n.sh:5` และ `:55` | comment ในโค้ด |
| `RUNBOOK_phase0.md:1` | ชื่อเรื่องในเอกสาร |
| `quantize_result/inspect_DPUCZDX8G_ISA1_B3136.txt` | **Inspector dry-run** — ลองยิงดูว่าเข้ากันได้ไหม ไม่ใช่ผล compile |

### 4.5 ข้อสรุป: ไม่ต้อง re-compile

ไฟล์ inspect ทั้งสอง arch เขียนตรงกันว่า:
```
All the operators are assigned to the DPU.
```
→ โมเดลรันได้ครบทั้งบน B3136 และ B4096 การเลือก B4096 (ซึ่งเป็น default ของบอร์ด) จึงไม่มีผลเสีย

> **ประหยัดเวลาไปหลายวัน** จากการตรวจหลักฐานแทนที่จะ re-compile เผื่อไว้

### 4.6 การแก้ไข
- แก้ `TARGET` ใน `track-b/quantize/quantize_yolo26n_pytorch.py` จาก B3136 → B4096 (2 จุด)
- เขียนบันทึกฉบับเต็ม: `07-notes/P1_arch_and_identity_resolution.md`

### 4.7 บทเรียน

> **แยกให้ออกระหว่าง "หลักฐานที่เครื่องมือสร้าง" กับ "ข้อความที่คนเขียน"**
>
> comment, ชื่อไฟล์, ชื่อเรื่องในเอกสาร = สิ่งที่คนพิมพ์ → ผิดได้ ล้าสมัยได้
> compile log, metadata, checksum = สิ่งที่เครื่องมือสร้าง → เชื่อถือได้มากกว่า
>
> เวลามีข้อมูลขัดกัน ให้เชื่อกลุ่มหลังเสมอ

## ส่วนที่ 5 — สิ่งที่ 3 วิกฤตนี้สอน

### 5.1 รูปแบบร่วมของทั้ง 3 เรื่อง

ทั้ง 3 เรื่องมีโครงสร้างเดียวกัน:

```
มีบันทึกที่บอกว่า "เรียบร้อยแล้ว"
        ↓
ไปตรวจหลักฐานดิบ
        ↓
พบว่าความจริงต่างจากบันทึก
        ↓
แก้ให้ตรงความจริง + เขียนบันทึกกำกับไว้
```

### 5.2 ทำไมส่วนนี้ควรเล่าให้อาจารย์ฟัง

ส่วนนี้ไม่ใช่ "ผลงาน" แต่เป็น **"วิธีคิด"** ซึ่งมักเป็นสิ่งที่อาจารย์ที่ปรึกษาอยากเห็นมากกว่า

- มันแสดงว่าเราไม่ได้แค่รันสคริปต์ตาม tutorial แล้วรายงานว่าผ่าน
- มันแสดงว่าเรารู้จักตั้งคำถามกับผลงานของตัวเอง
- มันแสดงว่าเราเข้าใจโครงสร้างของโมเดลลึกพอที่จะตรวจ identity จาก channel count ได้

### 5.3 ผลพลอยได้: กติกาที่ใช้ต่อทั้งโครงงาน

| กติกาที่เกิดจากวิกฤตนี้ | ถูกใช้ต่อที่ไหน |
|---|---|
| verify checksum ทุกครั้งที่โอนไฟล์ | ตอนโอน xmodel ขึ้นบอร์ด (ไฟล์ 06) |
| ตรวจ identity จาก channel count | ตอนยืนยันโมเดล 1 คลาสบนบอร์ด (เห็น 65 ch) |
| เชื่อ log ของเครื่องมือ ไม่เชื่อ comment | ตอนตัดสิน Track B (ต้อง compile จริง ไม่เชื่อ op histogram) |
| เก็บ backup ก่อนแก้ทุกครั้ง | ตอนแก้สคริปต์ quantize (เก็บเป็น `.regression.bak`) |
