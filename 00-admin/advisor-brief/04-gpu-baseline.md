# 04 — GPU Baseline: สร้างตัวเปรียบเทียบด้วยตัวเอง

> **สรุปไฟล์นี้ใน 3 บรรทัด**
> โครงงานนี้ต้องอ้างว่า "FPGA ดีกว่า GPU ในแง่พลังงาน" จึงต้องมีตัวเลข GPU ที่วัดเองด้วยเงื่อนไขเดียวกัน
> ไม่ใช่หยิบตัวเลขจากเปเปอร์คนอื่นมาเทียบ — เราวัด 3 โหมด (batch1 pure / end-to-end / batch sweep)
> ได้ผล 31.5 FPS @ 22.8 W (1.38 FPS/W) สำหรับโหมดที่ตรงกับงานจริง

---

## 1. ทำไมต้องวัด GPU baseline เอง

### 1.1 ปัญหาของการอ้างตัวเลขจากที่อื่น

ถ้าไปหยิบตัวเลข "YOLOv8n บน GPU ได้ X FPS" จากเปเปอร์หรือเว็บมาเทียบ จะโดนถามทันทีว่า:

| คำถาม | ทำไมตอบไม่ได้ |
|---|---|
| preprocessing เหมือนกันไหม | เขาอาจใช้ letterbox เราใช้ plain resize → ต้นทุนต่างกัน |
| นับ latency รวมอะไรบ้าง | เขาอาจนับแค่ forward pass ไม่รวมการโอนข้อมูล |
| วัดกำลังไฟยังไง | เขาอาจใช้ TDP บนกระดาษ ไม่ใช่ค่าที่วัดจริง |
| batch เท่าไร | ตัวเลขสวยๆ มักมาจาก batch ใหญ่ ซึ่งไม่ตรงกับงานจริง |
| warm up หรือยัง | รอบแรกๆ ช้ากว่าปกติมาก |

**สรุป: ตัวเลขที่วัดด้วยเงื่อนไขต่างกัน เอามาเทียบกันไม่ได้**

### 1.2 จังหวะที่ทำ

ทำ**ระหว่างรอบอร์ดมาถึง** — เป็นตัวอย่างของหลักการ "front-load งานที่ไม่ต้องใช้บอร์ด"
เพื่อให้เวลาที่มีบอร์ดจริงถูกใช้ไปกับ deploy และ debug เท่านั้น

### 2.1 สเปคที่ใช้

### 2.2 หลักการที่ยึด: แยก environment ให้ขาดจากกัน

```
conda gpubench (Python 3.12)     Vitis AI container (Python 3.7)
   ├─ torch 2.11.0+cu128            ├─ torch 1.12.1
   ├─ ultralytics 8.4.75            ├─ pytorch_nndct
   └─ pynvml                        └─ ultralytics 8.0.151
   → ใช้วัด GPU เท่านั้น            → ใช้ quantize/compile เท่านั้น
```

ถ้าปนกันจะเกิดปัญหาแบบที่เจอในบั๊กที่ 4 ข้างล่าง

### 2.3 บทเรียนสำคัญจากขั้นตอนนี้

> **"ลงสำเร็จ ≠ ได้ของที่ต้องการ"**
>
> `pip install torch` ผ่านโดยไม่มี error แต่ `torch.cuda.is_available()` คืนค่า `False`
> เพราะ Python 3.14 (default ของ Ubuntu 25.10) ใหม่เกินไป PyTorch ยังไม่ build CUDA wheel สำหรับ cp314
> → ได้ **CPU build** มาแทน ซึ่งจะทำให้วัดผลผิดทั้งหมดโดยไม่รู้ตัว
>
> **gate ที่ตั้ง:** ต้องเห็น `torch.cuda.is_available() = True` และเห็นชื่อ GPU ถูกต้อง จึงจะถือว่า env พร้อม

## 3. วิธีการวัด (Methodology)

### 3.1 หลักการออกแบบสคริปต์ `gpu_baseline.py`

| หลักการ | การนำไปใช้ |
|---|---|
| **ใช้โมเดลเดียวกัน** | โหลด `yolov8n.pt` ตัวเดียวกับที่ใช้ใน Phase 0 |
| **preprocessing ตรงกันเป๊ะ** | plain resize 640 → BGR→RGB → /255 → CHW (เหมือนฝั่ง FPGA ทุกขั้น) |
| **แยกวัดหลายโหมด** | เพื่อไม่ให้ตัวเลขเดียวถูกตีความเกินจริง |
| **กัน outlier** | median-of-medians จาก 5 runs × 200 iterations |
| **มี warm up** | ตัดรอบแรกๆ ที่ยังไม่เข้าที่ออก |
| **กัน OOM** | มี guard ใน batch sweep — ถ้า VRAM เต็มให้หยุดเอง ไม่ crash |
| **บันทึกข้อมูลดิบ** | `--save` เขียนผลลง JSON เพื่อให้ตรวจย้อนหลังได้ |

### 3.2 ทำไมต้อง median-of-medians

GTX 1660 Ti **Max-Q** เป็นรุ่นสำหรับโน้ตบุ๊ก ซึ่งมีพฤติกรรม **thermal throttle** — พอร้อนจะลดความเร็วลง
ถ้าวัดครั้งเดียวแล้วบังเอิญเจอช่วง throttle จะได้ตัวเลขที่ต่ำเกินจริง

```
run 1: [199 ค่า] → หา median → m1
run 2: [199 ค่า] → หา median → m2
run 3: [199 ค่า] → หา median → m3      →  median(m1..m5) = ค่าที่รายงาน
run 4: [199 ค่า] → หา median → m4
run 5: [199 ค่า] → หา median → m5
```

**ผลที่สังเกตได้:** โหมด batch=1 มี spread ±6 FPS (ไม่นิ่ง เพราะ throttle)
ส่วนโหมด batch=32 นิ่งมาก (util 96% ตลอด) → เป็นข้อมูลที่ควรรายงานพร้อมตัวเลขหลัก

### 3.3 สามโหมดที่วัด และเหตุผล

| โหมด | วัดอะไร | ทำไมต้องมี |
|---|---|---|
| **PURE GPU** (batch=1) | เฉพาะ forward pass บน GPU | เทียบกับ "DPU-only" ของฝั่ง FPGA ได้ตรงๆ |
| **END-TO-END** (batch=1) | รวม preprocessing + การโอนข้อมูล Host→Device | เป็นสิ่งที่ผู้ใช้เห็นจริง |
| **BATCH SWEEP** | ลอง batch 1, 4, 8, 16, 32, 64 | หาจุดที่ GPU ทำได้ดีที่สุด = ให้ความเป็นธรรมกับ GPU |

> **จุดสำคัญเชิงจริยธรรมการวิจัย:** การวัด batch sweep คือการ**เปิดโอกาสให้ GPU แสดงศักยภาพสูงสุด**
> ถ้าเราวัดแค่ batch=1 แล้วบอกว่า FPGA ชนะ จะเป็นการเลือกเงื่อนไขที่เข้าข้างตัวเอง

## 4. ผลการวัด

### 4.1 ผลหลัก (FP32, imgsz 640)

| โหมด | throughput | latency | power | ประสิทธิภาพ | หมายเหตุ |
|---|---|---|---|---|---|
| **Pure GPU** (batch=1) | **31.46 FPS** | 31.79 ms | 22.80 W | **1.38 FPS/W** | spread ±6 FPS |
| **End-to-end** (batch=1) | **25.53 FPS** | 39.17 ms | 22.65 W | **1.13 FPS/W** | รวม pre/post |
| **Peak** (batch=32) | **263.9 img/s** | 121.28 ms/batch | 58.46 W | **4.51 img/s/W** | util 96% นิ่ง |

### 4.2 ตาราง batch sweep ฉบับเต็ม

| batch | latency (ms) | throughput รวม (FPS) | power (W) | GPU util | FPS/W |
|---|---|---|---|---|---|
| 1 | 38.95 | 25.7 | 21.19 | **33%** | 1.21 |
| 4 | 36.86 | 108.5 | 43.92 | 33% | 2.47 |
| 8 | 33.46 | 239.1 | 57.54 | 61% | 4.16 |
| 16 | 61.76 | 259.1 | 57.52 | 83% | 4.50 |
| **32** | 121.28 | **263.9** | 58.46 | **96%** | **4.51** |
| 64 | 242.54 | 263.9 | 58.66 | 98% | 4.50 |

### 4.3 การอ่านตารางนี้ (สำคัญ)

**สังเกต 3 อย่าง:**

**1. throughput อิ่มตัวที่ batch 32**
batch 64 ได้ throughput เท่าเดิม (263.9) แต่ latency เพิ่มเป็น 2 เท่า
→ แปลว่า GPU ทำงานเต็มที่แล้วที่ batch 32 เพิ่มไปก็แค่รอคิว

**2. ที่ batch=1 GPU ใช้กำลังตัวเองได้แค่ 33%**
```
batch 1  →  util 33%,  21.19 W  →  1.21 FPS/W
batch 32 →  util 96%,  58.46 W  →  4.51 FPS/W
                                    ↑ ดีกว่า 3.7 เท่า
```
> **นี่คือหลักฐานเชิงตัวเลขของประเด็นในไฟล์ 01** ว่างาน edge (batch=1) เป็นสถานการณ์ที่ GPU เสียเปรียบ
> — ไม่ใช่เพราะ GPU ไม่ดี แต่เพราะสถาปัตยกรรมมันออกแบบมาเพื่ออย่างอื่น

**3. latency ต่อภาพแย่ลงเมื่อ batch ใหญ่**
batch 32 ใช้เวลา 121 ms ต่อ 1 batch → ภาพแรกในชุดต้องรอ 121 ms กว่าจะได้ผล
ในขณะที่ batch 1 ใช้ 39 ms
→ **งานเรียลไทม์เลือก batch ใหญ่ไม่ได้** เพราะจะเกิด latency ที่ผู้ใช้รู้สึกได้

### 4.4 การแปลงเป็นพลังงานต่อภาพ (มุมมองอีกแบบ)

| โหมด | พลังงานต่อภาพ |
|---|---|
| GPU pure (batch 1) | 22.80 W ÷ 31.46 FPS = **0.725 J/ภาพ** |
| GPU e2e (batch 1) | 22.65 ÷ 25.53 = **0.887 J/ภาพ** |
| GPU peak (batch 32) | 58.46 ÷ 263.9 = **0.222 J/ภาพ** |

*(ตัวเลขนี้จะถูกนำไปเทียบกับฝั่ง FPGA ในไฟล์ 07)*

## 5. บั๊กที่เจอระหว่างทำ (และวิธีแก้)

### บั๊กที่ 1 — Python 3.14 ไม่มี CUDA wheel

| ประเด็น | รายละเอียด |
|---|---|
| **อาการ** | ลง torch สำเร็จ แต่ `cuda.is_available() = False` |
| **สาเหตุ** | Python 3.14 (default ของ Ubuntu 25.10 "resolute") ใหม่เกินไป PyTorch ยังไม่ build CUDA wheel สำหรับ cp314 → pip ให้ CPU build มาแทน |
| **วิธีที่ลองแล้วไม่ได้ผล** | `apt install python3.12` (ไม่มีใน repo ของ resolute) · deadsnakes PPA (ไม่ publish repo สำหรับ resolute) |
| **วิธีแก้** | ใช้ **miniforge** สร้าง env Python 3.12 — ได้ binary สำเร็จรูป ไม่ต้องคอมไพล์ ไม่แตะ system Python |
| **บทเรียน** | verify ที่**ผลลัพธ์** ไม่ใช่ที่ exit code |

### บั๊กที่ 2 — `/tmp` เต็ม ทั้งที่ดิสก์เหลือ 954 GB

| ประเด็น | รายละเอียด |
|---|---|
| **อาการ** | `pip install torch` → `[Errno 28] No space left on device` |
| **สาเหตุ** | `/tmp` เป็น **tmpfs (อยู่ใน RAM)** จำกัด 1.4 GB · pip ใช้เป็นที่แตกไฟล์ torch ก้อนใหญ่ |
| **วิธีแก้** | `TMPDIR=~/thesis/gpu_baseline/piptmp pip install --no-cache-dir ...` |
| **บทเรียน** | **ดิสก์เหลือ ≠ ทุก mount เหลือ** — ต้องเช็ค `df -h /tmp` แยกต่างหาก |

### บั๊กที่ 3 — WSL filesystem พัง (รุนแรงที่สุด)

รายละเอียดอยู่ในไฟล์ [03-foundation-and-crises.md](03-foundation-and-crises.md) ส่วนที่ 2
สรุปคือ C: เหลือ 1.22 GB → `.vhdx` ขยายไม่ได้ → filesystem remount read-only → คำสั่งพื้นฐาน segfault
แก้ด้วย `wsl --shutdown` + เคลียร์ C: ให้เหลือ > 12 GB

> **บทเรียนเฉพาะทาง:** `df` ใน WSL **โกหก** — มันโชว์ค่า provision (1007 GB)
> ไม่ใช่พื้นที่จริงของ Windows host ที่ `.vhdx` วางอยู่

### บั๊กที่ 4 — ultralytics ลาก torch CPU มาทับ

| ประเด็น | รายละเอียด |
|---|---|
| **ความเสี่ยง** | `pip install ultralytics` จะ resolve torch dependency เอง อาจดึง CPU build มาทับ +cu128 ที่อุตส่าห์ลงไว้ |
| **วิธีป้องกัน** | ลง torch ก่อน แล้ว `pip install ultralytics --no-deps` + ลง dependency ที่เหลือเองแบบเลือกตัว |
| **การยืนยัน** | หลังลงเสร็จ เช็ค `torch.__version__` ยังเป็น `+cu128` ✅ |

### บั๊กที่ 5 — สคริปต์พังเพราะแก้ไฟล์ผิดพลาด

| ประเด็น | รายละเอียด |
|---|---|
| **อาการ** | `NameError: name 'summarize' is not defined` |
| **สาเหตุ** | ตอนแทรกฟังก์ชันใหม่ หัว `def summarize(...)` ถูกลบไปด้วยโดยไม่ตั้งใจ |
| **วิธีแก้ + กติกาใหม่** | เติมกลับ + ตั้งกฎว่าต้อง `grep -c "^def "` ทุกครั้งหลังแก้ไฟล์ |
| **บทเรียน** | **verify ก่อนเคลม** — เป็นกติกาเดียวกับที่ใช้ตรวจ artifact ในไฟล์ 03 |

## 7. ข้อจำกัดที่ต้องรายงานอย่างตรงไปตรงมา

| ข้อจำกัด | ผลกระทบ | เราจัดการอย่างไร |
|---|---|---|
| GPU วัดกำลังไฟ**เฉพาะชิป** (nvidia-smi) | ไม่รวม CPU/RAM/PSU ของเครื่อง | ระบุชัดในตาราง — และนี่**เข้าข้าง GPU** เพราะ FPGA วัดทั้งบอร์ด |
| GPU เป็น **FP32** ส่วน FPGA เป็น **INT8** | ไม่ใช่ precision เดียวกัน | ปิดด้วยตัวเลข mAP drop 1.5% (ไฟล์ 07 ตารางที่ 2) |
| GPU เป็นรุ่น **Max-Q** (โน้ตบุ๊ก) | มี thermal throttle | ใช้ median-of-medians + รายงาน spread |
| ต่างยุคกัน | GTX 1660 Ti (2019) vs KV260 (2021) | เป็นข้อจำกัดที่ต้องระบุ — เทียบเชิงสถาปัตยกรรมได้ แต่ไม่ใช่การเทียบรุ่นต่อรุ่น |

> **หลักการที่ยึด:** รายงาน caveat ทุกข้อเอง ก่อนที่จะโดนถาม
> เพราะการเทียบที่ซื่อสัตย์แล้วยังชนะ มีน้ำหนักกว่าการเทียบที่เลือกเงื่อนไขเข้าข้างตัวเอง
