## ตารางที่ 2 — ความแม่นยำ: float vs INT8 ⭐

### 2.1 วิธีวัด

| รายการ | ค่า |
|---|---|
| ชุดข้อมูล | valid set **57 ภาพ**, **289 กล่อง ground truth** |
| pipeline | **เหมือนกันทั้งสองฝั่ง** — plain resize 640 → DFL decode → NMS |
| conf threshold | 0.001 (ต่ำมาก เพื่อให้ได้ curve ที่สมบูรณ์สำหรับคำนวณ mAP) |
| IoU threshold (NMS) | 0.7 |
| float รันที่ | host (`infer_float.py`) |
| INT8 รันที่ | **บอร์ดจริง** (`infer_dump.py`) |

> **จุดสำคัญของการออกแบบ:** ใช้ pipeline เดียวกันเป๊ะทั้งสองฝั่ง
> → ความต่างที่เห็นจึงมาจาก **quantization ล้วนๆ** ไม่ปนกับความต่างของ preprocessing หรือ decode

### 2.2 ผลลัพธ์

| Metric | Float (host) | INT8 (KV260) | Δ (drop) |
|---|---|---|---|
| **mAP@0.50** | 0.8846 | **0.8713** | **−0.0133 (−1.5%)** |
| mAP@0.50:0.95 | 0.6879 | 0.6795 | −0.0084 (−1.2%) |
| Precision @0.25 | 0.8007 | 0.8225 | **+0.0218** |
| Recall @0.25 | 0.8478 | 0.8339 | −0.0139 |
| F1 @0.25 | 0.8235 | 0.8282 | **+0.0047** |

### 2.3 การตีความ

**1. ความแม่นยำถูกรักษาไว้เกือบสมบูรณ์**
mAP@0.5 ลดเพียง **1.3 จุด (1.5% เชิงสัมพัทธ์)** จากการบีบข้อมูลจาก 32 บิตเหลือ 8 บิต

**2. F1 แทบไม่เปลี่ยน — และนี่สำคัญกว่า mAP ในบริบทของงานนับ**
```
F1: 0.8235 → 0.8282  (ดีขึ้นเล็กน้อยด้วยซ้ำ)
```
สาเหตุ: Precision ขึ้น (+0.022) ในขณะที่ Recall ลง (−0.014)
→ INT8 model **ระมัดระวังขึ้นเล็กน้อย** (ทายน้อยลงแต่ถูกมากขึ้น)
→ สำหรับงานนับ การมี false positive น้อยลงเป็นเรื่องดี

**3. การ cross-check ที่สำคัญที่สุด**
```
float mAP@0.5 ที่เราวัดเอง     = 0.8846
mAP ที่ validate มาตรฐานบน Colab = 0.884
                                  ↑ ตรงกัน
```
> **นี่คือหลักฐานว่า pipeline การวัดผลที่เขียนเองถูกต้อง**
> ถ้าเลขนี้ไม่ตรง จะแปลว่าเราวัดผิดที่ไหนสักแห่ง แล้วตัวเลข INT8 ก็จะเชื่อไม่ได้ด้วย
>
> การมีจุด cross-check แบบนี้เป็นสิ่งที่ควรมีในทุกการทดลอง

### 2.4 บั๊กที่เจอระหว่างทำหมวดนี้

**ground truth จาก Roboflow เป็น polygon segmentation ไม่ใช่ bounding box**

```
ที่คาดไว้:   class x_center y_center width height      (5 ตัวเลข)
ที่ได้จริง:  class x1 y1 x2 y2 x3 y3 ... xn yn        (polygon หลายจุด)
```

→ ตอนแรกคำนวณ mAP ออกมาผิดทั้งหมด
→ ต้องเขียนโค้ดแปลง polygon → bbox (หา min/max ของทุกจุด) ก่อนคำนวณ

> **บทเรียน:** ต้องเข้าใจ format ของ ground truth ก่อนวัดผล
> ไม่ใช่สมมติว่ามันเป็นรูปแบบมาตรฐาน

## ตารางที่ 3 — Latency breakdown ⭐ (ข้อค้นพบสำคัญที่สุด)

### 3.1 วิธีวัด

| รายการ | ค่า |
|---|---|
| จำนวนรอบ | 100 iterations |
| warm up | 10 รอบแรก (ตัดทิ้ง ไม่นับ) |
| threads | 1 |
| สิ่งที่รายงาน | mean, median, std |

### 3.2 ผลลัพธ์

| Stage | mean (ms) | median (ms) | std | สัดส่วน |
|---|---|---|---|---|
| **Preprocess** (resize/convert/quantize บน PS) | **49.75** | 49.54 | 1.00 | **63%** |
| **DPU inference** | **12.49** | 12.49 | **0.04** | **16%** |
| **Decode + NMS** (DFL/sigmoid/NMS บน PS) | **16.07** | 16.14 | 0.16 | **21%** |
| **รวม end-to-end** | **78.31** | 78.12 | 1.04 | 100% |

### 3.3 การอ่านตัวเลข

**throughput ที่คำนวณได้:**
```
DPU-only    : 1000 / 12.49 = 80.1 FPS
end-to-end  : 1000 / 78.31 = 12.77 FPS
```

**การตรวจสอบความถูกต้อง (cross-check):**
```
DPU-only ที่คำนวณจาก latency = 80.1 FPS
xdputil benchmark              = 82.5 FPS
                                 ↑ ใกล้เคียงกัน (ต่าง 3%)
```
→ ยืนยันว่าการวัด latency ถูกต้อง (ความต่างเล็กน้อยมาจาก overhead ของการวัดเอง)

**ความเสถียร:**
```
DPU std = 0.04 ms   ← เสถียรมาก (ฮาร์ดแวร์เฉพาะทาง ทำงานเท่ากันทุกรอบ)
PS  std = 1.00 ms   ← แกว่งกว่า (มี OS scheduling, cache miss)
```
→ เป็นหลักฐานเชิงคุณภาพว่า **ฮาร์ดแวร์เฉพาะทางให้ latency ที่คาดเดาได้**
ซึ่งเป็นคุณสมบัติที่สำคัญมากสำหรับงาน real-time

### 3.4 ข้อค้นพบ ⭐

> ### DPU ใช้เวลาเพียง 16% ของ pipeline
> ### คอขวดจริงคือ preprocessing บน ARM PS (63%)
> ### **ระบบเป็น PS-bound ไม่ใช่ DPU-bound**

**ทำไมข้อค้นพบนี้มีค่ากว่าตัวเลข FPS:**

งานวิจัยจำนวนมากรายงานแค่ "accelerator ทำได้ X FPS" ซึ่งเป็นตัวเลขที่สวยแต่ไม่ตรงกับที่ผู้ใช้เห็น
การวัดแยกรายสเตจทำให้เห็นว่า **การซื้อ accelerator ที่แรงขึ้นจะไม่ช่วยอะไร**

```
สมมติเปลี่ยนไปใช้ DPU ที่เร็วขึ้น 2 เท่า:
   preproc 49.75 + DPU 6.25 + decode 16.07 = 72.07 ms → 13.9 FPS
   (จาก 12.77 → 13.9 = ดีขึ้นแค่ 8.8%)

สมมติ optimize preprocessing ให้เหลือ 10 ms:
   preproc 10.00 + DPU 12.49 + decode 16.07 = 38.56 ms → 25.9 FPS
   (จาก 12.77 → 25.9 = ดีขึ้น 103%)
```

> **ทิศทางงานต่อยอดจึงชัดเจน:** ไป optimize preprocessing
> (vectorize, เขียนเป็น C++, หรือใช้ hardware scaler ใน PL)
> ไม่ใช่ไปหา accelerator ที่แรงขึ้น

### 3.5 ทำไม preprocessing ถึงช้า

preprocessing ทำ 4 อย่าง: resize → BGR→RGB → หาร 255 → quantize
ทั้งหมดเป็นการวนลูปบนอาร์เรย์ขนาด 640×640×3 = **1,228,800 ค่า**

บน ARM Cortex-A53 ที่ทำงานผ่าน Python + OpenCV → ทำทีละค่าโดยไม่ได้ใช้ SIMD เต็มที่
ในขณะที่ DPU ทำ convolution 8.10 GOP ในเวลาน้อยกว่า เพราะมีวงจรที่ออกแบบมาเฉพาะ

## ตารางที่ 4 — กำลังไฟและประสิทธิภาพพลังงาน

### 4.1 วิธีวัด

| รายการ | ค่า |
|---|---|
| เซนเซอร์ | **INA260** (`ina260_u14`) — เซนเซอร์วัดกระแส/แรงดันบนบอร์ดจริง |
| จุดวัด | ราง SOM (System-on-Module) = **ทั้งโมดูล** |
| วิธีอ่าน | อ่านค่าจาก sysfs ระหว่างที่งานกำลังรัน |

> **หมายเหตุที่สำคัญต่อความเป็นธรรมของการเทียบ:**
> INA260 วัด **ทั้ง SOM** = รวม ARM CPU + DPU + DDR + regulator ทั้งหมด
> ในขณะที่ nvidia-smi ของ GPU วัด **เฉพาะชิป GPU** ไม่รวม CPU/RAM/PSU ของเครื่อง
> → **การเทียบนี้เข้าข้าง GPU** และ FPGA ยังชนะอยู่

### 4.2 ผลลัพธ์ 3 สภาวะ

| สภาวะ | Power avg (W) | Power peak (W) | Throughput (FPS) | Efficiency (FPS/W) |
|---|---|---|---|---|
| **Idle** | 4.85 | — | — | — |
| **DPU-saturated** (benchmark 4 threads) | **9.27** | 9.90 | **89.6** | **9.67** |
| **Real application** (video counting) | **5.10** | 5.45 | 10.15 | 1.99 |

**ค่าที่คำนวณต่อได้:**
```
dynamic power (load − idle) = 9.27 − 4.85 = 4.42 W
efficiency แบบ dynamic      = 89.6 / 4.42 = 20.3 FPS/W
พลังงานต่อภาพ (DPU-sat)     = 9.27 / 89.6 = 0.1035 J/ภาพ
พลังงานต่อภาพ (real-app)    = 5.10 / 10.15 = 0.502 J/ภาพ
```

### 4.3 ข้อค้นพบ ⭐ — หลักฐานชิ้นที่สองว่าระบบ PS-bound

> ### ตอนรันแอปนับกล่องจริง กำลังไฟเฉลี่ยเกาะ idle — เพิ่มขึ้นแค่ **+0.25 W**

```
idle              = 4.85 W
real application  = 5.10 W
                    ────────
ต่างกัน            =  0.25 W  ← น้อยมาก
```

**ทำไมถึงเป็นแบบนี้:**
```
ต่อ 1 เฟรม:  DPU ทำงาน 12.5 ms  แล้ว "ว่าง" ไป 65.8 ms รอ preprocess
              → DPU ทำงานจริงแค่ 16% ของเวลา → ไม่กินไฟ
```

> **นี่คือหลักฐานอิสระชิ้นที่ 2 ที่ยืนยันข้อค้นพบเดียวกันกับตารางที่ 3**
> โดยวัดคนละวิธี (วัดกำลังไฟ vs วัดเวลา) แต่ให้ข้อสรุปเดียวกัน
>
> **การมีหลักฐาน 2 ชิ้นจากวิธีที่ต่างกันสนับสนุนข้อสรุปเดียวกัน = ข้อสรุปที่แข็งแรง**

### 4.4 ทำไมต้องรายงาน 2 จุดปฏิบัติการ

| จุดปฏิบัติการ | ตัวเลข | บอกอะไร |
|---|---|---|
| **DPU-saturated** | 89.6 FPS @ 9.27 W = 9.67 FPS/W | **ศักยภาพสูงสุดของ accelerator** — ถ้าเลี้ยงข้อมูลทัน จะได้เท่านี้ |
| **Real application** | 10.15 FPS @ 5.10 W = 1.99 FPS/W | **จุดที่ใช้งานจริงตอนนี้** — ถูกจำกัดด้วย preprocessing |

> **ถ้ารายงานแค่ตัวเลขเดียวจะบิดเบือน:**
> - รายงานแค่ 9.67 → เกินจริง เพราะระบบจริงยังทำไม่ได้
> - รายงานแค่ 1.99 → ต่ำเกินจริง เพราะไม่ได้สะท้อนศักยภาพของฮาร์ดแวร์
>
> **การรายงานทั้งสองพร้อมกัน + อธิบายว่าอะไรกั้นอยู่ = การรายงานที่ซื่อสัตย์และมีประโยชน์ที่สุด**

**และมันชี้ทางต่อยอด:** DPU มี headroom เหลืออีก 79 FPS → optimize preproc จะได้ FPS เพิ่มโดย**power แทบไม่ขึ้น**

## ตารางที่ 5 — เปรียบเทียบ GPU (FP32) vs KV260 FPGA (INT8) ⭐

### 5.1 ตารางเปรียบเทียบ

| ระบบ | Precision | FPS | Power (W) | FPS/W | ขอบเขตการวัด power |
|---|---|---|---|---|---|
| GPU pure (batch 1) | FP32 | 31.5 | 22.80 | 1.38 | เฉพาะชิป GPU |
| GPU e2e (batch 1) | FP32 | 25.5 | 22.65 | 1.13 | เฉพาะชิป GPU |
| GPU peak (batch 32) | FP32 | **263.9** | 58.46 | 4.51 | เฉพาะชิป GPU |
| **KV260 DPU-sat** (4 thr) | INT8 | 89.6 | **9.27** | **9.67** | **ทั้งบอร์ด SOM** |
| **KV260 real-app** (video) | INT8 | 10.15 | **5.10** | 1.99 | **ทั้งบอร์ด SOM** |

### 5.2 ข้อสรุป 5 มุม (รายงานอย่างซื่อสัตย์)

**มุมที่ 1 — ประสิทธิภาพพลังงาน ดีสุด-ต่อ-ดีสุด**
```
FPGA 9.67 FPS/W  vs  GPU 4.51 FPS/W  →  FPGA ดีกว่า 2.1×
```
และ FPGA ยังเสียเปรียบในการวัด (วัดทั้งบอร์ด vs วัดแค่ชิป)

**มุมที่ 2 — กำลังไฟสัมบูรณ์** ← จุดขายหลักของ edge
```
FPGA 9.27 W  vs  GPU peak 58.5 W  →  น้อยกว่า 6.3×
```

**มุมที่ 3 — เทียบแบบแฟร์ที่สุด (end-to-end ทั้งคู่)**
```
FPGA real-app 1.99  vs  GPU e2e 1.13 FPS/W  →  ดีกว่า 1.8×
กำลังไฟ 5.10 W      vs  22.65 W             →  น้อยกว่า 4.4×
```

**มุมที่ 4 — พลังงานต่อภาพ**
| ระบบ | J/ภาพ |
|---|---|
| GPU peak | 0.222 |
| **KV260 DPU-sat** | **0.104** ← ดีกว่า 2.1× |
| GPU e2e | 0.887 |
| **KV260 real-app** | **0.502** ← ดีกว่า 1.8× |

**มุมที่ 5 — สิ่งที่แลกไป (ต้องรายงาน)**
```
throughput ดิบ: GPU 263.9 FPS  vs  FPGA 89.6 FPS  →  GPU ชนะ 2.9×
```
→ **FPGA แลกความเร็วดิบกับพลังงาน ขนาด และต้นทุน**
ซึ่งเป็น trade-off ที่ถูกต้องสำหรับงาน edge แต่ไม่ถูกต้องสำหรับงาน datacenter

### 5.3 การปิด caveat "FP32 vs INT8"

> **คำถามที่จะโดนถามแน่นอน:** "เทียบ INT8 กับ FP32 ยุติธรรมไหม"
>
> **คำตอบที่มีตัวเลขรองรับ:** ต้นทุนของ INT8 คือ mAP ลดแค่ **1.5%** (ตารางที่ 2)
> ในขณะที่ได้ประหยัดไฟ **6.3 เท่า**
>
> → การแลกนี้คุ้มค่าอย่างชัดเจนสำหรับงาน edge และเป็นเหตุผลที่ INT8 เป็นมาตรฐานของ edge inference

### 5.4 ข้อจำกัดที่ต้องรายงานเอง

| ข้อจำกัด | ทำไมต้องพูด |
|---|---|
| GPU วัดเฉพาะชิป / FPGA วัดทั้งบอร์ด | เข้าข้าง GPU — แต่ต้องบอกให้ชัดว่าตัวเลขไม่ใช่ขอบเขตเดียวกัน |
| GPU FP32 / FPGA INT8 | ปิดด้วยตัวเลข mAP drop |
| GPU เป็นรุ่นโน้ตบุ๊ก (Max-Q) มี throttle | ใช้ median-of-medians + รายงาน spread ±6 FPS |
| ต่างยุคกัน (2019 vs 2021) | เป็นการเทียบเชิงสถาปัตยกรรม ไม่ใช่การเทียบรุ่นต่อรุ่น |

## ตารางที่ 6 — งานนับกล่อง เทียบ Ground Truth ⭐ (โจทย์หลักของโครงงาน)

### 6.1 วิธีการ

```
ขั้น 1: DPU ทำ detection ทุกเฟรม
        → ได้กล่อง + คะแนน ต่อเฟรม

ขั้น 2: centroid tracker (greedy matching)
        → จับคู่กล่องในเฟรมนี้กับ track ที่มีอยู่ ด้วยระยะจุดศูนย์กลาง
        → ถ้าระยะ < max_dist → ถือว่าเป็นวัตถุเดียวกัน (ID เดิม)
        → ถ้าไม่มีคู่ → สร้าง track ใหม่

ขั้น 3: line-crossing
        → ถ้า track ข้ามเส้นที่กำหนด "ครั้งแรก" → count += 1
        → (ครั้งแรกเท่านั้น กันการนับซ้ำถ้าวัตถุแกว่งไปมารอบเส้น)
```

### 6.2 เทคนิคสำคัญ: แยกการ detect ออกจากการ tune

**ปัญหา:** การรันวิดีโอ 600 วินาที (18,000 เฟรม) บนบอร์ดที่ประมวลผลได้ ~10 FPS
ใช้เวลา **~30 นาทีต่อรอบ** → ถ้าอยากลองค่าพารามิเตอร์ 20 แบบ = 10 ชั่วโมง

**วิธีแก้ที่ใช้:**
```
รันบนบอร์ด "ครั้งเดียว"                     รัน sweep บน host "ไม่จำกัดรอบ"
┌──────────────────────────┐              ┌─────────────────────────────┐
│ video_dump_dets.py       │              │ count_offline.py --sweep    │
│ dump กล่องทุกเฟรม        │──dets600─────►│ ลอง axis/line/max_dist      │
│ → dets600.json (6.3 MB)  │   .json      │ ทุกชุดค่า ในไม่กี่วินาที     │
│ 174,769 กล่อง            │              └─────────────────────────────┘
│ ใช้เวลา 30 นาที           │
└──────────────────────────┘
```

> **ผลลัพธ์:** ประหยัดเวลาไปหลายชั่วโมง และที่สำคัญกว่านั้น —
> ทำให้ทำ **sensitivity analysis** ได้ ซึ่งกลายเป็นข้อมูลที่มีค่าที่สุดในตารางนี้
> (ถ้าไม่ทำแบบนี้ คงได้แค่ตัวเลขเดียวโดยไม่รู้ว่ามัน robust หรือเปล่า)

### 6.3 ผลลัพธ์

**Ground truth = 215 กล่อง** (คลิป 600 วินาที, 18,000 เฟรม @30fps, นับด้วยมือ)

| Config เส้นนับ | นับได้ | Error |
|---|---|---|
| **calibrated: แกน x, เส้นที่ 0.40·W, max_dist=60** | **215** | **0.0%** |
| แกน x, เส้น 0.30·W, max_dist=60 | 219 | 1.9% |
| แกน x, เส้น 0.30·W, max_dist=40 | 209 | 2.8% |
| แกน x, เส้น 0.40·W, max_dist=90 | 224 | 4.2% |
| **ไม่ calibrate (เส้นกลางจอ 0.5)** | 270–331 | **25–54%** |
| แกน y (ทุก config) | — | 20–92% |

### 6.4 การวิเคราะห์ (ไม่ใช่แค่รายงานว่า 100%)

**ข้อ 1 — แกนต้องเป็น x**
```
กล่องเคลื่อนที่แนวนอนบนสายพาน  →  แกน x ถูกต้อง
แกน y ผิดหมด (error 20–92%)   →  เพราะกล่องแทบไม่เคลื่อนในแนวตั้ง
                                   → ไม่มีการ "ข้ามเส้น" ที่มีความหมาย
```
→ ผลนี้**ยืนยันว่าระบบเข้าใจการเคลื่อนที่ของวัตถุถูกต้อง** ไม่ใช่แค่ได้เลขบังเอิญ

**ข้อ 2 — ตำแหน่งเส้นต้องอยู่โซนที่กล่องเพิ่งเข้าเฟรม (x ≈ 0.3–0.4)**

```
       ซ้าย                                              ขวา
       │                                                  │
       │◄─── กล่องเพิ่งเข้าเฟรม ──►│◄── กล่องหนาแน่น ──►│
       │      ยังไม่ทับกัน          │      ซ้อนทับกัน      │
       │                             │                     │
       0.0        0.3   0.4         0.5                  1.0
                   ▲     ▲            ▲
                   │     │            │
              ดีที่สุด  ดีที่สุด   นับเกิน 25–54%
```

**ทำไมเส้นกลางจอถึงนับเกิน:**
```
บริเวณกลางภาพ กล่องหนาแน่น/ซ้อนทับกัน
      ↓
detection กระพริบ (เฟรมนี้เจอ เฟรมหน้าไม่เจอ เพราะโดนบัง)
      ↓
tracker จับคู่ไม่ได้ → track เดิมตาย → สร้าง track ใหม่
      ↓
track ใหม่ข้ามเส้นอีกครั้ง → นับซ้ำ
      ↓
นับได้ 270–331 แทนที่จะเป็น 215
```

**ข้อ 3 — ผลไม่ใช่ความบังเอิญ (sensitivity analysis)**

```
บริเวณรอบค่าที่เลือก:
   เส้น 0.30–0.40 × max_dist 40–60  →  นับได้ 209–219  →  error < 3% ทั้งย่าน
                                          ▲
                              ไม่ใช่แหลมเดียวที่บังเอิญตรง
```

> **นี่คือคำตอบสำหรับคำถาม "จูนจนพอดีหรือเปล่า"**
> ถ้าเป็นการจูนจนพอดี ผลจะดีเฉพาะจุดเดียวและแย่ทันทีเมื่อขยับค่านิดเดียว
> แต่ผลนี้ดีทั้งย่าน = ระบบ **robust** จริง

**ข้อ 4 — การตั้งเส้นนับคือ calibration มาตรฐาน**
ระบบ line-counting ทุกตัวในอุตสาหกรรมต้องกำหนดเส้นนับตามมุมกล้อง
ทำ **ครั้งเดียวต่อ 1 มุมกล้อง/สายพาน** แล้วใช้ได้ตลอด
→ ไม่ใช่การ "แอบจูนให้ได้เลขสวย" แต่เป็นขั้นตอนติดตั้งปกติ

และเรา**รายงานผลตอนไม่ calibrate ไว้ด้วย** (error 25–54%) เพื่อความโปร่งใส

### 6.5 ตัวเลขประกอบ

|---|---|

### 6.6 ข้อจำกัดทางเทคนิคที่เจอ

**บอร์ด decode วิดีโอ H.264 ไม่ได้**
```
OpenCV 4.5.2 บน PetaLinux (ผ่าน GStreamer) ไม่มี codec H.264
      ↓
ต้องแปลงคลิปเป็น MJPG .avi ก่อนโอนขึ้นบอร์ด
      ↓
ขนาดพองจาก 30 MB → 514 MB
      ↓
โชคดีที่ /tmp เป็น tmpfs ขนาด 2 GB → พอดี
```

## สรุปข้อค้นพบหลัก (Key Findings)

### 1. YOLOv8n INT8 บน KV260 รักษาความแม่นยำได้เกือบสมบูรณ์
mAP@0.5 ลดเพียง **1.5%** เทียบ float · F1 แทบไม่เปลี่ยน (ดีขึ้นเล็กน้อยด้วยซ้ำ)
พร้อม cross-check ที่ยืนยันว่า pipeline การวัดถูกต้อง

### 2. ประสิทธิภาพพลังงานเหนือกว่า GPU 1.8–2.1× และกินไฟน้อยกว่า 4.4–6.3×
ขึ้นกับจุดปฏิบัติการที่เทียบ — และการวัดยังเข้าข้าง GPU (วัดแค่ชิป vs วัดทั้งบอร์ด)

### 3. คอขวดอยู่ที่ ARM PS (preprocessing) ไม่ใช่ DPU ⭐
DPU ใช้เวลาแค่ 16% ของ pipeline · ยืนยันด้วย**หลักฐาน 2 ชิ้นจากวิธีวัดที่ต่างกัน**
(latency breakdown + power ที่เพิ่มจาก idle แค่ 0.25 W)
→ ชี้ทิศทาง optimization ที่ชัดเจนและวัดผลได้

### 4. ระบบนับกล่องทำงานได้จริงบน edge device ที่กินไฟระดับ ~5 W
นับได้ **215/215 (error 0.0%)** พร้อม sensitivity analysis พิสูจน์ว่า robust
(error < 3% ตลอดย่านพารามิเตอร์รอบข้าง)
