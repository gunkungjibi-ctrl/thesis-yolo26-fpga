# 01 — โจทย์และเหตุผล: ทำไมต้อง FPGA

> **สรุปไฟล์นี้ใน 3 บรรทัด**
> งานนับวัตถุจากวิดีโอเป็นงานที่ต้องรัน 24 ชั่วโมงต่อเนื่อง ทีละภาพ ที่หน้างาน
> ซึ่งเป็นสถานการณ์ที่ GPU เสียเปรียบที่สุด (ออกแบบมาให้เก่งเรื่อง batch ใหญ่)
> FPGA ที่มีตัวเร่ง AI ในตัวจึงเป็นทางเลือกที่ควรพิสูจน์ด้วยตัวเลขจริง

---

## 1. ปัญหาที่ต้องการแก้

### 1.1 สถานการณ์จริง

การนับวัตถุจากวิดีโอแบบเรียลไทม์ เช่น

- นับพัสดุที่ไหลผ่านสายพานในคลังสินค้า
- นับรถที่ผ่านจุดตรวจ
- นับสินค้าที่ออกจากไลน์ผลิต

งานพวกนี้มีลักษณะร่วมกัน 4 อย่าง:

| ลักษณะ | ผลที่ตามมา |
|---|---|
| ทำงาน **ต่อเนื่อง 24 ชั่วโมง** | ค่าไฟสะสมเป็นต้นทุนจริง ไม่ใช่เรื่องเล็ก |
| ประมวลผล **ทีละเฟรม** (batch = 1) | ไม่สามารถรวมภาพเป็นก้อนใหญ่เพื่อเพิ่ม throughput ได้ |
| ติดตั้ง **หลายจุด** ในโรงงานเดียว | ต้นทุนต่อจุดคูณด้วยจำนวนจุด |
| อยู่ **หน้างาน** ไม่ใช่ห้องเซิร์ฟเวอร์ | มีข้อจำกัดเรื่องขนาด ความร้อน ฝุ่น ไฟ |

### 1.2 ทำไมการใช้ GPU จึงไม่เหมาะกับงานนี้

GPU เป็นสถาปัตยกรรมที่ออกแบบมาให้ **"เก่งเรื่องปริมาณ"** — มีหน่วยคำนวณจำนวนมหาศาลที่ทำงานพร้อมกัน
มันจะแสดงประสิทธิภาพสูงสุดเมื่อมีข้อมูลป้อนเข้าไปเยอะพอที่จะเลี้ยงหน่วยคำนวณทุกตัวให้ทำงานพร้อมกัน

**แต่งานนับวัตถุมีภาพเดียวต่อครั้ง** → หน่วยคำนวณส่วนใหญ่ว่าง แต่ยังกินไฟอยู่

เราวัดปรากฏการณ์นี้ได้จริงในโครงงานนี้ (รายละเอียดในไฟล์ 04):

| โหมด | GPU utilization | throughput | กำลังไฟ | ประสิทธิภาพ |
|---|---|---|---|---|
| batch = 1 (แบบที่งานจริงต้องใช้) | **33%** | 31.5 FPS | 22.8 W | **1.38 FPS/W** |
| batch = 32 (แบบที่ GPU ชอบ) | 96% | 263.9 FPS | 58.5 W | 4.51 FPS/W |

> **สังเกต:** ที่ batch = 1 ซึ่งเป็นสถานการณ์จริงของงานนี้ GPU ใช้กำลังตัวเองได้แค่ **1 ใน 3**
> แต่ยังกินไฟ 22.8 W → **ประสิทธิภาพพลังงานตกลงไป 3.3 เท่า** เทียบกับตอนที่มันทำงานเต็มที่

นี่คือช่องว่างที่โครงงานนี้ต้องการโจมตี

### 1.3 ต้นทุนที่มองไม่เห็น

| ประเด็น | GPU (การ์ดระดับกลาง) | เป้าหมายของ edge device |
|---|---|---|
| กำลังไฟ | 60–250 W | < 15 W |
| ต้องมีเครื่องพีซีประกอบ | ใช่ (CPU + RAM + PSU + เคส) | ไม่ — จบในบอร์ดเดียว |
| ระบบระบายความร้อน | พัดลม/ของเหลว | passive heatsink |
| ขนาด | ระดับเคสพีซี | ระดับฝ่ามือ |

ถ้าโรงงานหนึ่งต้องติด 20 จุด ความต่างของกำลังไฟ 50 W ต่อจุด × 20 จุด × 24 ชม. × 365 วัน
= ประมาณ **8,760 kWh ต่อปี** ซึ่งเป็นตัวเลขที่มีนัยสำคัญทางธุรกิจ

## 2. FPGA และ DPU คืออะไร (พื้นหลังสำหรับผู้ฟัง)

### 2.1 FPGA โดยย่อ

**FPGA (Field-Programmable Gate Array)** คือชิปที่เราสามารถ "เดินวงจรใหม่" ได้ด้วยซอฟต์แวร์
ต่างจาก CPU/GPU ที่วงจรถูกกำหนดตายตัวมาจากโรงงาน

- **ข้อดี:** สร้างวงจรที่พอดีกับงานเป๊ะ ไม่มีส่วนที่ไม่ได้ใช้มากินไฟ
- **ข้อเสีย:** ออกแบบยากกว่ามาก ต้องใช้ความรู้ระดับฮาร์ดแวร์

### 2.2 ทางลัดที่ทำให้โครงงานนี้เป็นไปได้: DPU

การเขียนวงจร YOLO ขึ้นมาเองจากศูนย์บน FPGA เป็นงานระดับปริญญาเอกหลายปี
แต่ AMD/Xilinx มี **DPU (Deep-learning Processing Unit)** — เป็น**วงจรตัวเร่ง AI สำเร็จรูป**
ที่เอาไปวางบน FPGA ได้เลย พร้อม toolchain ที่แปลงโมเดล PyTorch → ไฟล์ที่ DPU รันได้

```
สิ่งที่เราไม่ต้องทำ:          สิ่งที่เราต้องทำ:
┌────────────────────┐       ┌─────────────────────────────┐
│ ออกแบบวงจร conv    │       │ แปลงโมเดลให้ DPU รับได้      │
│ ออกแบบ memory ctrl │  →    │ (quantize / เปลี่ยน op)      │
│ ออกแบบ dataflow    │       │ เขียน pre/post processing    │
│ ทำ timing closure  │       │ เขียน tracking + counting    │
└────────────────────┘       │ วัดผลและวิเคราะห์            │
     AMD ทำให้แล้ว           └─────────────────────────────┘
```

> **แต่ทางลัดนี้มีราคา** — DPU รองรับเฉพาะ operation ชุดหนึ่งเท่านั้น
> ถ้าโมเดลใช้ operation ที่ DPU ไม่รู้จัก มันจะถูกเด้งกลับไปรันบน CPU ซึ่งช้ามาก
> **ปัญหานี้คือหัวใจของคำถามวิจัยข้อ 1** (ดูข้อ 3 ข้างล่าง) และเป็นสิ่งที่เกิดขึ้นจริงกับ YOLO26 (ไฟล์ 08)

### 2.3 ทำไม KV260 ตอบโจทย์ครบ

บอร์ด **AMD Kria KV260** ที่ใช้ในโครงงานนี้เป็น **Zynq UltraScale+ MPSoC** ซึ่งมี 2 ส่วนในชิปเดียว:

```
┌──────────────────── ชิปเดียวกัน ────────────────────┐
│                                                      │
│   PS (Processing System)      PL (Programmable Logic)│
│   ┌──────────────────┐        ┌────────────────────┐ │
│   │ ARM Cortex-A53   │  ←──→  │  DPU B4096         │ │
│   │ quad-core        │        │  (วงจรที่เราวางลงไป)│ │
│   │ = CPU ปกติ       │        │                    │ │
│   │ รัน Linux ได้    │        │  เร่ง convolution  │ │
│   └──────────────────┘        └────────────────────┘ │
│      ทำงาน logic ที่           ทำงานคำนวณหนัก        │
│      แตกกิ่งเยอะ                ที่ทำซ้ำๆ            │
└──────────────────────────────────────────────────────┘
```

**นี่คือเหตุผลที่ระบบนับกล่องจบในบอร์ดเดียวได้:**

| งาน | ธรรมชาติของงาน | รันที่ |
|---|---|---|
| อ่านวิดีโอ, resize, normalize | งานลำดับ | PS (ARM) |
| YOLO inference | คำนวณหนัก ทำซ้ำ ขนานได้ | **PL (DPU)** |
| decode กล่อง, NMS | คณิตศาสตร์ + ตัดสินใจ | PS |
| tracking (จับคู่ ID ข้ามเฟรม) | logic แตกกิ่งเยอะ ขนานยาก | PS |
| line-crossing → นับ | เงื่อนไข if-else | PS |

การแบ่งงานแบบนี้เรียกว่า **heterogeneous computing** — เอาแต่ละงานไปวางบนหน่วยประมวลผลที่เหมาะกับมัน
ซึ่งเป็นข้อได้เปรียบที่ GPU การ์ดแยกทำไม่ได้ (เพราะ GPU ต้องมี CPU แยกต่างหาก + ต้องโอนข้อมูลผ่าน PCIe)

## 3. คำถามวิจัย 4 ข้อ

โครงงานนี้ตั้งคำถามไว้ 4 ข้อ และ**ผลการทดลองทุกหมวดถูกออกแบบมาให้ตอบคำถามเหล่านี้พอดี**

### คำถามที่ 1 — YOLO รุ่นใหม่ deploy ลง DPU ได้จริงแค่ไหน ติดข้อจำกัดอะไร

**ทำไมถึงถาม:** DPU รองรับ operation จำกัด และ Vitis AI 3.0 ออกปี 2022
ในขณะที่ YOLO26 เป็นโมเดลรุ่นใหม่กว่านั้นมาก → มีโอกาสสูงที่จะเข้ากันไม่ได้
แต่**ยังไม่มีใครรายงานว่าติดตรงไหน** เพราะ YOLO26 ไม่อยู่ใน Vitis AI Model Zoo

**ตอบด้วย:** ไฟล์ 08 (Track B) — พบว่าติดที่ attention block 2 จุด ไม่ใช่ที่ NMS-free head อย่างที่คาด

---

### คำถามที่ 2 — quantize เป็น INT8 แล้วเสียความแม่นยำเท่าไร คุ้มกับที่ประหยัดไฟหรือไม่

**ทำไมถึงถาม:** DPU รันได้เฉพาะ **INT8** (จำนวนเต็ม 8 บิต) ในขณะที่โมเดลต้นฉบับเป็น **FP32** (ทศนิยม 32 บิต)
การบีบจาก 32 บิตเหลือ 8 บิตแปลว่า**ทิ้งข้อมูลไป 4 เท่า** → คำถามคือทิ้งแล้วโมเดลยังแม่นอยู่ไหม

นี่เป็นคำถามที่ต้องตอบ **มิฉะนั้นการเปรียบเทียบกับ GPU (ที่รัน FP32) จะไม่ยุติธรรม**

**ตอบด้วย:** ไฟล์ 07 ตารางที่ 2 (mAP ตก 1.5%) + ตารางที่ 4–5 (ประหยัดไฟ 6.3 เท่า)

---

### คำถามที่ 3 — เมื่อวัดทั้งระบบ (ไม่ใช่แค่ตัวเร่ง) คอขวดจริงอยู่ที่ไหน

**ทำไมถึงถาม:** งานวิจัยจำนวนมากรายงานแค่ **"ตัวเร่งทำได้กี่ FPS"** ซึ่งเป็นตัวเลขที่สวยแต่หลอก
เพราะระบบจริงต้องมี preprocessing และ postprocessing ด้วย ผู้ใช้เห็นแค่ตัวเลขปลายทาง

**ตอบด้วย:** ไฟล์ 07 ตารางที่ 3 — และคำตอบทำให้ประหลาดใจ: **คอขวดคือ CPU ไม่ใช่ DPU**
(DPU ใช้เวลาแค่ 16% ของ pipeline)

---

### คำถามที่ 4 — ระบบนับได้แม่นแค่ไหนเทียบกับที่คนนับ

**ทำไมถึงถาม:** เป้าหมายปลายทางของโครงงานไม่ใช่ "ตรวจจับกล่องได้" แต่คือ **"นับกล่องได้ถูก"**
ซึ่งเป็นคนละเรื่องกัน — โมเดลอาจ detect แม่น แต่ถ้า tracking ผิดพลาด กล่องเดียวจะถูกนับ 2 ครั้ง

**ตอบด้วย:** ไฟล์ 07 ตารางที่ 6 — GT 215 กล่อง ระบบนับได้ 215 (error 0.0%)
พร้อม sensitivity analysis พิสูจน์ว่าไม่ใช่ความบังเอิญ

## 4. สิ่งที่โครงงานนี้จะส่งมอบ

### 4.1 Contribution หลัก
ระบบนับวัตถุแบบเรียลไทม์บน heterogeneous FPGA SoC **พร้อมผลวัดเชิงประจักษ์ครบ 4 มิติ**
(ความแม่นยำ / ความเร็ว / พลังงาน / ความถูกต้องในการนับ) เทียบกับ GPU baseline ที่วัดเองด้วยเงื่อนไขเดียวกัน

### 4.2 Contribution เชิงองค์ความรู้
**ข้อจำกัดของการ deploy YOLO รุ่นใหม่บน DPU stack เดิม** — ระบุได้ถึงระดับว่าติดที่ operation ไหน
ตำแหน่งใดในกราฟ และทำไมตำแหน่งนั้นถึงสำคัญ

### 4.3 ส่วนขยาย (ทำเพิ่มระหว่างทาง)
**Cross-platform comparison** — port ระบบเดียวกันไปบอร์ด Efinix Ti375 ซึ่งใช้สถาปัตยกรรมคนละแบบ
(soft RISC-V + TinyML accelerator แทน hard DPU) → เทียบ 3 แพลตฟอร์ม (ไฟล์ 09)

### 4.4 สิ่งที่ไม่ผูกเป็นเงื่อนไขจบ
การออกแบบ **custom accelerator** สำหรับ layer ที่เป็นคอขวด — เป็นงาน optional
ทำต่อเมื่อระบบฐานทำงานได้และ profiling ระบุคอขวดชัดแล้ว (ซึ่งตอนนี้ระบุแล้วว่าคือ preprocessing)

## 5. ทำไมโจทย์นี้ถึง "พอดี" กับระดับปริญญาตรี

| ประเด็น | เหตุผล |
|---|---|
| มีเส้นทางที่พิสูจน์แล้ว | DPU + Vitis AI มี documentation และ prior work → ไม่ตันแน่นอน |
| มีจุดที่ยังไม่มีใครทำ | YOLO26 บน DPU ยังไม่มีใครรายงาน → มีที่ให้ contribute |
| วัดผลได้เป็นตัวเลข | FPS, W, mAP, จำนวนที่นับได้ → ไม่ใช่งานที่ประเมินยาก |
| มีแผนสำรองชัดเจน | ถ้า YOLO26 ไม่ผ่าน ยังมี YOLOv8n รองรับ (ดูไฟล์ 02 ข้อ 4) |
