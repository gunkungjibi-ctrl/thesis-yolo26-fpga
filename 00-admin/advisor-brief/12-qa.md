# 12 — คำถามที่น่าจะโดนถาม และคำตอบที่เตรียมไว้

> **วิธีใช้ไฟล์นี้:** อ่านก่อนเข้าพบ 1 รอบ แล้วซ้อมตอบเฉพาะ 5 ข้อแรก (ที่ทำเครื่องหมาย ⭐)
> เพราะเป็นข้อที่มีโอกาสโดนถามสูงที่สุดและตอบยากที่สุด
> แต่ละคำตอบมี **โครงสร้าง 3 ส่วน**: ยอมรับประเด็น → ให้ข้อมูลที่รองรับ → สรุปให้เห็นภาพ

## หมวด A — คำถามเกี่ยวกับผลการทดลอง

### ⭐ A1. ทำไม end-to-end ได้แค่ 12.8 FPS ทั้งที่ DPU ทำได้ 82 FPS แบบนี้เรียก real-time ได้หรือ

**คำตอบ:**

ถูกต้องครับ และนั่นคือ**ข้อค้นพบหลักข้อหนึ่งของโครงงาน** ไม่ใช่ข้อบกพร่องที่ซ่อนไว้

จาก latency breakdown: DPU ใช้เวลาแค่ **16%** ของ pipeline (12.5 ms จาก 78.3 ms)
ส่วน preprocessing บน ARM กิน **63%** (49.7 ms) → ระบบเป็น **PS-bound ไม่ใช่ DPU-bound**

**และเรามีหลักฐาน 2 ชิ้นที่วัดคนละวิธียืนยันตรงกัน:**
1. **latency breakdown** — วัดเวลาแยกรายสเตจ
2. **power ตอนรันแอปจริง** — เพิ่มจาก idle แค่ **+0.25 W** (4.85 → 5.10 W) = DPU ว่างเกือบตลอด

**ประเด็นนี้ชี้ทิศทาง optimization ที่ชัดเจนและวัดผลได้:**
```
ถ้าเปลี่ยนไปใช้ DPU ที่เร็วขึ้น 2 เท่า  →  12.77 → 13.9 FPS  (ดีขึ้น 8.8%)
ถ้า optimize preproc เหลือ 10 ms       →  12.77 → 25.9 FPS  (ดีขึ้น 103%)
```

**สรุป:** ตัวเลข 12.8 FPS เป็นข้อมูลที่มีค่ากว่าตัวเลข 82 FPS เพราะมันบอกว่าต้องไปแก้ตรงไหน

### ⭐ A2. เทียบกับ GPU ยุติธรรมหรือไม่ ในเมื่อ FPGA เป็น INT8 แต่ GPU เป็น FP32

**คำตอบ:**

เป็นคำถามที่ถูกต้องครับ และเราปิดประเด็นนี้ด้วยตัวเลข mAP

**ต้นทุนของ INT8 = mAP@0.5 ลดแค่ 1.5%** (0.8846 → 0.8713) และ F1 แทบไม่เปลี่ยน
**สิ่งที่ได้กลับมา = ประหยัดไฟ 6.3 เท่า** (9.27 W vs 58.5 W)

**และการวัดของเรายังเข้าข้าง GPU ด้วยซ้ำ:**
| | ขอบเขตการวัด power |
|---|---|
| GPU (nvidia-smi) | **เฉพาะชิป GPU** — ไม่รวม CPU, RAM, เมนบอร์ด, PSU |
| FPGA (INA260) | **ทั้งบอร์ด SOM** — รวม ARM, DPU, DDR, regulator ทั้งหมด |

→ ถ้าวัดขอบเขตเดียวกัน FPGA จะชนะมากกว่านี้อีก

**เพิ่มเติม:** INT8 เป็นมาตรฐานของ edge inference อยู่แล้ว (TensorRT, TFLite, DPU ใช้หมด)
การรัน FP32 บน edge device ไม่ใช่สิ่งที่ใครทำในทางปฏิบัติ

### ⭐ A3. การนับได้ 215/215 พอดี จูนจนพอดีหรือเปล่า

**คำตอบ:**

ไม่ครับ และเรามีหลักฐาน 2 ชั้นที่ยืนยัน

**ชั้นที่ 1 — Sensitivity analysis**
```
บริเวณรอบค่าที่เลือก (เส้น 0.30–0.40·W × max_dist 40–60):
   → นับได้ 209–219  →  error < 3% ทั้งย่าน
```
ถ้าเป็นการจูนจนพอดี ผลจะดีเฉพาะจุดเดียวและแย่ทันทีเมื่อขยับนิดเดียว
แต่ผลนี้ดีทั้งย่าน = **ระบบ robust จริง ไม่ใช่ fluke**

**ชั้นที่ 2 — การกำหนดเส้นนับคือ calibration มาตรฐาน**
ระบบ line-counting ทุกตัวในอุตสาหกรรมต้องกำหนดเส้นตามมุมกล้อง
ทำ **ครั้งเดียวต่อ 1 มุมกล้อง/สายพาน** แล้วใช้ได้ตลอด → เป็นขั้นตอนติดตั้งปกติ ไม่ใช่การโกง

**และเรารายงานผลตอนไม่ calibrate ไว้ด้วยเพื่อความโปร่งใส:**
- เส้นกลางจอ (0.5) → นับได้ 270–331 = error 25–54%
- พร้อมอธิบายสาเหตุ: บริเวณกลางภาพกล่องซ้อนทับ → detection กระพริบ → track แตก → นับซ้ำ

**หลักฐานเสริมว่าระบบเข้าใจปัญหาจริง:** แกน y ผิดหมด (error 20–92%)
เพราะกล่องเคลื่อนที่แนวนอน → ผลนี้ยืนยันว่าระบบจับการเคลื่อนที่ได้ถูกต้อง

### A4. ทำไมถึงรายงาน FPS/W สองค่า (9.67 กับ 1.99) ใช้ค่าไหนกันแน่

**คำตอบ:**

ใช้**ทั้งสองค่า** ครับ เพราะมันตอบคนละคำถาม

| ค่า | ความหมาย | ตอบคำถามว่า |
|---|---|---|
| **9.67 FPS/W** (DPU-saturated) | ศักยภาพสูงสุดของ accelerator | "ฮาร์ดแวร์ตัวนี้ทำได้แค่ไหน" |
| **1.99 FPS/W** (real application) | จุดที่ระบบใช้งานจริงตอนนี้ | "ระบบที่สร้างขึ้นทำได้แค่ไหน" |

**ถ้ารายงานแค่ค่าเดียวจะบิดเบือน:**
- รายงานแค่ 9.67 → เกินจริง เพราะระบบจริงยังทำไม่ได้
- รายงานแค่ 1.99 → ต่ำเกินจริง เพราะไม่สะท้อนศักยภาพฮาร์ดแวร์

**และช่องว่างระหว่างสองค่าคือข้อมูลที่มีค่าที่สุด** — มันบอกว่ามี headroom เหลืออีก 79 FPS
ที่จะได้มาถ้าแก้คอขวดที่ preprocessing โดยที่ power แทบไม่เพิ่ม

### A5. valid set มีแค่ 57 ภาพ น้อยไปหรือเปล่า

**คำตอบ:**

น้อยกว่า dataset วิจัยมาตรฐานครับ แต่มีเหตุผลรองรับ 3 ข้อ:

1. **เป็น dataset โดเมนเฉพาะ** — กล่องพัสดุบนสายพานในมุมกล้องคงที่
   ความหลากหลายต่ำกว่า COCO มาก → ต้องการภาพน้อยกว่าเพื่อให้ผลมีเสถียรภาพ

2. **มี 289 กล่อง ground truth** ใน 57 ภาพ → จำนวน object ที่วัดจริงไม่ได้น้อย

3. **มีการ cross-check** — float mAP ที่เราวัดเอง (0.8846) ตรงกับที่ validate มาตรฐานบน Colab (0.884)
   → ยืนยันว่า pipeline การวัดถูกต้อง

**และที่สำคัญกว่า:** ตัวชี้วัดปลายทางของโครงงานไม่ใช่ mAP บน valid set
แต่คือ **counting error บนวิดีโอ 18,000 เฟรม** ซึ่งมี ground truth 215 กล่อง
→ นั่นคือการทดสอบที่ใกล้เคียงการใช้งานจริงมากกว่า

## หมวด B — คำถามเกี่ยวกับขอบเขตโครงงาน

### ⭐ B1. ชื่อโครงงานคือ YOLO26 แต่ที่ deploy สำเร็จคือ YOLOv8n

**คำตอบ:**

ถูกต้องครับ และเราแยกสองเรื่องนี้ชัดเจนตั้งแต่ต้นด้วย **กลยุทธ์ two-track**

| Track | บทบาท | ผล |
|---|---|---|
| **A (YOLOv8n)** | พิสูจน์ว่า**ระบบนับทั้งระบบทำงานได้จริงบน FPGA** | ✅ สำเร็จ + ผลวัดครบ 4 หมวด |
| **B (YOLO26n)** | ตอบคำถามวิจัยว่า **โมเดลรุ่นใหม่ deploy ลง DPU ได้แค่ไหน** | ✅ **ตอบได้แล้ว** |

**คำตอบของ Track B ไม่ใช่ "ทำไม่ได้" เฉยๆ แต่เจาะจงถึงระดับนี้:**
- **ไม่ได้ติดที่ NMS-free head** อย่างที่ทุกคนคาด (แก้ได้ด้วย `end2end=False`)
- **ติดที่ attention block 2 จุด** — `model.10` (~32% ของกราฟ) และ `model.22` (~69%)
- **กลไก:** MatMul แบบ data×data (DPU ทำได้แค่ data×weight) + Softmax (ไม่ใช่ DPU op)
- **ทำไมร้ายแรง:** อยู่**กลางกราฟ** → ตัด DPU subgraph เป็น ~3 ชิ้น (ต่างจาก Sigmoid ที่อยู่ปลายกราฟซึ่งไม่เป็นไร)

**ทำไมนี่คือ contribution:** YOLO26 ไม่อยู่ใน Vitis AI Model Zoo และยังไม่มีใครรายงาน
คนที่จะทำต่อจะรู้ทันทีว่าต้องเตรียมรับมืออะไร และมีทางเลือก 3 ทาง (ยอมรับ multi-subgraph / ถอด attention / เปลี่ยน DPU)

### B2. ถ้า Track B ไม่ผ่าน แปลว่าโครงงานล้มเหลวหรือเปล่า

**คำตอบ:**

ไม่ครับ และเราวางแผนรับมือเรื่องนี้ไว้ตั้งแต่ต้นโครงงาน

**เหตุผลเชิงวิชาการ:**
> คำถามวิจัยคือ **"YOLO รุ่นใหม่ deploy ลง DPU ได้แค่ไหน"**
> คำตอบว่า **"ไม่ได้ เพราะติดที่ X ตำแหน่ง Y ด้วยกลไก Z"**
> เป็นคำตอบที่สมบูรณ์พอๆ กับคำตอบว่า "ได้"

สิ่งที่ทำให้มันเป็น contribution จริงคือ **ความเจาะจง** — ไม่ได้บอกแค่ "มันไม่ทำงาน"
แต่บอกได้ถึงระดับ node ในกราฟ พร้อมอธิบายกลไกและเสนอทางเลือก

**เหตุผลเชิงบริหารความเสี่ยง:** Track A สำเร็จครบวงจรแล้ว → โครงงานมีผลลัพธ์ที่จับต้องได้แน่นอน
Track B เป็นส่วนที่เพิ่มคุณค่า ไม่ใช่ส่วนที่โครงงานพึ่งพา

### ⭐ B3. ทำไมทำสองบอร์ด จะทำทันหรือ

**คำตอบ:**

**โปรเจค KV260 พิสูจน์จบครบวงจรแล้วครับ** — มีผลวัดครบ 4 หมวด + ระบบนับทำงานได้จริง
Efinix เป็น**ส่วนขยาย** ไม่ใช่งานที่โครงงานพึ่งพา

**คุณค่าที่เพิ่มขึ้น:** เปลี่ยนจาก "ทำ YOLO บน FPGA ได้" เป็น **cross-platform comparison**
```
GPU (ทั่วไป)  vs  KV260 (hard DPU)  vs  Ti375 (soft RISC-V + accelerator)
```
→ ตอบคำถามที่ตอบไม่ได้ถ้ามีแพลตฟอร์มเดียว เช่น
"ข้อจำกัดที่เจอเป็นของ FPGA โดยทั่วไป หรือเฉพาะ DPU ตัวนี้"

**และไม่ได้เริ่มจากศูนย์** — reuse ได้: dataset, ground truth (GT=215), GPU baseline, counting logic

**มี fallback ชัดเจน:** ถ้า Ti375 รัน YOLO เต็มตัวไม่ไหว → ยังเขียนเข้าเล่มได้ในหัวข้อ
"ข้อจำกัดของ soft accelerator เทียบ hard DPU" ซึ่งเป็นหลักการเดียวกับ Track B

**สถานะปัจจุบัน:** E3-A เสร็จแล้ว (ได้ INT8 tflite verify parity 59/59) + โค้ด RISC-V เขียนเสร็จ

### B4. custom accelerator ที่เขียนไว้ในแผนตอนแรก ทำหรือยัง

**คำตอบ:**

ยังไม่ได้ทำครับ และมันถูกระบุเป็น **optional ไม่ผูกเป็นเงื่อนไขจบ** ตั้งแต่ต้น

**เหตุผลของการวางแผนแบบนั้น:** การออกแบบ custom accelerator ควรทำ**หลังจาก**
(1) ระบบฐานทำงานได้ และ (2) profiling ระบุคอขวดชัดแล้ว

**ตอนนี้เงื่อนไขทั้งสองครบแล้ว:**
- ระบบทำงานได้ ✅
- profiling ระบุแล้วว่าคอขวดคือ **preprocessing (49.7 ms, 63%)** ไม่ใช่ layer ใดของโมเดล ✅

**ข้อค้นพบที่น่าสนใจ:** คอขวดไม่ได้อยู่ที่ layer ของโมเดลอย่างที่คาดตอนวางแผน
→ ถ้าจะทำ custom hardware ควรทำ **hardware scaler สำหรับ preprocessing** ไม่ใช่ accelerator สำหรับ conv layer
→ นี่เองก็เป็นผลของ profiling ที่มีค่า

## หมวด C — คำถามเกี่ยวกับวิธีการ

### C1. ทำไมใช้ Python รัน inference ไม่ใช้ C++

**คำตอบ:**

โค้ด C++ (`yolo_dpu_infer.cpp`) เขียนและ compile-check ผ่านแล้วครับ
แต่ทำได้แค่ raw inference + dequantize ส่วน **DFL decode ต้องเขียนใหม่ทั้งหมด**
(เพราะตอน quantize เราตัดส่วน decode ออกจากกราฟเพื่อให้ผ่าน XIR)

**การตัดสินใจ:** เขียน Python ก่อนเพื่อ**พิสูจน์ความถูกต้องของ decode logic ให้จบก่อน**
เพราะการ debug decode ที่ผิดใน C++ ยากกว่ามาก

**และตอนนี้มีข้อมูลที่ยืนยันว่าการเลือกนี้ไม่กระทบผลหลัก:**
คอขวดคือ preprocessing (49.7 ms) ไม่ใช่ตัว interpreter
→ การ port เป็น C++ อยู่ในรายการงาน optimize ที่ระบุไว้แล้ว

### C2. ทำไมใช้ plain resize ไม่ใช้ letterbox

**คำตอบ:**

เพื่อความสอดคล้องตลอด pipeline ครับ — **calibration, training, inference บนบอร์ด และ GPU baseline ใช้ plain resize เหมือนกันหมด**

**ผลที่ตามมาที่ต้องระวัง:** เมื่อ scale พิกัดกล่องกลับไปภาพต้นฉบับ ต้องใช้ตัวคูณ**แยกแต่ละแกน**
```
x_original = x_640 × (origW / 640)
y_original = y_640 × (origH / 640)
```
เพราะภาพต้นฉบับ 640×360 มีอัตราส่วนต่างจาก 640×640 มาก
(ถ้าใช้ตัวคูณเดียวทั้งสองแกน กล่องจะเพี้ยน — เป็นจุดที่เราตรวจสอบและยืนยันแล้ว)

**ข้อดีของ plain resize บน edge:** ไม่ต้องคำนวณ padding และไม่ต้องเก็บ offset
→ preprocessing เบากว่าเล็กน้อย (แม้จะยังเป็นคอขวดอยู่ดี)

### C3. calibration ใช้แค่ 32 ภาพ พอหรือ

**คำตอบ:**

เดิมตั้งใจใช้ 208 ภาพครับ แต่ลดเหลือ 32 เพราะข้อจำกัดของเครื่อง (RAM 5.88 GB → container OOM)

**และผลยืนยันว่าเพียงพอ:**
- INT8 mAP@0.5 = 0.8713 เทียบ float 0.8846 → **drop แค่ 1.5%**
- output ทั้ง 3 หัวมี float range ปกติ **ไม่ saturate**

**เหตุผลเชิงหลักการ:** calibration ต้องการแค่ภาพที่พอจะสะท้อนการกระจายของค่าที่ไหลผ่านโมเดล
ซึ่งสำหรับ dataset โดเมนเฉพาะที่มีความหลากหลายต่ำ (สายพานมุมเดียว) 32 ภาพก็ครอบคลุมได้

**สิ่งที่สำคัญกว่าจำนวน:** calibration set ต้อง**ตรงโดเมน** — เราเคยใช้ COCO แล้วต้องเปลี่ยนมาใช้ภาพสายพานจริง

### C4. ทำไมเปลี่ยน SiLU เป็น LeakyReLU ทำให้ความแม่นยำเสียไหม

**คำตอบ:**

เพราะ **DPUCZDX8G ไม่รองรับ SiLU** ครับ (ต้องคำนวณ exponential ซึ่งไม่ใช่ op ของ DPU)
ถ้าไม่เปลี่ยน → SiLU ทุก layer จะถูกเด้งไป CPU → กราฟถูกตัดเป็นสิบชิ้น → ไม่มีทางผ่าน gate

**เรื่องความแม่นยำ มี 2 กรณีที่ต่างกันมาก:**

| กรณี | ผล |
|---|---|
| เปลี่ยนเฉยๆ **ไม่ retrain** | **พังหนัก** — logit range ระเบิดถึง ±2000 → int8 saturate → detection พลิกจากเจอเป็นพลาด (เราพิสูจน์ด้วยข้อมูล 4 ชั้น) |
| เปลี่ยนแล้ว **fine-tune 400 epochs** | **กลับมาเท่าเดิม** — mAP 0.884 |

**ข้อสรุปเชิงวิชาการ:** การสลับ activation เพื่อ hardware compatibility ทำได้โดยไม่เสียความแม่นยำ
**ถ้ายอมลงทุน fine-tune** — ราคาที่จ่ายคือ**เวลา** ไม่ใช่**ความแม่นยำ**

**หมายเหตุเรื่องค่า 0.1015625:** เลือกเป็น 26/256 เพราะเป็นค่าที่**แทนได้พอดีใน fixed-point** ที่ DPU ใช้
(ถ้าใช้ 0.1 ธรรมดา จะแทนแบบ binary ไม่ลงตัว → คลาดเคลื่อนสะสมทุก layer)

### D4. GPU ที่ใช้เทียบเป็นรุ่นเก่า (2019) และเป็นรุ่นโน้ตบุ๊ก ไม่แฟร์หรือเปล่า

**คำตอบ:**

เป็นข้อจำกัดที่เรารายงานไว้เองครับ และมีมุมมองที่ต้องพิจารณา 2 ด้าน:

**ด้านที่ไม่แฟร์กับ GPU:** GTX 1660 Ti Max-Q เป็นรุ่นปี 2019 และเป็นรุ่นโน้ตบุ๊กที่มี thermal throttle
→ เราจัดการด้วย median-of-medians (5 runs × 200 iters) และรายงาน spread (±6 FPS)

**ด้านที่ไม่แฟร์กับ FPGA:**
- KV260 เป็นบอร์ดปี 2021 แต่ **DPU B4096 เป็น IP ที่ออกแบบมาก่อนหน้านั้น**
- การวัด power ของ FPGA รวมทั้งบอร์ด ส่วน GPU วัดแค่ชิป

**สิ่งที่การเทียบนี้บอกได้จริง:** เป็นการเทียบ**เชิงสถาปัตยกรรม** (GPU ทั่วไป vs AI accelerator เฉพาะทาง)
ไม่ใช่การเทียบรุ่นต่อรุ่นหรือยุคต่อยุค

**และข้อสรุปเชิงสถาปัตยกรรมยังยืนอยู่:** ที่ batch=1 GPU ใช้กำลังตัวเองได้แค่ **33%**
ซึ่งเป็นข้อจำกัดเชิงโครงสร้าง ไม่ใช่เรื่องของรุ่นหรือยุค

### D5. ถ้าเปลี่ยนมุมกล้องหรือสายพาน ระบบยังนับได้ไหม

**คำตอบตรงไปตรงมา:**

**ต้อง calibrate เส้นนับใหม่ครับ** — เป็นข้อจำกัดที่รายงานไว้แล้ว

**แต่นี่เป็นข้อจำกัดของระบบ line-counting ทุกตัวในอุตสาหกรรม** ไม่ใช่ของระบบเรา
การกำหนดเส้นนับตามมุมกล้องเป็นขั้นตอนติดตั้งมาตรฐาน ทำครั้งเดียวต่อจุดติดตั้ง

**สิ่งที่ผลของเราบอกเพิ่ม (และมีประโยชน์):**
เราไม่ได้แค่บอกว่า "ต้อง calibrate" แต่บอกได้ว่า **ควรวางเส้นตรงไหนและเพราะอะไร**
```
วางที่โซนกล่องเพิ่งเข้าเฟรม (x ≈ 0.3–0.4·W) ที่กล่องยังไม่ทับกัน
   → error < 3%

วางกลางจอ (x = 0.5) ที่กล่องหนาแน่น/ซ้อนทับ
   → detection กระพริบ → track แตก → นับซ้ำ → error 25–54%
```
→ เป็น **guideline ที่นำไปใช้ติดตั้งจริงได้** ไม่ใช่แค่ตัวเลขผลการทดลอง

**ส่วนตัวโมเดล detection** — ถ้าเปลี่ยนโดเมนมาก (แสง มุม ชนิดกล่อง) ควร fine-tune ใหม่
ซึ่งเรามี pipeline ที่ทำซ้ำได้แล้ว (Colab notebook + สคริปต์ quantize/compile)
