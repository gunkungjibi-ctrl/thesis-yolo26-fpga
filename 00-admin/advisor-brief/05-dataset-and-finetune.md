## 2. ปัญหาสำคัญ: DPU ไม่รองรับ SiLU

### 2.1 SiLU คืออะไร และทำไม YOLO ใช้

**Activation function** คือฟังก์ชันที่ใส่ไว้หลัง layer เพื่อให้โมเดลเรียนรู้ความสัมพันธ์ที่ไม่เป็นเส้นตรงได้

YOLOv8 และ YOLO26 ใช้ **SiLU (Sigmoid Linear Unit)** หรือที่เรียกว่า Swish:

```
SiLU(x) = x × sigmoid(x) = x / (1 + e^(-x))
```

มันให้ผลดีกว่า ReLU ในงาน detection แต่มีปัญหาคือ **ต้องคำนวณ exponential**

### 2.2 ทำไม DPU ทำไม่ได้

DPU ออกแบบมาให้ทำเลขจำนวนเต็มแบบง่ายๆ ให้เร็วที่สุด
`e^(-x)` เป็นฟังก์ชันที่ต้องใช้วงจรซับซ้อน (lookup table ขนาดใหญ่หรือ CORDIC)
→ ไม่คุ้มที่จะใส่ลงในวงจรที่เน้นความเร็วและประหยัดพลังงาน

**ผลที่ตามมา:** ถ้าโมเดลใช้ SiLU → operation นั้นจะถูกเด้งไปรันบน CPU
และเนื่องจาก SiLU อยู่**ทุก layer** → กราฟจะถูกตัดเป็นชิ้นๆ นับสิบ → ไม่มีทางผ่าน gate

### 2.3 ทางออก: LeakyReLU(0.1015625)

```
LeakyReLU(x) = x           ถ้า x > 0
             = 0.1015625×x ถ้า x ≤ 0
```

มีแค่การเปรียบเทียบกับ 0 และการคูณ → DPU ทำได้เร็วมาก

**ทำไมต้องเป็นเลขประหลาด 0.1015625:**

```
0.1015625 = 26 / 256 = 26 / 2^8
```

เป็นเลขที่**แทนได้พอดีในระบบ fixed-point** ที่ DPU ใช้
ถ้าใช้ 0.1 ธรรมดา → แทนแบบ binary ไม่ลงตัว → เกิดความคลาดเคลื่อนที่สะสมทุก layer

> นี่เป็นตัวอย่างที่ดีของ **hardware-aware model design** — ต้องเลือกค่าที่ฮาร์ดแวร์ชอบ ไม่ใช่ค่าที่มนุษย์อ่านสวย

## 3. การพิสูจน์ว่า "เปลี่ยนเฉยๆ ไม่ได้ ต้อง fine-tune"

ส่วนนี้เป็นงาน diagnostic ที่ทำก่อนหน้า และเป็นหลักฐานว่าทำไมขั้นตอน fine-tune ถึงจำเป็น

### 3.1 อาการที่เจอ

ตอน verify ว่า quantization ถูกต้องหรือไม่ ใช้ **cosine similarity** เทียบ output ของ float model กับ quantized model
เกณฑ์ที่ตั้งไว้คือต้อง > 0.99

**ผลที่ได้: 0.991 / 0.942 / 0.894** สำหรับ output 3 สเกล (80×80 / 40×40 / 20×20)
→ **ต่ำกว่าเกณฑ์ที่ 2 ใน 3 tensor**

### 3.2 การขุดหาสาเหตุแบบเป็นชั้น

**ชั้นที่ 1 — สมมติฐานแรก: ส่วน box (DFL) เป็นตัวฉุด?**

แยกวัด BOX กับ CLASS ออกจากกัน:

| Output | BOX cos | CLASS cos | CLASS float logit range |
|---|---|---|---|
| 80×80 | 0.963 | 0.992 | [−128.7, 11.1] |
| 40×40 | 0.944 | 0.941 | [−340.5, 29.8] |
| **20×20** | 0.925 | **0.893** | **[−2007.4, 169.4]** |

→ **สมมติฐานถูกหักล้าง** — CLASS แย่พอกันหรือแย่กว่า BOX
→ แต่เห็นแพทเทิร์นใหม่: **logit range ระเบิดตามความละเอียดที่หยาบลง** (±65 → ±340 → **±2007**)

**ชั้นที่ 2 — พิสูจน์ saturation โดยตรง**

```
float range ที่แท้จริง:  [−128.7, +56.1]
quantized ถูก clamp เหลือ: [−64.0, +38.5]     ← ข้อมูลนอกช่วงนี้หายถาวร
```

คำนวณให้เห็นภาพ: int8 มีแค่ **256 ระดับ**
ถ้าต้องครอบคลุมช่วง ±2000 → 1 ระดับ ≈ **16 หน่วย** → หยาบเกินกว่าจะแทนค่าได้

**ชั้นที่ 3 — หาผลกระทบที่จับต้องได้**

หาพิกเซลที่แย่ที่สุด:
```
float:     logit = +6.004  →  sigmoid = 0.9975  →  "เจอ object แน่นอน"
quantized: logit = −11.000 →  sigmoid = 0.0000  →  "ไม่เจออะไรเลย"
                    ↑ sign flip — พลิกจากเจอเป็นพลาด
```

**ชั้นที่ 4 — เบาะแสชี้ต้นตอ**

นับ cell ที่โมเดลบอกว่ามั่นใจ > 0.5:
```
ที่ 40×40:  556 cells    ← ผิดปกติมหาศาล
ที่ 20×20:  204 cells
```
ภาพปกติมี object ไม่กี่ตัว การที่โมเดลบอกว่า "เจอ" ที่ 556 ตำแหน่ง
→ **แสดงว่า float model ต้นทางเองก็เพี้ยนแล้ว ไม่ใช่ปัญหาของ quantization**

### 3.3 กลไกที่สรุปได้

```
สลับ SiLU → LeakyReLU โดยไม่ retrain
        │
        │  น้ำหนักเดิมถูกเทรนมาให้เข้ากับ SiLU
        │  พอเปลี่ยนฟังก์ชัน ค่าที่ไหลออกมาเปลี่ยนไปหมด
        ▼
logit distribution เพี้ยน — range ระเบิดถึง ±2000
        │
        ▼
int8 ใช้ scale เดียวต่อ tensor → รับ range กว้างขนาดนี้ไม่ไหว → saturate/clamp
        │
        ▼
cos_sim ตก + detection พลิกจาก "เจอ" เป็น "พลาด"
```

### 3.4 ข้อสรุปสองชั้น

**ชั้นที่ 1 — ไม่ใช่บั๊กของ pipeline**
เป็นผลลูกโซ่จากการยังไม่ fine-tune → แก้ที่ต้นเหตุ (ทำ fine-tune) แล้วปัญหาหายเอง
**และยืนยันแล้วด้วยผลจริง:** หลัง fine-tune ครบ INT8 mAP drop เหลือแค่ **1.5%**

**ชั้นที่ 2 — metric ที่เลือกใช้ตอนแรกผิด**
cosine similarity บน raw logit ก่อน decode **มองโลกแง่ร้ายเกินไป**
สิ่งที่ควร verify คือ **detection agreement / mAP หลัง decode + NMS** ซึ่งเป็นสิ่งที่ผู้ใช้เห็นจริง

> **บทเรียนเชิงวิธีวิจัย:** การเลือก metric ผิดทำให้ตีความผลผิด
> metric ที่ดีต้องสอดคล้องกับสิ่งที่เราสนใจจริงๆ ไม่ใช่สิ่งที่วัดง่าย

## 5. ผลการ Fine-tune

### 5.1 ผลลัพธ์

| โมเดล | activation | epochs | **mAP@0.5** |
|---|---|---|---|
| **YOLOv8n** | LeakyReLU(0.1015625) | 400 | **0.884** |
| **YOLO26n** | LeakyReLU(0.1015625) | 400 | **0.831** |

น้ำหนักที่ได้:
- `03-model/track-a-yolov8n-baseline/finetune/yolov8n_leaky_pkg_ft.pt`
- `03-model/track-b-yolo26n-target/finetune/yolo26n_leaky_pkg_ft.pt`

### 5.2 ข้อค้นพบเชิงวิชาการ

> **ค่านี้ใกล้เคียงกับที่ได้จากโมเดล SiLU ตัวเดิม**
> → **พิสูจน์ว่าการสลับ activation เพื่อให้ map ลง DPU ได้ ไม่ทำให้ความแม่นยำเสีย ถ้า fine-tune พอ**

ข้อสรุปนี้มีประโยชน์กับคนที่จะ deploy YOLO บน DPU ต่อไป เพราะเป็นการยืนยันว่า:
1. ข้อจำกัดเรื่อง activation ของ DPU **แก้ได้** ไม่ใช่ทางตัน
2. ราคาที่ต้องจ่ายคือ **เวลา fine-tune** ไม่ใช่ **ความแม่นยำ**

### 5.3 ประเด็นเรื่องความเข้ากันได้ของเวอร์ชัน

**คำถามที่ต้องตอบ:** โมเดลที่เทรนบน Colab (ultralytics 8.4.71) จะโหลดในคอนเทนเนอร์ (ultralytics 8.0.151, py3.7) ได้ไหม

**คำตอบ: ได้ และ LeakyReLU ยังอยู่ครบ** — ตรวจสอบแล้ว
→ เป็นการปิดความเสี่ยงที่อาจทำให้ต้องเทรนใหม่

### 5.4 การเชื่อมโยงกลับไปยังส่วนที่ 3

หลังจาก fine-tune แล้ว ปัญหา logit range ระเบิด **หายไป**
- ตอน deploy จริงบนบอร์ด: output ทั้ง 3 หัวมี float range ปกติ **ไม่ saturate**
- INT8 mAP drop เหลือแค่ **1.5%** (แทนที่จะพังยับอย่างที่เห็นในส่วนที่ 3)

→ **ยืนยันว่าการวินิจฉัยสาเหตุถูกต้อง และการแก้ที่ต้นเหตุได้ผล**

## 6. สรุปห่วงโซ่เหตุผลของทั้งไฟล์นี้

```
DPU ไม่รองรับ SiLU
      ↓
ต้องเปลี่ยนเป็น LeakyReLU(26/256) — เลขที่ fixed-point แทนได้พอดี
      ↓
แต่เปลี่ยนเฉยๆ ทำให้ logit ระเบิด ±2000 → INT8 saturate → detection พลิก
      ↓  (พิสูจน์ด้วยข้อมูล 4 ชั้น)
ต้อง fine-tune
      ↓
แต่เครื่องมี RAM แค่ 5.9 GB → เทรนไม่ได้
      ↓
ย้ายไป Colab T4 + ย้าย env ไปไดรฟ์ D:
      ↓
fine-tune 400 epochs → mAP 0.884 (เท่าเดิม)
      ↓
ผลปลายทาง: INT8 บนบอร์ดจริง mAP drop แค่ 1.5% ✅
```
