# 10 — ปัญหาวิศวกรรมที่เจอตลอดทาง และวิธีแก้

> **สรุปไฟล์นี้ใน 3 บรรทัด**
> รวบรวมปัญหา 13 ข้อที่เจอจริง พร้อมสาเหตุราก วิธีแก้ และบทเรียนที่ได้
> ส่วนใหญ่เป็นปัญหา **environment และทรัพยากรเครื่อง** ไม่ใช่ปัญหา logic
> ปิดท้ายด้วย case study การขุดหาสาเหตุแบบเป็นชั้น ซึ่งเป็นตัวอย่างวิธีคิดที่ดีที่สุดในโครงงาน

## 0. ทำไมต้องมีไฟล์นี้

อาจารย์ที่ปรึกษามักถามว่า **"ติดอะไรบ้าง"** — และคำตอบที่ดีไม่ใช่ "ไม่ติดอะไรครับ"
แต่คือการแสดงว่าเรา**เข้าใจระบบลึกพอที่จะหาสาเหตุรากได้** ไม่ใช่แค่ลองไปเรื่อยจนบังเอิญผ่าน

ปัญหาทั้งหมดในไฟล์นี้ถูกจัดกลุ่มตามหมวด และแต่ละข้อมี 5 ส่วน:
**อาการ → สาเหตุราก → สิ่งที่ลองแล้วไม่ได้ผล → วิธีแก้ → บทเรียน**

## หมวด A — ทรัพยากรเครื่อง (5 ข้อ)

### A1. WSL filesystem พัง คำสั่งพื้นฐาน segfault ⚠️ (รุนแรงที่สุด)

| | |
|---|---|
| **อาการ** | ลง torch ไปครึ่งทาง → `Read-only file system` → `Bus error` → `Segmentation fault` กับคำสั่งพื้นฐาน (`touch`, `df`, `rm`) |
| **สาเหตุราก** | WSL `.vhdx` วางบน Windows C: ที่เหลือแค่ **1.22 GB** · torch ~6 GB ทำให้ `.vhdx` ต้องขยายเกินที่ C: มี → kernel remount filesystem เป็น read-only เพื่อป้องกันข้อมูลเสียหาย |
| **วิธีแก้** | `wsl --shutdown` (filesystem กลับมาเขียนได้หลัง remount) + เคลียร์ C: ให้เหลือ > 12 GB ก่อนลงใหม่ |
| **ผลกระทบจริง** | Phase 0 artifacts **ไม่หาย** (เขียนเสร็จก่อนดิสก์เต็มนานแล้ว) — แต่เป็นสัญญาณเตือนที่นำไปสู่งาน P0 (ดูไฟล์ 03) |
| **บทเรียน** | **`df` ใน WSL โกหก** — โชว์ค่า provision 1007 GB แต่ตัวจริงคือพื้นที่ Windows host ที่ `.vhdx` วางอยู่ |

### A2. `/tmp` เต็ม ทั้งที่ดิสก์เหลือ 954 GB

| | |
|---|---|
| **อาการ** | `pip install torch` → `[Errno 28] No space left on device` |
| **สาเหตุราก** | `/tmp` เป็น **tmpfs (อยู่ใน RAM)** จำกัด 1.4 GB · pip ใช้เป็นที่แตกไฟล์ torch ก้อนใหญ่ |
| **วิธีแก้** | `TMPDIR=~/thesis/gpu_baseline/piptmp pip install --no-cache-dir ...` |
| **บทเรียน** | **ดิสก์เหลือ ≠ ทุก mount เหลือ** — ต้องเช็ค `df -h /tmp` แยกต่างหาก |

### A3. ไดรฟ์ C: เต็มเรื้อรัง (0.44 GB)

| | |
|---|---|
| **อาการ** | pip install ล้มซ้ำๆ · หลายเครื่องมือพังแบบไม่มีเหตุผลชัด |
| **สาเหตุราก** | C: ใช้ไป 274 / 275 GB |
| **วิธีแก้** | ย้าย environment ไปไดรฟ์ D: (`D:\yolo26-export-env`, เหลือ 40.9 GB) **พร้อม redirect temp/cache:** `$env:TEMP` / `$env:TMP` / `$env:PIP_CACHE_DIR` ไป D: |
| **จุดที่พลาดง่าย** | **ถ้าไม่ redirect TEMP** pip จะยังแตกไฟล์ build ลง `C:\...\Temp` แล้วล้มอยู่ดี แม้ปลายทางจะอยู่ที่ D: |
| **วิธีกู้พื้นที่แบบปลอดภัย** | `pip cache purge` (ได้คืน ~237 MB) · เคลียร์ `%TEMP%` (มี ~1.9 GB) |
| **บทเรียน** | ก่อนติดตั้งอะไรใหญ่ๆ ให้เช็ค free space ก่อนเสมอ ถ้า < 2 GB ให้ไปไดรฟ์อื่น |

### A4. RAM ไม่พอเทรน — spawn python ไม่ได้ด้วยซ้ำ

| | |
|---|---|
| **อาการ** | `System.OutOfMemoryException` ตอน PowerShell พยายามเรียก python |
| **สาเหตุราก** | host มี RAM รวม **5.9 GB** (เหลือว่าง ~1 GB) |
| **วิธีแก้** | **ย้ายการ fine-tune ไป Google Colab (T4)** — host ยังใช้ quantize/compile/export ได้ปกติ เพราะงานพวกนั้นไม่กิน RAM เท่าการเทรน |
| **บทเรียน** | รู้ขีดจำกัดของเครื่องก่อน แล้วออกแบบการแบ่งงาน (local vs cloud) ตามนั้น |

### A5. quantize container ตาย `unexpected EOF` exit 125 ⭐

| | |
|---|---|
| **อาการ** | container ตายกลางคัน ไม่มี error message ที่มีความหมาย |
| **การวินิจฉัย** | รัน `docker info` เพื่อดูสถานะ → **คำสั่งนี้เองก็ล้ม** `errno=1450` = `ERROR_NO_SYSTEM_RESOURCES` → บ่งชี้ว่าเป็นปัญหาระดับระบบ ไม่ใช่ของสคริปต์ |
| **สาเหตุราก** | host RAM 5.88 GB → WSL2 cap ~2.9 GB → ปกติจะใช้ pagefile ช่วย **แต่ C: เหลือ 0.5 GB ทำให้ pagefile ขยายไม่ได้** |
| **วิธีแก้** | เคลียร์ C: (0.2 → **17 GB**) → pagefile/swap ขยายได้ + ลด calibration เป็น `--subset_len 32 --batch_size 4` |
| **สิ่งที่ไม่ต้องทำ** | **ไม่ต้องแตะ `.wslconfig`** — ซึ่งเป็นวิธีที่คนส่วนใหญ่จะไปแก้ แต่ไม่ได้แก้ต้นเหตุ |
| **บทเรียน** ⭐ | **ดิสก์เต็มทำให้ RAM ไม่พอได้** (ผ่านกลไก pagefile) — เป็นความเชื่อมโยงที่ไม่ชัดในตอนแรก |

## หมวด B — Environment และ Dependency (3 ข้อ)

### B1. `cuda.is_available() = False` ทั้งที่ลง torch สำเร็จ ⭐

| | |
|---|---|
| **อาการ** | `pip install torch` ผ่านไม่มี error แต่ใช้ GPU ไม่ได้ |
| **สาเหตุราก** | Python 3.14 (default ของ Ubuntu 25.10 "resolute") ใหม่เกินไป · PyTorch ยังไม่ build CUDA wheel สำหรับ cp314 → pip เลย fallback ไปให้ **CPU build** |
| **สิ่งที่ลองแล้วไม่ได้ผล** | `apt install python3.12` (ไม่มีใน repo ของ resolute) · deadsnakes PPA (ไม่ publish repo สำหรับ resolute → `apt update` fail) |
| **วิธีแก้** | ใช้ **miniforge** สร้าง env Python 3.12 — ได้ binary สำเร็จรูป ไม่ต้องคอมไพล์ ไม่แตะ system Python |
| **บทเรียน** ⭐ | **"ลงสำเร็จ ≠ ได้ของที่ต้องการ"** — ต้อง verify ที่**ผลลัพธ์** (`cuda.is_available()`) ไม่ใช่ที่ exit code ของ pip |

> บทเรียนข้อนี้เป็นแพทเทิร์นเดียวกับปัญหา C2 ข้างล่าง (`set +e` ทำให้สคริปต์บอกว่าสำเร็จทั้งที่ล้ม)

### B2. ultralytics ลาก torch CPU มาทับ

| | |
|---|---|
| **ความเสี่ยง** | `pip install ultralytics` resolve torch dependency เอง อาจดึง CPU build มาทับ `+cu128` ที่อุตส่าห์ลงไว้ |
| **วิธีป้องกัน** | ลง torch ก่อน → `pip install ultralytics --no-deps` → ลง dependency ที่เหลือเองแบบเลือกตัว |
| **การยืนยัน** | หลังลงเสร็จ เช็คว่า `torch.__version__` ยังเป็น `+cu128` ✅ |
| **บทเรียน** | dependency resolver ทำลาย environment ที่ตั้งใจ pin ไว้ได้ — ต้อง verify หลังลงทุกครั้ง |

### B3. Inspector รัน YOLO26n ไม่ได้ (Python version clash)

| | |
|---|---|
| **อาการ** | รัน `--inspect` ไม่ได้เลย |
| **สาเหตุราก** | `pytorch_nndct` ต้องการ py3.7.12 (ผูก ABI) · `ultralytics 8.4.71` ต้องการ py ≥ 3.8 · ไม่มี env ไหนในคอนเทนเนอร์มีทั้งคู่ |
| **วิธีแก้** | export ONNX ใน env py3.9 แยกบนไดรฟ์ D: แล้ววิเคราะห์ op graph เอง |
| **บทเรียน** | toolchain compatibility บล็อกก่อนถึงเรื่องเทคนิคด้วยซ้ำ — รายละเอียดเต็มในไฟล์ 08 |

### C1. `XIR don't support multi-outputs op` ⭐

| | |
|---|---|
| **อาการ** | export XIR ล้มที่ `nndct_chunk` (×8 จาก C2f) และ `split_with_sizes` (จาก Detect head) |

### D1. Docker Desktop crash "initializing Inference manager"

| | |
|---|---|
| **อาการ** | Docker Desktop เปิดไม่ขึ้น ค้างที่ `dockerInference` |
| **สาเหตุราก** | ฟีเจอร์ Model Runner ค้างกับ stale AF_UNIX socket ใน `%LOCALAPPDATA%\Docker\run\` ที่ Windows ลบไม่ได้ |

### D2. `scp` ขึ้นบอร์ดไม่ได้

| | |
|---|---|
| **อาการ** | `scp` ล้ม · `scp -O` (legacy) ก็ยังไม่ผ่าน |

| **บทเรียน** | embedded Linux image มักตัดของที่ไม่จำเป็นออก — อย่าสมมติว่ามีเครื่องมือมาตรฐานครบ |

### D3. บอร์ด decode วิดีโอ H.264 ไม่ได้

| | |

| **สาเหตุราก** | OpenCV 4.5.2 บน PetaLinux (ผ่าน GStreamer) ไม่มี codec H.264 |
| **วิธีแก้** | แปลงคลิปเป็น **MJPG `.avi`** ก่อนโอนขึ้นบอร์ด |

### D4. Serial console ถูกจองแบบ exclusive

| | |
|---|---|
| **อาการ** | เปิด COM6 ซ้ำจากอีกหน้าต่าง → `Access denied` |

## หมวด E — ข้อมูลและ Quantization (2 ข้อ)

### E1. mAP คำนวณออกมาผิด

| | |
|---|---|
| **อาการ** | ตัวเลข mAP ไม่สมเหตุสมผล |
| **สาเหตุราก** | ground truth จาก Roboflow เป็น **polygon segmentation** ไม่ใช่ bounding box (`class x1 y1 x2 y2 ... xn yn` แทนที่จะเป็น `class cx cy w h`) |
| **วิธีแก้** | เขียนโค้ดแปลง polygon → bbox (หา min/max ของทุกจุด) ก่อนคำนวณ |
| **บทเรียน** | ต้องเข้าใจ format ของ ground truth ก่อนวัดผล ไม่ใช่สมมติว่าเป็นรูปแบบมาตรฐาน |

### E2. quantization พังเงียบๆ เพราะ calibration ผิด scale ⭐ (ฝั่ง Efinix)

| | |
|---|---|
| **อาการ** | quantize ผ่านไม่มี error **แต่ผลเป็นขยะ** — score ระเบิด ได้ 300+ กล่องมั่ว |
| **การวินิจฉัย** | ไปดูค่า scale ที่ converter คำนวณ → `input scale = 1.0` ← ผิดปกติชัดเจน |
| **สาเหตุราก** | calibration data อยู่ในช่วง `[0,255]` แต่ SavedModel คาดหวัง `[0,1]` → converter คำนวณ scale ครอบคลุมช่วงที่ผิด |
| **วิธีแก้** | normalize `/255` ใน representative dataset |
| **ผลหลังแก้** | `input scale = 0.00392 = 1/255` · `zero-point = −128` ← **เป็นเลขที่ถูกต้องโดยโครงสร้าง** |
| **บทเรียน** ⭐ | **quantization พังได้โดยไม่มี error แจ้งเตือน — ต้องตรวจค่า scale/zero-point ที่ได้ออกมาเสมอ** |

> **สังเกตความคล้ายกับ E1 และกับปัญหา calibration set ผิดโดเมนในไฟล์ 05:**
> ทั้งหมดเป็นตระกูลเดียวกัน — **"ข้อมูลที่ป้อนเข้าไม่ตรงกับที่ระบบคาดหวัง"**
> และทั้งหมด**ไม่มี error แจ้งเตือน** ต้องจับได้ด้วยการตรวจค่ากลางทาง

## Case Study — การขุดหาสาเหตุแบบเป็นชั้น (M5)

ส่วนนี้เป็นตัวอย่างวิธีคิดที่ดีที่สุดในโครงงาน จึงแยกออกมาเล่าเต็ม

### สถานการณ์

ตอน verify ว่า quantization ถูกต้องหรือไม่ ใช้ **cosine similarity** เทียบ float vs quantized
เกณฑ์ที่ตั้งไว้ > 0.99 แต่ได้ **0.991 / 0.942 / 0.894** → ต่ำกว่าเกณฑ์ที่ 2 ใน 3 tensor

### แทนที่จะเดา — ขุดเป็นชั้น

**ชั้นที่ 1 — ตั้งสมมติฐานแล้วทดสอบเพื่อ "หักล้าง"**

สมมติฐาน: ส่วน BOX (DFL) น่าจะเป็นตัวฉุด (เพราะมี 64 channel เยอะกว่า class)

| Output | BOX cos | CLASS cos | CLASS float logit range |
|---|---|---|---|
| 80×80 | 0.963 | 0.992 | [−128.7, 11.1] |
| 40×40 | 0.944 | 0.941 | [−340.5, 29.8] |
| **20×20** | 0.925 | **0.893** | **[−2007.4, 169.4]** |

→ **สมมติฐานถูกหักล้าง** (CLASS แย่พอกันหรือแย่กว่า)
→ **แต่เห็นแพทเทิร์นใหม่:** logit range ระเบิดตามความละเอียดที่หยาบลง

> **จุดสำคัญของวิธีคิด:** การทดสอบที่หักล้างสมมติฐานตัวเองมีค่าเท่ากับการยืนยัน
> เพราะมันตัดตัวเลือกออกและมักเผยเบาะแสใหม่

**ชั้นที่ 2 — พิสูจน์กลไกโดยตรง**

```
float range ที่แท้จริง:   [−128.7, +56.1]
quantized ถูก clamp เหลือ: [−64.0, +38.5]   ← ข้อมูลนอกช่วงนี้หายถาวร

คำนวณ: int8 มี 256 ระดับ · ถ้าต้องครอบคลุม ±2000
       → 1 ระดับ ≈ 16 หน่วย → หยาบเกินกว่าจะแทนค่าได้
```

**ชั้นที่ 3 — หาผลกระทบที่จับต้องได้**

```
พิกเซลที่แย่ที่สุด:
  float:     logit = +6.004  →  sigmoid = 0.9975  →  "เจอ object แน่นอน"
  quantized: logit = −11.000 →  sigmoid = 0.0000  →  "ไม่เจออะไรเลย"
                                                       ↑ sign flip
```
→ เปลี่ยนจากตัวเลข abstract (cos_sim) เป็นผลกระทบที่เข้าใจได้ (detection พลิก)

**ชั้นที่ 4 — หาเบาะแสชี้ต้นตอ**

```
นับ cell ที่โมเดลมั่นใจ > 0.5:
   ที่ 40×40:  556 cells   ← ผิดปกติมหาศาล
   ที่ 20×20:  204 cells
```
ภาพปกติมี object ไม่กี่ตัว → **แสดงว่า float model ต้นทางเองก็เพี้ยนแล้ว**
→ ปัญหาไม่ได้อยู่ที่ quantization

**ชั้นที่ 5 — ตรวจ metric ที่ใช้เอง**

ลองคำนวณ cos บน post-sigmoid → ได้ **แย่ลงอีก (0.65 / 0.75 / 0.71)**
แต่วิเคราะห์แล้วพบว่า**หลอกตา** — sigmoid ของ logit ±2000 อิ่มตัวเป็น 0/1 หมด
→ cosine บน field ที่เกือบ binary และ sparse จึง noisy
→ **metric นี้ไม่ควรใช้ตัดสิน**

### กลไกที่สรุปได้

```
สลับ SiLU → LeakyReLU โดยยังไม่ fine-tune
        ▼
logit distribution เพี้ยน — range ระเบิดถึง ±2000
        ▼
int8 per-tensor fixpos เดียว รับ range กว้างขนาดนี้ไม่ไหว → saturate/clamp
        ▼
cos_sim ตก + detection พลิกจาก "เจอ" เป็น "พลาด"
```

### ข้อสรุปสองชั้น

**ชั้นที่ 1 — ไม่ใช่บั๊กของ pipeline**
เป็นผลลูกโซ่จากการยังไม่ fine-tune → **แก้ที่ต้นเหตุ** (ทำ fine-tune ก่อน) แล้วปัญหาหายเอง
**ยืนยันแล้วด้วยผลจริง:** หลัง fine-tune ครบ INT8 mAP drop เหลือ **1.5%**

**ชั้นที่ 2 — metric ที่เลือกใช้ตอนแรกผิด**
cosine similarity บน raw logit ก่อน decode **มองโลกแง่ร้ายเกินไป**
สิ่งที่ควร verify คือ **detection agreement / mAP หลัง decode + NMS** ซึ่งเป็นสิ่งที่ผู้ใช้เห็นจริง

> **บทเรียนเชิงวิธีวิจัย ⭐:** การเลือก metric ผิดทำให้ตีความผล ผิดได้
> metric ที่ดีต้องสอดคล้องกับ**สิ่งที่เราสนใจจริง** ไม่ใช่**สิ่งที่วัดง่าย**
